## 1. The requirement

A services company runs platform and delivery engineers. Each engineer serves two or three projects of different customers. Work arrives from customer-facing channels:

- meetings, which are recorded, summarised into requirements and turned into a ticket or a task input;
- chat, on two chat products;
- ticket systems, on three issue trackers.

Depending on the customer, the team opens a task and logs time in one system or another. Today an engineer then hands the input to a coding agent, one of several third-party agent harnesses, by hand.

The wanted flow has five steps:

1. Take a request from a customer-facing source.
2. A coding agent writes a plan. The agent has a configured "brain", a memory that knows which repository, environment and conventions each request maps to.
3. The engineer reads the plan, edits it and approves it.
4. The agent executes the plan. The outcome is a pull request, a deployment or another change tied to code and system context.
5. The engineer verifies the outcome with the customer and loops until it is accepted.

Engineers who develop may tune the flow: add plugins, change prompts. The engineer's job becomes facing the customer and verifying outcomes. The work is mostly operations work, with development work included.

Two questions came with it. Does this fit the platform as a plugin, or does it need a separate platform? And how does it compare with an open-source personal agent that has a message gateway over many chat channels and a persistent memory (section 12)?

## 2. A plugin bundle, not a separate platform

**Answer.** A plugin bundle, not a separate platform: one optional first-party bundle, working name `aiops-delivery`, on the definitions the platform already has in design. It needs no change to the kernel, the launcher or the loader, no new shipped profile and no change to the order of work. The answer holds under conditions, and not yet.

- **When.** Nothing of it runs inside the platform before the first community release, the exit of S8b. Steps S2b to S8b are ahead and none has a date (`08:630`). Until then the only form is a convention outside the platform (form 0, section 10).
- **Conditions.** Several customers in one install depend on ADR-049 leaving tenant create on a self-host in the community edition (D2) and on how one engineer selects a tenant (D16); otherwise the community form is one install per customer for good. The agent executing the plan inside the platform depends on D6 option (a), on ADR D and on D7, and has no date; section 16 weighs the three harnesses and the sandbox service named as candidates for it on 2026-11-27, and adds D18 to D22. The packaging depends on D15.
- **What the dated forms are.** Forms 2 and 3 are a plan desk and a guarded write around a coding agent that still runs outside the platform. The platform drafts and checks the plan, records the sign-off and, from form 3, opens the pull request under approval. The code is written by the engineer's own agent and uploaded. The hand-off by hand that the requirement wants removed (section 1) shrinks to one file out and one patch in (section 5.4); it goes away only with form 5.
- **What stays outside.** Some needs are served in no form (the second table below).

None of these is a reason for a second platform: each is a line to amend by ADR, a question for the owner, or a need that a second platform would have to build as well.

**Reasons.**

1. Steps 2, 3 and 5 of the flow, and the pull-request outcome of step 4, map onto a definition that exists in design (section 3): a run of an agent harness for the plan (`00:45`), `approval.Decide` for the decision (`00:68`), the change ledger and the lease for the write (`00:69`, `00:70`), an executor whose write is a pull request (`00:62`), a verifier (`00:75`), the audit chain (`00:73`) and the tenant for the customer (`00:326`). Three needs map onto nothing (section 3, rows 4, 19 and 25), and the agent turning the approved plan into a change maps onto nothing before form 5 (row 30).
2. The part that is hard to build twice is the policy spine. Approval floor, change ledger, credential leases, quorum, audit chain and scrub are first-party plugins that the kernel makes impossible to shadow (principle 5, `00:28`), and five generic mechanisms keep a tuned prompt or an added plugin from weakening them (`00:259`). A separate platform would rebuild these or run without them. Section 12 shows what running without them looks like.
3. The ways in already exist or are on the path: an optional bundle of the release that an operator enables with no rebuild (`00:521`; for a bundle that wraps no upstream this waits for D15), a remote plugin in any language (`08:391`), a pack with no code (`00:507`), and a distribution the operator builds and signs for site-private in-process code (`00:107`, `08:403`). Nothing in the design falls outside the closed vocabularies of the kernel, the launcher and the loader (`00:263`).
4. A pillar is one `core:group` row that names its persona, tool set, harness selection and executors (`00:55`). Delivery work is one more group.
5. No outside product covers the whole flow (section 12), so there is no platform to adopt in place of a bundle.

## 4. What is new

The standing rules apply to each item: no definition merges without its fake, its suite, its `definition.yaml`, a provider and a consumer; no plugin merges without `aiopsctl plugin check` and a T3 test; a definition lands with its first consumer (`08:678`, `08:680`, `00:206`). The list is ordered by when each item is first needed (section 10).

### 4.1 The first build: one plugin, one command row, one group row

**`delivery`, a plugin.** In-process Go, first-party, under `plugins/`, roles api and worker. Key: none. It provides nothing, because no other plugin calls it in process: the CLI and the chat verb reach it through its routes, and a seam exists when a consumer does (`00:26`). It injects `sql`, `blob`, `jobs`, `events`, `http`, `authz`, `audit` and `harnesses`, wants `notifiers` and `chatCommands`, and from the guarded form injects `executors` and `changes`, which have open consumers (`00:227`, `00:234`). It injects neither `approval`, which is reached through `change-hub` (`03:296`), nor `credentials`, which is consumer-bound to `remediation` (`00:227`). It listens on `run/first-message` (open, `07:460`) and on `run/answer` (signed, so a first-party listener, `07:461`), for the pair (delivery, `investigate`) only. Its durable namespace is the schema `delivery` and a blob prefix: `request` (source reference, text digest, subject, state), `plan_version` (number, parent, author subject, digest, blob reference), `patch` (plan version, author of record, declared origin, digest, blob reference), `iteration` (run ids and change ids of one request), `mapping` (the versioned per-tenant rows of section 6.2) and `note`. With no definition it has no fake and no suite of its own; it carries the generated cycle test and two-tenant test of every process-scope plugin (`00:300`) and a T3 test. A `deliveries` definition (singular, class open, provider `delivery`, an in-memory record as the fake, a suite over the state machine and the digest rule) is written in the change that adds its first in-process consumer, and not before.

**`command-delivery`, a contribution to `commands`.** Key `commands`: a registry, class open on both sides, provider `cli`, no remote contribution (`00:222`). The definition, its fake and its suite exist since S2a (`sdk/def/commands/v0/definition.yaml`); this adds one contribution, which passes that suite. It sits in the companion bundle `aiops-delivery-cli` that the operator enables in the profile `cli`, by the pattern of `command-slack` (`ADR-061:1407`, `00:284`), and it calls the routes of `delivery`. Paths: `delivery request`, `plan` (with `show --bundle` for the hand-off file of section 5.4), `propose`, `status`, `accept`, `rework`, `note`, `map`. A mapping file kept under form 0 is entered once through `delivery map`; its format is a draft until ADR A, so that is a manual step and no promise of compatibility.

**`pillar-delivery`, a `core:group` row.** No key, no definition and no suite: a pillar has none (`00:55`). The bundle `aiops-delivery` carries it, as the first-party bundle `aiops-pillars-mvp` carries its groups (`05:181`); an installed artifact could not (`05:154`). Its config names the persona and operating rules as content, leaves `harness` empty so the default harness runs (`05:191`), sets `kinds: {investigate: {firstMessage: delivery, answer: delivery}, ask: {}}` in the form of `05:193`, an empty `signalKinds`, `tools: []`, and from the guarded form the executor row of section 4.2. With no default tools the run is offered only the enabled tool rows that name this pillar (`05:196`): the read tools of the tenant's tracker and forge packs, and none of the telemetry, Kubernetes or kernel-data tools of the incident pillar. If the group schema of S8a refuses one row as both builder and checker, `delivery` splits into two rows.

**Content.** A persona, operating rules and the plan schema (a JSON Schema: summary, assumptions, steps with intent and paths touched, repository and base, environment, checks, rollback, open questions, and from form 3 an optional set of line-level hunks for a small change; a change set of whole files is never part of it, section 4.2). It is bundle content, versioned with the bundle (`08:339`), and holds no customer text (`08:1348`).

**Rules `delivery` holds in its own code.** Each is a rule of the plugin and of its T3 test, and none needs a change to the policy spine.

1. *One customer per tenant.* The mapping has no customer column and `delivery` has no customer selector: the tenant is the customer, in every form. Code cannot detect two customers behind one tenant, so this rule is an operating rule as well (section 6.1).
2. *No run from an unauthenticated source.* A request from any source other than an authenticated platform user lands in `triage`, and a holder of `deliveries.open` releases it before any run starts. The external requester of such a request is display text and never a subject.
3. *Two blocks, two trust labels.* The first message carries a trusted block (the mapping row, the notes and the list of convention files to read first) and a separate fenced untrusted block (the request text and any rework text). Repository files, the convention files included, and tool results are untrusted content the agent reads; the operating rules say that they are data and not instructions.
4. *Notes hold no copied text.* A note written at acceptance holds fields that code derives: request id, repository, environment, digests, change reference. Free text enters a note only when a platform user writes it. Text of a request, a plan or a tool result is never copied into a note, so it is not replayed into later runs.
5. *The proposer is the author of record.* `delivery propose` is accepted only for a plan version with a current sign-off and a patch recorded for that version, and only from the subject who uploaded that patch or, for hunks from a run, who signed that version. `change-hub` records that verified subject as the requester, so the rule "not the requester" (`03:445`) keeps the author of a patch from approving it. A person who wants to propose a colleague's patch uploads it and becomes its author of record.
6. *An upload declares its origin.* An uploaded patch carries the tool and the model endpoint that made it, as the uploader's declaration, and `delivery` refuses it where the tenant's consent record does not allow that endpoint (D13). The declaration is a person's word, not proof.

### 4.2 The guarded pull request: three contributions to existing definitions

**The catalogue action `open-pull-request`, a contribution to `executors`.** Key `executors`: a registry, provider-bound to `remediation`, the only caller of an executor (`00:57`, `00:234`); consumers are the surfaces that ask for a typed action, here `delivery`. The definition, its fake and its suite are built at S5 with a no-op executor (`08:700`); this contribution passes the obligations half of that suite (`00:57`). Its home is a row of its own in the optional bundle, named by `pillar-delivery` alone. It is not an action of `remediation-executor-gitops-pr`, which `pillar-incident` carries in `aiops-pillars-mvp` from P2 (`00:287`): an action whose content is an arbitrary patch stays out of the catalogue and the golden dumps of every shipped profile. Whether the two rows share forge code is for ADR-031 and ADR B. Target: an entity reference of a kind the action declares, with the repository as a typed parameter (`07:64`). Parameters: repository, base commit, branch, patch digest, the digest of the signed plan version the patch was recorded for, and two facts a person declared for the repository. `Plan` is side-effect free and reads the repository with a read credential. It refuses unless all of this holds: the patch is in the one accepted format and under the size bound; it applies on the base commit exactly, with no fuzz; no path is on the deny list; no added line contains a pseudonym (section 13); and the two declared facts are set, which code copies into the envelope from the mapping row: whether the base branch requires another person's review, and whether a pushed branch runs a pipeline with secrets (section 5.7). Where the forge lets the read credential read the protection of the base branch, `Plan` reads it and refuses when the branch is unprotected or the lease identity could push to it. It reports the paths, the size and the pipeline posture as blast radius, and returns a reference to the patch by digest so that a surface can show the diff. The deny list is a value of the row's config; its default refuses pipeline definitions, so a change to a pipeline definition is made outside the platform unless the operator removes that entry. `Apply` pushes one branch and opens one pull request under the lease, idempotent on the token; the receipt is the pull request reference and its head commit. `Rollback` closes the pull request and deletes the branch before a merge, and is a revert pull request after one. `Verify` reads the pull request back and returns a state (`07:671` to `07:675`).

**What bounds this action.** The schema types the envelope, not the effect: the action space is any patch under the size bound, and none of the checks above reads what the patch does. The control is a person who reads the diff before deciding, and then the review on the forge. The approval notice and `aiopsctl` therefore show the diff that the digest names, or the digest and a link where a surface cannot. Whether `approval.Decide` refuses a decision for this action class from a surface that cannot show the diff is decided in ADR B; today a request shows "plan, blast radius" (`06:389`; section 9, row 36). The platform cannot prove that the approver read it. No code checks that a patch implements the plan it names: the plan digest in the envelope tells the approver which signed plan the author says the patch implements, and nothing more.

**Hunks from a run, from form 3.** An answer may carry line-level hunks for a small change. They pass the same `Plan`. Every tool result reaches the model capped and scrubbed (`07:789`, `00:74`), so a hunk built from a scrubbed or truncated view has context or removed lines that differ from the raw file and fails the exact apply, and the check on added lines catches a pseudonym. A whole file written from such a view would replace every scrubbed value and cut the file at the cap, with nothing to compare it against, so whole files are never accepted. This origin needs `pii` to expose a recogniser (section 9, row 21); until it does, only uploaded patches are accepted. Form 2 has no `Plan` in its path, so it has no hunks: the plan lists the intended edits as prose and paths.

**A lease row for a Git forge, behind `credentials`.** Key `credentials`: provider-bound to `credential-lease` with its `lease-*` rows and consumer-bound to `remediation` (`00:227`). No new consumer of the key is added. It is the row ADR-031 decides for the GitOps executor (`08:1165`); this record asks that the same decision cover application repositories (section 9, row 31). The row of `00` §5.4 states what the token itself can do on each forge if it leaks, not what the executor does with it (section 4.4).

**`verify-pull-request`, a contribution to `verifiers`.** Key `verifiers`: class open, dispatched by `change-hub` (`00:227`, `00:75`). It reads whether the pull request is at the expected head, the state of its checks, whether it is merged and, for a GitOps repository, whether the sync was seen. It reports a state; the mapping onto the closed verdict list is fixed by the ADR of section 11, row B. It is one more check beside the two of `00:75` and the condition rounds that ADR-031 writes in as the one third check (`00:769`, `08:831`), so ADR B edits the Verification before close row. It is not a condition round: it reads the forge and no telemetry store. Its receipt differs too: for `remediation-executor-gitops-pr` the controller's sync is the receipt (`05:736`), while for this action the receipt is the pull request and its head commit, and the sync is only one of the states read later. ADR B may instead fold the read into the executor's `Verify` behind `verify-readback` and add no check. Either way it has to say how a change with no alert is judged (section 9, row 20), and that failing checks on a pull request are a state and not the verdict `failed`, which hands over to the rollback policy (`05:613`; section 9, row 35). Customer acceptance is a state of the delivery request and never a verdict word (`05:611` to `05:614`).

### 4.3 Two definitions, each written only when its first consumer is built

**`requestSources`, for push and pull intake.** A plural key, a registry; class open; tenant by handle; remote `contrib`, so it is written with its remote adapter (`08:645`). Provider and dispatcher: `delivery`. Contributions: `request-source-*` rows, in-process or remote. A contribution has `Describe` (family, push or poll), `Parse(payload)` and an optional `Poll(cursor)`, and each returns requests with an external reference, a project key, a title, a body and the external requester. The external requester is display text, and a request from a source row lands in `triage` (section 4.1). The dispatcher calls the contribution, never the reverse, because a remote plugin cannot own a route or a job (`07:1117`). Fake: a scripted source. Suite: `Parse` is deterministic and has no effect, the external reference is stable across a replay, the body is returned raw and never pre-scrubbed (`00:74`), a poll cursor only advances. It lands with the first source that is not the API, and the ADR that defines it also settles how a pushed webhook gets its tenant (section 9, row 13).

**`workspaces`, for a run that edits a checkout.** Undecided. This paragraph lists what the ADR of section 11, row D has to settle and fixes no shape. The working shape is a singular, provider-bound key with no remote form, whose consumer is the dispatcher of the run: `Open(repository, base commit, mode)` returns a handle, `Seal(handle)` returns the patch and the log as artifacts by digest, and `Wipe(handle)` ends it. That shape binds the key to whichever plugin wraps a sandbox service, so the clone, the unpack of a hostile tree, the diff and the egress probe would be written again for each service. The shape proposed to ADR D instead is a first-party provider bound to `workspaces` that owns those four and dispatches a registry of sandbox-service rows, whose contributions only create a sandbox, upload, start one command, download and kill (principle 9, `00:32`; section 16.4). Form 5 runs the tests of the repository, which is arbitrary code from a repository that may be hostile, so four properties are requirements:

1. One sandbox per run, created at `Open` and destroyed at `Wipe`. A long-lived instance that is only cleaned keeps background processes, files outside the checkout and poisoned tool caches for the next run and the next tenant. On a self-host `sidecars-static` only names the shared instances that compose or Helm started (`03:113`), so nothing designed today can start a sandbox per run; the provider would call a sandbox service the operator runs (section 9, row 33). A service of that kind was read on 2026-11-27: its API creates one micro virtual machine per call and destroys it on request, and it exists as a hosted service and as a runtime an operator installs on one host (section 16.3). That answers who would start the sandbox. Nothing was run against it. One thing is still reused by every run, the template a sandbox starts from: it holds harness binaries and toolchains only and is never built from the content of a customer's repository, which is an exception ADR D rules on (section 16.4).
2. The clone and the diff are made outside the sandbox, on a copy of the tree. Git is never run inside a checkout whose configuration, hooks and attributes the code in it could rewrite, because that would run that code where the clone credential is. The guides of the service read for section 16.3 do the opposite, with the clone and the diff inside the sandbox and the repository token passed in; a provider does not follow them.
3. Everything reachable from inside is a credential with a row in the table of `00` §5.4 and a stated blast radius: the model key of a wrapped harness (`03:520`) and any endpoint that serves the run's tools (`HR:91`). "The run holds no credential" is true of neither topology: a harness beside the checkout holds that key and reaches every read tool of the tenant, and a harness outside the sandbox needs edit and execute operations that `tools` never offers a harness (`07:789`). A sandbox service adds two credentials that stay outside, with the provider: the API key of the service and the access token of its agent inside the sandbox (section 16.4). An endpoint counts by what it serves and not by its address: the listener that serves the model route also serves `/v1/admin` and, where enabled, `/v1/tools` (`00:133`), so an allow by address puts every route of that listener in reach of the code in the sandbox.
4. Egress is denied by default, and the deny is observed and not only set. The provider sets the deny on every `Open`, reads it back, and then runs a probe from inside the sandbox before it uploads anything: a connection to an address the provider holds has to fail, over TCP, over UDP and over IPv6, and `Open` fails closed if one succeeds. A read-back alone passes on a runtime that stores the setting and does not enforce it. The host of the sandbox service also sits behind a deny on its own network that does not depend on the service. The deny is not a default to inherit: the service read for section 16.3 leaves outbound access open unless the create call denies it. A dependency mirror on the allow-list is a second destination, and an exception ADR D rules on (section 16.4). The requirement is not established for any runtime until the probe and the T3 test have run on it.

A suite on an in-memory fake proves the interface only. Isolation is a property of a sandbox runtime, proven by a T3 test on a real provider, run for each pinned commit of the runtime. The test tries persistence across runs, the template path included, a credential read, access across handles, egress over TCP, UDP and IPv6, and every route of the gateway's listener other than the model route. ADR D also decides whether such a run stays in `harnesses` or needs a registry of its own (D6).

## 5. The flow, traced

### 5.1 Step 1: take a request

- **Entry.** `aiopsctl delivery request add --source <reference> --file <text>`, the route `POST /v1/delivery/requests`, or the chat verb `delivery` on an enabled surface. A meeting summary enters as a file; the platform records and transcribes nothing.
- **Keys.** `http` runs identity and then mints the tenant handle before the handler (`00:217`); on chat, the surface's installation record resolves the tenant and `chat` mints (`00:330`). `authz.Check` with a permission the plugin declares, `deliveries.open`. `sql`, `events` and `audit` commit the request row, its event and its audit row in one transaction (`03:480`).
- **Invariants.** The tenant is never derived from the payload (`00:327`). The request text is untrusted input and reaches a model only in the fenced untrusted block of the first message, which is kept apart from the block that holds the mapping row and the notes (section 4.1).
- **Sources other than a platform user.** A request that a source row parsed from a webhook or a poll lands in `triage`, and a holder of `deliveries.open` releases it before any run. Otherwise anyone who can file or edit a ticket could start a model run over the customer's repository with text of their choice, hold one of the two run slots (`00:425`) and spend the daily budget.
- **Mapping.** The `mapping` rows of the tenant resolve the subject (an entity reference), the repository, the base branch and the environment. Payload fields select a row inside one tenant and never the tenant, which is the customer (section 6.1). A request that matches no row stops in `triage` for a person; no run starts.
- **No signal.** The request is not a `Signal`, so `correlate` and `casefile` are not involved and the incident measures are not touched.

### 5.2 Step 2: the agent writes a plan

- **Keys.** `delivery` calls `harnesses.Dispatch` with kind `investigate`, the pillar `delivery`, the entity reference as subject and the request id as trigger. `agent-runs` selects the harness, takes the slot lease and the budget lease, writes the run row and dispatches `run/first-message` with the pillar and the kind (`03:200`).
- **Hooks.** On `run/first-message`, `delivery` adds two bounded blocks: a trusted one with the mapping row, the notes and which convention files of the repository to read first, and a fenced untrusted one with the request text and any rework text (section 4.1). On `run/answer`, `delivery` validates the answer against the plan schema and may return one follow-up message (`07:461`).
- **Tools and model.** The harness reads the ticket and the repository through rows of `tool-mcp`; every call gets the actor filter, the output cap, the scrub and an audit row (`07:789`). For a tracker or a forge that is not a proven read: the effects class of a `tool-mcp` row is asserted by its pack and not proven by the recording sandbox, and model-written arguments leave the kernel (`07:822`, `HR:64`). The controls are the allow-list with the recorded digest of the tool list, a credential the pack states is read-only (`00:403`, `00:407`), the boot print of every enabled row, and for a binding in `contrib/` a maintainer's reading of the recorded tool list (`CR:374`). A site-private pack has the first three only, and checking them is the operator's work. The model is reached only through `llm-gateway`, whose inner scrub no hook can skip (`00:56`).
- **Invariants.** The harness holds no credential. Every offered tool is declared a read: proven for the kernel's own read tools, asserted by the pack for a `tool-mcp` row. The approval floor, under which reads are free (`00:68`), and the crash restart (`00:45`) rest on that declaration for tracker and forge reads. Every step is a row before it is forwarded (`03:200`).
- **Result.** `delivery` stores the answer in `blob` by digest as plan version 1, emits `delivery.plan_ready` and sends a notice.
- **Why kind `investigate`.** It needs no change to `harnesses` v0: budgets and the builder and checker rows are keyed by pillar and kind (`HR:41`, `HR:113`), a compliance run needs no incident (`00:45`), and the compliance pillar already uses the kind (`05:166`). Whether plan writing gets a kind of its own is part of D6.

### 5.3 Step 3: the engineer reads, edits and approves

Two gates exist, and they are different things.

- **Plan sign-off, a product gate.** `delivery plan show` prints the plan; `delivery plan edit --file` uploads an edited text as a new version with a parent, an author and a new digest. `delivery plan sign` records the subject and the digest under `authz.Check` with `deliveries.sign-plan`, with an audit row. A sign-off authorises nothing to be written on any target. It is not an `approval.Decision`, and it clears on any later version. A patch is recorded against one plan version: hunks from a run are part of the version that carries them, and an uploaded patch names the signed version it was made for. An edit of the text makes a new version with no patch: neither hunks nor an upload are carried over, and a revise run or a new upload supplies the patch for the new version before `propose` accepts it.
- **Write approval, the decision of record.** `delivery propose` is accepted only for a plan version with a current sign-off and a patch recorded for that version, from the author of record (section 4.1). Code then builds the typed envelope `{action: open-pull-request, target, parameters: {repository, base commit, branch, patch digest, plan digest, declared repository facts}}`, in which the plan digest is that of the signed version. `remediation` calls `Plan`; `change-hub` writes the `ChangeRecord` in `planned` and opens `approval.Request` with the digest and the tier of the action (`03:296`, `03:319`). `approval.Decide` counts a decision only from a verified subject that holds `approvals.decide` in the tenant, is not the requester, has not voted and names the digest (`03:442` to `03:447`).
- **Requester.** The requester is the verified subject of the call, set by `change-hub` and never a field that `delivery` or another consumer fills (`03:319`). In the form that changes nothing, the engineer who proposes is that subject and a second platform user approves, as in the incident flow. The alternatives are D3.
- **What the approver sees.** The plan, the blast radius that `Plan` reported and the diff that the digest names (section 4.2).
- **Order.** With hunks from a run the patch exists before the sign-off. The order of the requirement still holds: nothing is written before the write approval, and that approval names the patch recorded for the signed version.
- **Invariants.** The approval floor, the quorum of the tier and the monotonic gates `approval/gates` and `change/pre-dispatch` (`00:68`). A gate listener sees the plan digest, the action class, scrubbed target references and the requester, and no parameter (`03:287`).

### 5.4 Step 4: execute

- **The patch is an input, named by digest.** It has one of three recorded origins: a file a person uploaded, made with any tool outside the platform, with its declared origin; from form 3, line-level hunks of a read-only run's answer, for a small change; or, in the last form, a sealed workspace. The write path and the checks of `Plan` are the same for all three and do not depend on who or what wrote the patch.
- **The hand-off to an agent outside.** In forms 2 and 3 the code is written outside the platform. `delivery plan show --bundle` writes one file with the signed plan, the mapping row and the notes, as the input of the engineer's own agent; the kernel has no MCP surface for a client's agent (`03:586`), so a file is the hand-off. The upload that comes back names the signed version and declares its tool and model endpoint (section 4.1). This is the main path of forms 2 and 3 and not a side path: the outside agent plans again from the file, and nothing in the platform sees how it worked.
- **Dispatch.** `change-hub` re-checks the quorum and the bindings, re-plans, compares the digest, runs `change/pre-dispatch` and only then signs the `ChangeToken`; a changed digest or a lost quorum returns the record to `pending_approval` with no token (`03:298`, `03:449`).
- **Apply.** The `remediation` guard refuses `Apply` without a valid token or with a changed digest (`00:70`). The executor takes the forge lease from `credentials.Write(token)`, pushes the branch and opens the pull request. No change becomes `applied` without a receipt, and a missed deadline marks it `uncertain`, never `applied` (`03:474`, `03:300`).
- **Merge.** A person merges on the forge, under the forge's own login and branch protection; it is the last human gate and is outside the system (`01:131`).
- **Not a repository change.** A deployment by pipeline trigger, on a host or in a console has no path in forms 0 to 5 (section 5.7; D17).

### 5.5 Step 5: verify with the customer, and loop

- `verify-readback` calls the executor's `Verify`; `verify-pull-request` reports head, checks, merge and sync. `change-hub` records one verdict from the closed list (`05:611` to `05:614`). Failing checks on a first iteration are normal and are a state for a person, not the verdict `failed` (section 9, row 35).
- The request moves to `customer_review`. The engineer records `delivery accept` or `delivery rework --note`, each under `authz.Check` and audited.
- **Rework.** The note becomes part of the untrusted block of the next first message. A new plan version, a new sign-off, a new patch digest, a new approval, a new token and a new `ChangeRecord` follow; the link between the records of one request is the `iteration` rows of `delivery`.
- **On accept.** Code writes one `note` row from fields it derives (request id, repository, environment, plan digest, change reference) and copies no text of the request, the plan or a tool result. Memory is written by code or by a person, never by a model (section 6.3).

### 5.6 Plan revision

| Revision | What happens | Effect on gates |
|---|---|---|
| The engineer edits the text | A new `plan_version` with parent, author and digest, and no patch | The sign-off clears; `propose` waits for a patch recorded for the new version |
| The engineer asks the agent to revise | A follow-up run that carries the neutral history, or the harness's own blob where it declares `opaque-history` (`07:1197`, `HR:74`) | The sign-off clears; new hunks, if any, belong to the new version |
| A patch is uploaded for a signed version | A patch row with the version, the uploader, the declared origin and the digest | The sign-off stays; the write approval is still to come |
| The plan or the patch changes after the write approval | The envelope digest changes | The record returns to `pending_approval`; a new decision is needed (`03:298`, `06:223`) |
| The customer asks for a change after delivery | A new iteration (section 5.5) | Every gate runs again |

### 5.7 The two outcomes and their tiers

The tier of a catalogue action is fixed in its entry, and the tier table can only be raised per tenant (`00:72`, `00:68`). L0 to L2 need one approver who is not the requester and L3 two (`03:448`). The tiers below are proposals for the ADR of section 11, row B.

| Outcome | What the platform writes | Proposed tier | Why | Last human gate |
|---|---|---|---|---|
| A pull request | One branch and one pull request in one repository | L1, the tier a rollout restart has today (`03:319`), only where the mapping row says a pushed branch runs no pipeline with secrets. Where one runs, a second catalogue action at L2 is proposed, because a tier is fixed per entry (`00:72`) | Where no pipeline runs on the push, nothing changes on a running system until a person merges, and the rollback is to close and delete. Where one runs, the push itself executes content of the patch with the pipeline's secrets | The merge on the forge (`01:131`); where a pipeline runs on the push, `approval.Decide` is the last gate before execution |
| A deployment through GitOps | Nothing more: the merge is the deployment and the controller's sync is the receipt (`05:736`) | The tier of the pull request | The platform's write is the same | The merge on the forge |
| A deployment by a typed Kubernetes action | One of the five catalogue actions (`00:72`). Their offers are derived from alert labels today (`00:72`, `03:296`), so a request outside an incident is possible only if section 9, row 14 holds | The fixed tier of that action | The tier is fixed in the catalogue entry | `approval.Decide` |
| A deployment by pipeline trigger, on a host or in a console | Not in this design, in any form. It is the class of the deferred host executor (`00:617`); whether this requirement fires that trigger is D17 | To be set by its own ADR; L2 outside production and L3 for production are proposed, as two catalogue actions | A gate listener cannot see the environment (`03:287`), so a rule by environment is a separate action today | `approval.Decide`, two approvers at L3 |

Opening a pull request can start the customer's pipeline on content a model wrote, with the pipeline's secrets. The path deny list does not bound that: a pipeline runs files outside its own definition, such as build scripts, test code, container build files, package scripts and included templates. The pipeline posture is therefore a precondition of the action and not the customer's homework: a person records per repository whether a pushed, unmerged branch runs a pipeline with secrets, `Plan` refuses while the field is unset, and the value selects the catalogue action and so the tier. A forge rule that holds pipelines until a person approves was read for one product's own agent only (section 12.2). For a branch pushed into the same repository by a token with write access it is unverified on every forge, as is a token scope that excludes pipeline definitions, which the lease should use where a forge has one (section 12.4).

## 6. Customers, tenancy and where the memory lives

### 6.1 A customer is a tenant

This is the recommended model, not a recorded decision (D2).

- One tenant id is already the `tenant_id` column, the secret scope, the blob prefix and the key of every per-tenant record (`00:326`). Row-level security is forced on every tenant table (`00:335`), secrets are scoped (tenant, plugin, name) under one key per tenant (`00:377`), the audit chain is per tenant (`00:73`), and the model budget is a row of a tenant table (`00:353`, `00:335`). The first release still has one upstream key and one daily budget for the install; a key per tenant is a hosted P2 item (`00:56`).
- An engineer who serves three customers is three `tenant_binding` rows for one platform user, and `authz.Check(subject, tenant, permission)` decides per customer (`00:339`, `00:224`).
- Intake names the customer by credential, never by message: the binding of the caller on the API, the channel binding on chat (`00:327`, `06:289`).
- Off-boarding a customer is the tenant delete saga, which purges every namespace of every plugin from the `durable` registry, `delivery` included (`00:433`).
- The cost is measured for hundreds of tenant trees (`ADR-036:79`); a handful of customers is far inside it.

**What stands in the way.** The first community release runs the one tenant `default`, and nobody can create a second tenant through an API before S4b (`08:546`, `08:720`, `08:808`). Whether a self-host may create a second tenant at all is the open tenant case of ADR-049, due before S4b (`08:1183`), and the proposed edition principle puts "operating for many organisations" on the enterprise side (`08:963`). A project level between tenant and entity is not proposed: it would rebuild every fence above inside one plugin.

**The rule: one customer per tenant, in every form.** Before S4b that means one install per customer. Several customers in the tenant `default` is not a form of this design. There the customer would be chosen by payload fields of a mapping rule, against the rule on intake above and `00:327`; every holder of `approvals.decide` in `default` could approve a write to any customer's repository; and one secret scope would hold every customer's forge lease and read credentials, so a request of one customer that steers the agent could read another customer's repository and place it in its own pull request. The guarded write (S9a) and tenant create (S4b) are on two tracks that do not wait for each other (`08:803`), so nothing in the order of work prevents that state; the rule does. The mapping has no customer column and `delivery` has no customer selector. Code cannot tell that two repositories under one tenant belong to two customers, so the rule is also an operating rule that the bundle's documentation states.

**What the rule costs.** With one install per customer an engineer who serves three customers works in three installs: three CLI contexts, three logins, three places to look for a plan that waits. If ADR-049 puts tenant create on the enterprise side, that is the community answer for good (D2).

**One engineer, several customers.** Under D3 option 1 the proposer cannot approve, so every customer tenant needs at least two platform users who hold `approvals.decide` (`03:444`, `03:445`), and the second one decides on every iteration, because each rework is a new approval (section 5.5). The requirement has one engineer read, edit and approve. No list spans customers: `delivery status` answers for one tenant, so an engineer's waiting plans and reviews across two or three customers are a CLI loop over their bindings, or over the installs before S4b. A queue of the decisions waiting on people is a deferred item and is per tenant (`00:612`); a list across tenants is designed nowhere. How a call selects its tenant is D16.

### 6.2 The mapping, the configured part of the "brain"

Versioned per-tenant rows in the schema `delivery`, edited through the API and `aiopsctl delivery map`, as the tenant maps of `signal_core` are (`05:425`). A row maps a rule (source, project key, labels) to a subject (an entity reference in the grammar of `00:672`), a repository with its forge and base branch, an environment (cluster and namespace references), the convention files to read first, and two facts a person declares for the repository (whether the base branch requires another person's review, and whether a pushed branch runs a pipeline with secrets; section 5.7). It holds nothing about where a customer's tasks and time logs live, because nothing in forms 0 to 5 would read it (D10). The estate cannot hold this: it is a projection that is never edited through the API or chat, and its first-slice classes hold no repository (`00:58`, `09:203` to `09:207`).

### 6.3 Where memory lives, and where it does not

| Kind of memory | Home | Written by |
|---|---|---|
| Conventions that belong to the code | Files in the customer's repository, read through the read tools as untrusted content, never as instructions (section 4.1) | The customer's and the company's engineers, by pull request |
| The mapping of section 6.2 | Rows of `delivery`, versioned | A person |
| Notes from accepted deliveries | Rows of `delivery`, bounded into the trusted block of the first message | Code at acceptance, from fields it derives; free text only by a platform user |
| Persona and operating rules | Bundle content, site scope. Neither a patch layer nor a tenant overlay can address content (`07:1327`, `00:465`), so a changed prompt is one of the mechanisms of section 6.4, and a per-customer variant is a row or a tenant-writable config field | Engineers, by the mechanisms of section 6.4 |
| The transcript of each run | `agent_runs.run_step` (`00:346`) | `agent-runs` |

Memory does not live in the harness, which may keep no tenant data after a run (`HR:62`), and it is not written by a model: write tools are never offered to a harness or chat (`07:789`), and the recall the platform designs elsewhere is computed by code or promoted by a person (`09:620`). "Written by code" is not enough by itself: code that copies request or tool text into a note replays it into every later run, so a note written by code holds derived fields only. It does not live in this repository either: customer text and customer references never enter it (`08:1348`). The neutral bundle is first-party; per-customer rows, notes and prompts are site data, site-layer patches, or packs under the company's own publisher id (`08:1368`).

Run transcripts, plan text and notes are plaintext rows; only secrets are encrypted (`00:377`). The erasure bound is the tenant delete, which is one more reason for section 6.1.

| A verifier | `verifiers` has no remote form (`00:227`): in-process Go in a distribution | Yes | 3 |
| Stricter approval for one customer | The tier table raised per tenant; a gate listener that raises or denies (`00:68`, `03:287`) | None | 3; listeners P2 |

No tuning reaches the floor: an added plugin or a changed prompt cannot grant an approval, lower a tier, read a write credential or skip the scrub (`00:259`). `delivery` provides no key, so a third plugin cannot replace a part of it: a developer's own plan checker, verifier or plan schema is a distribution, never an installed artifact.

## 7. Harnesses, trackers and chat products as optional plugins

The rule is principle 9: every upstream enters through one provider or contribution behind a definition whose fake and suite name no upstream, and lives in its own bundle or pack (`00:32`). `aiops-delivery` wraps no upstream, and that has no precedent. Every optional bundle listed today wraps one (`00:521`, `08:281`), `aiops-dashboard-app` included: its rows need `aiops-app`, a plugin loaded by an upstream server and rated `optional-plugin-only` (`00:290`, `LR:108`). The home rule W8 covers only a first-party plugin that wraps an optional upstream (`00:112`). An optional first-party bundle with no upstream is a new category, and the owner decides whether the rule is widened (D15).

**Coding harnesses.**

- A wrapped harness is its own optional plugin in its own optional bundle, under the home rule W8 (`00:112`); its process is the role id `harness-sidecar`, which the operator installs (`HR:181`). It is selected for the delivery pillar alone through the group's `harness` field, and `harness-native` stays the default everywhere (`HR:102`, `00:111`).
- As a harness it runs with its own shell and file tools off, proven by its rendered profile, as the round-5 design already states for an agent behind the Agent Client Protocol (`docs/design/harness-r5/agent-harness.md:376`). It reaches the model through the gateway's HTTP surface with a lease-bound key (`03:520`). Both statements were checked on 2026-11-27 against the three candidate harnesses of section 16.2. Removing a harness's own shell, file and web tools is documented for one of the three. Two of the three cannot use a chat-completions surface at all, so reaching the gateway depends on which wire formats ADR-012 gives it (D19). In form 5 the rule on tools is reversed: the harness works with its own shell and file tools on the checkout, which no departure of the closed list covers (D6, D18).
- A harness that calls a vendor-hosted model itself is not admitted in the community edition (`HR:83`). This is the largest edition finding for the requirement, because that is how such agents are commonly used with a vendor login (D7). None of the three harnesses of section 16.2 needs a vendor login: each starts with an API key and a configured base URL, so D7 option (a) does not keep them out if the gateway serves their formats.
- Verdicts already recorded: goose, opencode and the Agent Client Protocol are `ok` at licence-file level with the vendors' service terms UNVERIFIED (`LR:88`); Codex CLI is `ok-with-conditions` (`LR:89`); the Claude Agent SDK is `optional-plugin-only`, never shipped by the project and never in the community index (`LR:90`); OpenHands is `unverified` and stays out until its runtime repository is read (`LR:92`). The register holds no entry for a harness that may be wrapped: its one entry from this area, `langgraph-platform`, is rated `replace-or-rebuild`. An entry enters with the commit that first uses, wraps or names its upstream (`ADR-054:600`), and an `unverified` entry is read before the step that first uses it (`08:1347`). Read again on 2026-11-27 (section 16.2): the Codex CLI verdict is confirmed by a reading of the licence files at a tag, and its Linux package holds more bundled parts than `LR:89` lists; `LR:90` is confirmed for the SDK, and the CLI it wraps has no row of its own; a third candidate, dsh as a wrapped harness, is rated `optional-plugin-only` (`LR:42`). Section 16.7 lists the entries and readings owed.
- The lowest-risk first adapter is a protocol adapter for the Agent Client Protocol that drives an agent the user installs. Its id stays generic until a register entry allows a name (`08:1370`). The owner's input of 2026-11-27 names three harnesses to wrap first (section 16). All three document a headless mode with a JSON event stream, which is the simpler adapter for a process inside a per-run sandbox; one of them also documents a profile for the Agent Client Protocol.

**Trackers.**

- Reads: rows of `tool-mcp` in a pack with no code, one pack per system, where the system offers a Streamable HTTP MCP server with read tools (`00:113`); otherwise a remote read tool, which the S8b exit proves in Python (`08:630`).
- A tracker is not a named external system today, and nothing defers one: the decisions hold no tracker row, no `ext-` id for one and no trigger row for one (`01:335`, `01:364`). Naming one needs, in order, an `ext-` id, a new trigger row and a numbered ADR (`01:396`), and a reading of its terms and mark policy at a primary source before any id carries its name (`08:1370`).
- A notice can be posted to a tracker through `notifier-webhook` (`01:335`). A state change, a new task or a time log has no seam (section 3, row 25; D10).

**Chat products.**

- The one designed surface is the optional bundle for Slack, operator-enabled and in no shipped profile (`00:117`); its platform terms are rated `optional-plugin-only`, and a lawyer's question on commercial distribution and on the server-side transcript is open (`LR:123`, `LR:202`).
- A second chat product is a `chatSurfaces` contribution in in-process Go, because the definition has no remote adapter (`06:135`). A first-party one waits for the trigger "first customer request" (`00:602`). The licence record rates two candidates: one needs the vendor's written approval for its name, the other has store, bot and brand terms UNVERIFIED (`LR:129`).
- The designed surface refuses people outside the installing organisation: an externally shared channel is dropped unless bound, and an external member is never linked (`06:289`, `06:332`). A customer-facing thread is therefore captured by an engineer, with the text in the command, and not read from the thread by the platform. Customer chat intake stays a manual copy in every form (section 10).

## 8. The chosen design and the three proposals

Three proposals were worked through for this record.

- **Proposal A, least new surface.** No new definition, key, hook, kind or departure. The agent stays a read-only run whose answer is a plan and a change set of whole files; the only write is one catalogue action in the planned pull-request executor. New: one plugin, one command row, one group row.
- **Proposal B, a vertical of its own.** Four new definitions (request sources, the delivery record, runners, workspaces) with two dispatchers of their own. It shares only infrastructure and the policy spine, so the incident-shaped contracts of S5 to S8a could be accepted as written.
- **Proposal C, earliest value.** Fix four data formats now (request, mapping, plan, write envelope) and replace the parts one at a time: a hand-run kit outside the kernel today, a site-composed pillar on the first release, the bundle after it, the guarded write at S9a, the in-platform run last.

**The chosen design** is proposal A's surface, built in proposal C's order, with five parts of proposal B.

| Taken from | What | Why |
|---|---|---|
| A | No new definition for the first three forms; the plan run as kind `investigate` of its own pillar; the write as one catalogue action, in a row of its own in the optional bundle | It needs no change to `harnesses`, `signals` or the binding maps, and the no-scaffolding rule holds (`08:680`) |
| A | A change as an optional part of the answer, narrowed to line-level hunks from form 3 | It serves a small change with no workspace. Whole files are not taken, because the model sees capped and scrubbed reads (section 4.2) |
| C | The split of patch, envelope and write: a model or a person writes the patch, code builds the envelope, the platform guards the write | It makes the three origins of a patch one write path, and it needs one sentence of `00:72` and not a rewrite. It still weakens the row for this action class (D5) |
| C | The order: earliest form first, the guarded write next, the in-platform run last | The in-platform run has the most open decisions, and nothing earlier depends on it |
| C | The upload of a patch made outside the platform | Engineers keep the agent they use today while the platform guards the write. It is the main path of forms 2 and 3, which makes those forms a desk around an outside agent and not yet the wanted flow (section 2) |
| B | The record with plan versions, the sign-off as a product gate, acceptance as a state and not a verdict | Proposal A overloads the verdict `uncertain` for "ask the customer", which distorts the measure behind the paid verification turn (`00:642`) |
| B | `verify-pull-request` | Without it every delivery change ends `uncertain` with reason `no_data` (`05:614`) |
| B | `requestSources`, written when the first source beyond the API is built | The requirement names six sources; the transport of `signal-core` fits and its consumer does not |
| B | `workspaces`, with the patch cut outside the sandbox and not reported by the run | It is needed whichever registry the run lives in. Its shape is undecided (section 4.3) |
| B | Memory written by code or by a person only | It keeps the read seam closed (`07:789`) |

**Not taken.**

- From A: every delivery change ending `uncertain` on purpose; a pseudo service key for work that has no service; a change set of whole files.
- From B: a second agent registry (`runners`) and a second run dispatcher. A contributor would write two adapters against two suites for one agent, and improvements to `agent-runs` would not reach it. It is kept as the fallback of D6 if `harnesses` is frozen read-only for good. Also not taken: a service subject as the requester by default, which is the deferred sole-approver rule by a side door (`00:617`).
- From C: a command plugin for the hand-run kit, and a write envelope with digests kept by hand. A convention on plain files gives the value with no code, and a digest in a Git repository would read like an approval without being one (D8).

A second member of the same class is OpenClaw, MIT (<https://github.com/openclaw/openclaw>): "The Gateway is the local control plane for sessions, tools, events, and channel connections", and tools run on the host for the main session unless sandboxing is configured. **Comparison.** The class is a single-operator personal agent. Its trust model is one home directory, one memory and approvals in the chat.

| | The personal-agent class | This design |
|---|---|---|
| Channel gateway | One process, an adapter per platform, a session per chat | The `chat` dispatcher with one `chatSurfaces` row per product (`06:29`), and far fewer products, each in-process Go under a licence review (`06:135`) |
| Who is the customer | Not modelled; a profile or a separate gateway | The tenant, resolved from an installation record or a binding, never from the message (`00:327`) |
| Memory | Written by the model, small, one per profile, unreviewed by default | Rows written by code or a person, per tenant behind row-level security, purged with the tenant (section 6.3) |
| Approval | Per shell command, by any chat member by default, with a model-judged mode and a bypass | Per typed change, by a verified platform user who is not the requester, bound to a digest (`03:442` to `03:447`) |
| Evidence | Local logs | A per-tenant audit chain, exportable (`00:73`) |

What is worth taking is the pattern of a gateway with adapters and a default-deny allow-list, which the `chat` dispatcher already has. What is deliberately not taken is model-written memory and approval in the chat by whoever is present. A chat surface may carry a decision to `approval.Decide`; it may not be the approval.

**What this means for the design.**

- No product read here maps an inbound request to a customer and then to a repository, an environment and conventions. The mapping of section 6.2 has no upstream to wrap.
- No product read here binds an approval to what executes. Plans are approved as prose, on a timer, or not at all, and the review is of the pull request. The digest binding is the platform's own (`00:72`).
- The controls worth copying are already rules here: the requester cannot approve (`03:445`), the agent holds no standing credential and pushes one branch (`00:69`), a person merges (`01:131`). One is not: holding the customer's pipeline until a person approves was read as a property of one product's own agent, and is unverified as a forge setting for a branch that any other token pushes (section 12.4). The design does not rely on it (section 5.7).
- Every product ends at the pull request. Verification with the customer, the rework loop and time logging exist in none of them.
- An adapter for the Agent Client Protocol must map a permission request to a refusal or to an end of the run, never to the agent's own remembered "always allow".

### 16.1 The answer

**Feasible as a design. Not admitted by the accepted lines as written, and on no dated step.** Each of the three harnesses documents what a wrapper needs: a headless mode, a machine-readable event stream, a start with an API key and no vendor login, and a configurable model endpoint. The sandbox service documents what requirement 1 of section 4.3 needs. Requirements 2 and 3 are work of the provider that the service does not prevent. Requirement 4 is a setting the service documents; that the self-hosted build enforces it is not established (section 16.3). Most of what stands in the way is in this repository: the read-only harness contract and its network rule, the wire format of the gateway, what its listener serves and who can reach it, the scrub on source code and two licence verdicts. One obstacle is in the service: it always blocks traffic from a sandbox to private addresses, which is where a gateway on the operator's network sits.

**What the input supplies.** A sandbox per run was the part that nothing designed could start (section 9, row 33). A service the operator runs or buys fills it, as a candidate for the provider of ADR D. Three candidates for ADR F replace "any coding harness", so the open point of section 12.4 on base URLs could be read at the source. The input answers none of D6, D7, D13 and D15.

### 16.2 The three harnesses as wrapped harnesses

**The shape all three share.** A first-party in-process plugin that links nothing of the upstream drives another process. None of the three has a Go library, and each documents a headless mode whose event stream a wrapper maps to step rows. A remote plugin cannot host them: a remote unit gets no mount, no environment variable and no route out (ADR-063, decisions 24 and 25, proposed), and loopback shims wait for their trigger (`00:632`). As the plan harness of forms 2 to 4 this is the third topology of `HR:89` to `HR:91`: `sidecars` starts the process, and the fence is a network the plugin renders. Form 5 is not that topology. The process runs inside the sandbox of the run, the `workspaces` provider starts it (section 16.4), the wrapper drives it through a stream of that provider, and the fence is the rule of the sandbox service. That is a fourth topology, which the harness record does not have. It also moves the dial into a plugin the wrapper depends on, which is what the rule of `HR:58` and the network sentence of `00:45` exist to refuse, so ADR D edits those lines and says what bounds the new path (section 16.5). Plan and execution are two runs in two sandboxes: the sign-off is a product gate outside any harness (section 5.3), one sandbox per run keeps no session file, and the input of the second run is the signed plan. No plan mode and no approval prompt of a harness is a gate of the platform.

### 16.4 The shape of a `workspaces` provider that wraps the service

The definition stays as section 4.3 leaves it: undecided, with a fake and a suite that name no upstream (principle 9, `00:32`). The shape below is the one proposed to ADR D. It keeps the code that security rests on in one first-party plugin and puts a sandbox service behind it as one contribution.

- **Two plugins.** The provider bound to `workspaces` is in-process Go, first-party, and wraps no upstream. It owns the clone, the unpack of a hostile tree, the diff, the egress probe, the orphan sweep and the audit rows, holds the repository read credential, and injects `dialer`, `secrets`, `blob` and `jobs`. Behind it is a registry of sandbox-service rows. A row is in-process Go, first-party, in an optional bundle of its own under the home rule W8, since it wraps an optional upstream (`00:112`), and its id is generic until a register entry allows a name (`08:1370`). It does five things only: create a sandbox with given network settings, upload, start one command, download, and kill. It is a plain HTTP client of the service's published API description, pinned at a commit: the service publishes client libraries for two other languages and none for Go, so no module of the upstream enters the build, and a change of the API is adapter drift that the row owns. With the working shape of section 4.3 the clone, the unpack and the diff would instead be rewritten, and their T3 test with them, for every service.
- **No Git process.** D18 option (a) says that the kernel starts no shell, so the clone, the unpack and the diff start no process in the kernel's context. The tree at the base commit comes from the forge's archive API or from a linked Git library with a register entry, which is the choice ADR B makes for the write (section 11). The diff is computed between the uploaded tree and the downloaded one, by the provider's own code or by that library, in the one accepted patch format. If ADR D chose a Git process, it would run outside the kernel with external diff, text conversion and hooks off, and D18 would have to say so.
- **The network rule of a harness.** A harness reaches the network only through a `sidecars` endpoint of its own row (`00:45`), and a `harnesses` contributor may not inject `dialer` (`HR:58`). In form 5 the wrapper drives a process on another machine through a stream of `workspaces`, so the dial has moved into a plugin the wrapper depends on. That is a way around the rule, and ADR D asks for it as an edit of `00:45`, `HR:58` and the topology table (`HR:89` to `HR:91`). A possible bound for ADR D to state: `workspaces` is consumer-bound to the dispatcher of the run and never to a `harnesses` contributor; the wrapper gets the stream of one command and no other operation; the start operation runs one command line that the dispatcher renders from the wrapper's declared profile, in the sandbox of that run, and takes no network setting; and `plugin check` refuses a `harnesses` contributor that names `workspaces` or `dialer` in its `uses`.
- **The operation the working shape lacks.** `Open`, `Seal` and `Wipe` start nothing inside the sandbox. A run needs one more operation: start one command in the workspace, with a deadline, and stream its output as untrusted text. ADR D adds it to `workspaces` or names another seam.
- **Everything emitted from inside is transcript.** The tests of the repository run in the same micro virtual machine as the harness. They can write to its output, replace its binary and forge the event stream, the final answer, the test results, the token counts, the exit status and the log. In form 5 all of these are attacker-writable. They are stored as transcript and shown as untrusted on every approval surface. None is an input to `verifiers`, to a cap or to the tool-profile check: caps are enforced at the gateway and by the life of the sandbox, never from the stream (`00:45`), and the profile check is made from outside, by the provider, from the digest of the profile it uploaded and the command line it started. A statement that the tests passed is a claim of the run. The checks that count are the diff a person reads, the pipeline of the pull request and the review on the forge.
- **The template.** A sandbox starts from an image that the operator builds, because no template, image or bundle of the project may contain a harness that is rated `optional-plugin-only` or published with all rights reserved (`LR:42`, `LR:90`, `08:1356`). The template is the one thing every later run reuses, so it is an exception to requirement 1 that ADR D rules on. The rule proposed: a template holds harness binaries and toolchains only, and is never built from the content of a customer's repository. A template that carries a repository's dependencies is built by running that repository's manifests and install scripts, outside any per-run sandbox and usually with the network open, and every later run of every tenant then starts from the result.
- **Dependencies.** With egress denied, a repository whose tests download dependencies fails. A mirror on the allow-list is a second destination and an exception to requirement 4, and a pull-through mirror forwards names that hostile code chooses to public registries. The options for ADR D are an offline mirror with no upstream, one per tenant, or a fetch step in a sandbox of its own that holds no credential and whose output is uploaded into the sandbox of the run. Neither is designed here, and the fetch step still has to show that the tree does not leave through it. The T3 test covers the template and the dependency path.
- **One instance per tenant, and the tenant delete.** The API key of the service can read files, run commands and replace network rules in every sandbox of its account, and the self-hosted runtime has no account and an unauthenticated control port (section 16.3). Principle 6 says what follows: such an upstream "runs one instance per tenant in a multi-tenant profile; its plugin manifest says so, and no default bundle carries such a process" (`00:29`). The sandbox-service row declares that in its manifest; for the hosted service the least is an account and a key per tenant, and whether that meets principle 6 is for ADR D. Until an install has it, form 5 is one install per customer. The row also declares an `external` durable namespace (`00:433`): the tenant delete kills every sandbox of the tenant and removes its instance, and what a hosted service keeps after a kill, seven days of logs and storage with no stated deletion time, is a step the provider cannot perform, so the saga waits or an operator records the manual step.

**The allowed destination is not the internal listener as it stands.** The internal listener of `kernel-api` serves `/v1/admin`, and `/v1/llm` and `/v1/tools` where an external harness plugin is enabled (`00:133`); the two are served side by side so that the fence of a harness process allows one egress target (`03:569`). An allow by address of that listener gives the code in the sandbox a network path to the admin routes and, with the key it can read, to the tenant's read tools where the facade is on. The run therefore needs a listener or a port that serves the model route to workspace runs and nothing else, or a proxy the provider renders that passes that one path. Both are edits of accepted lines, asked as D20. The guard on the kernel's own outbound dial (`00:448`) says nothing about a connection that comes in from a sandbox host.

**One run, in order.**

1. `Open`: the provider fetches the tree at the base commit with the read credential, outside, and builds the upload archive.
2. It creates the sandbox with egress denied except for the one address of the model route, inbound access private, kill on timeout and the run id as metadata. It reads the settings back and then runs the probe of requirement 4 from inside. It stops if the settings differ or if any probe connection succeeds. Where the model route is on a private address, the node exemption of section 16.3 is a precondition that the operator set and the provider cannot read.
3. It uploads the tree, the signed plan with the mapping row and the notes, and the rendered profile of the harness, and records the digest of the profile.
4. It starts the harness as one background command with a deadline and streams the output; the wrapper writes each event as a step row before it is forwarded (`03:200`), as untrusted transcript.
5. The gateway accepts the key only while `agent-runs` holds the run lease. The ceilings on model requests and tokens are enforced there and the deadline by the life of the sandbox; nothing outside counts the calls of the harness's own tools (section 16.5). A cancel kills the sandbox.
6. `Seal`: the provider downloads the tree, unpacks it as hostile input, cuts the diff outside and stores the patch and the log by digest.
7. `Wipe`: it kills the sandbox and confirms that it is gone, on every error path as well.
8. A scheduled job kills any sandbox whose run has ended.
9. The sealed patch then passes the same `Plan` and `Apply` as an uploaded one (section 5.4).

**The author of record of a sealed patch.** Rule 5 of section 4.1 names the uploader of a patch or, for hunks from a run, the subject who signed the plan version. A sealed patch is neither, so the rule "not the requester" has no subject in form 5 until one is named. Proposed for ADR D: as for hunks from a run, the author of record is the subject who signed the plan version that the run executed. That subject is the requester of the change and cannot approve it, as under the answer to D3. The origin of a sealed patch is recorded by code and not declared by a person: the harness with its version, and the model route of the run. Rule 6 then checks that origin against the tenant's consent record as it checks an upload's.

No effect leaves the sandbox before `Seal`, so a crash costs a run and writes nothing. Whether such a run restarts by itself is still the crash rule that ADR D decides (section 9, row 28).

**The scrub and a harness that edits.** This is an inference from the shape of the edit tools, not a statement of any vendor. A harness in the sandbox reads raw files and sends them in its model requests. The gateway replaces values with pseudonyms, the model answers with an edit as exact strings or as a whole file, and the harness applies it to the raw file. An edit built from a pseudonymised view either fails to match or writes the pseudonym into the file. The hunk check of section 4.2 does not reach this, because the write happens inside the sandbox before any `Plan`. Whether any of the three harnesses keeps working when a gateway rewrites request bodies between turns was not tested.
