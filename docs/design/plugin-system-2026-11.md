## 1. The owner's direction and the principle change
The founding requirement is to rebuild on the architecture of dsh: everything is a plugin, pluggable, and testable alone before it is attached. Round 1 followed dsh for composition and departed from it in three places to protect dates. The owner has withdrawn the date argument twice. All three departures are reversed in the kernel and in every profile; where a multi-tenant, multi-replica server forces an adaptation it is a row of section 15 with its reason, and no adaptation is argued from schedule.

| Round 1 (00 as it stands) | This record |
|---|---|
| Principle 3, "extension points are earned": 12 points, about 22 kernel rows with no definition, several "packages, not points" | **Principle 3, "a seam exists when a consumer does".** Every service that another plugin calls, the launch services included, has a definition with three roles that must all exist (definition, provider, consumer), a fake and a conformance suite that the fake passes. The fake is the second implementation from the first day, with one stated exception: the `sql` fake is the same engine in a throwaway schema, because the contract is a PostgreSQL dialect. A plugin that nobody calls has no definition |
| Plugins compiled in through an `init()` map; third parties, the plugin manager, the gate and the builder in P3 | An explicit module table generated by the distribution builder; the builder, the remote runtime, the gate, signing and install proven at S2a and S2b on toy registries, before any product feature |
| Fixed dependency order at boot; layers change on restart; `ctx.isolate` not ported | Service-availability-driven fibers with epochs; no boot order; live recomposition through one queue, in place in every profile; `Isolate` and `Intercept` carried |
| Principle 5, "policy that must not be bypassed is a host invariant", enforced by kernel point guards | **Principle 5, "policy is an invariant of the plugin that owns the seam".** The kernel makes that plugin impossible to shadow and its privileged keys impossible to inject without a binding; a consumer cannot exist without it (section 7). The kernel holds no policy |
| Principle 2: a fake host (`sdk/plugintest`) | **Principle 2:** the kernel ships in the SDK, so a Go plugin is tested on the real runtime with fakes of the services around it; a non-Go plugin is driven by the same kernel inside `aiopsctl`. No fake host exists |

Unchanged: profiles and bundles (principle 1), the ingest path independent of the kernel (4), shared fate as a budget (6), unmodified upstream behind a service boundary (7), logged state changes and named triggers (8); the Grafana observability stack first, Slack chat-ops, the on-call module, hosted multi-tenant plus self-host, Apache-2.0.

## 3. The kernel
**Contains** (`sdk/kernel`; the line budget is fixed at the S0 exit from the measured port and enforced in CI from then on; source inspection records Cordis at 2,811 lines, but no retained Go implementation measurement is accepted in this baseline):

| Part | Cordis source | Content |
|---|---|---|
| Context tree | `context.ts` | Immutable nodes; `Extend`, `Isolate` (with labels), `Intercept` (by service name, ancestors first) |
| Service store | `reflect.ts`, `service.ts` | Typed keys with a major; one provider per name per realm; `Provide` with a per-consumer availability check, `ProvideFor`, resolve; an index by key and realm for notification (Cordis scans every fiber) |
| Fibers | `fiber.ts` | Six states, epochs, one transition at a time, providers retained until dependants unload, `Update`, `Await`, effects |
| Hooks | `events.ts` | `Event`, `Waterfall`; the built-in `internal/plugin`, `internal/status`, `internal/service`, `internal/config`, `internal/update`, `internal/commit` |
| Registry and logger | `registry.ts`, `logger.ts` | Plugin records, the fiber index, a `log/slog` front with fiber attributes |

**Added to Cordis, each with a row in section 15:** three deadlines (load, drain, dispose); `Enter` leases and the quiesce step; tracked goroutines (`Go`); `Batch` and `Settle`; key classes checked against two binding maps; hook ownership, declared stages and an explicit audience; typed scope values written only by the fiber that provides the scope's owning key. **Moved out after review, because Cordis does not hold them either:** health probes (the `health` registry), `Gate` (`sdk/gate`), schema derivation and `Volatile[T]` (`sdk/plugin`; the loader commits volatile values, as `entry.ts:180` does), the row id (a scope value set by the loader).

The root installs four built-in services as Cordis does: `reflect`, `registry`, `hooks` (Cordis `events`, renamed because `events` is our outbox) and `logger`. The launcher passes the kernel two pieces of data at construction: for each provider-bound key the module-table entries allowed to provide it, and for each consumer-bound key the entries allowed to inject it. An entry is the registered `Plugin` value, never the string a plugin declares about itself; a fiber mounted with `c.Plugin` inherits the entry and the classes of the row that mounted it, so a child spec that names itself `aiops/approval` gains nothing.

**Beside it, not in the tree** (`boot/`, as `dsh-app-boot`): flag parsing; layer composition and dumps; the module table; admission (section 12); the required audit; reading the committed process-scope generation; the `prepare` step that provides the launch services (`sdk/def/launch/v1`) before any row mounts; the mount of the `loader` plugin; fail-loud; signals and bounded shutdown; reading the kill switches (layer 6) into the `killSwitches` launch service.

**Must never contain**, checked in CI and not by review:
1. `sdk/kernel` is its own Go module with no `require` line. `boot/` and `loader/` import `sdk/kernel`, `sdk/def/launch`, `sdk/def/loader` and `sdk/def/composition`, and nothing else from `sdk/def/` or `plugins/`.
2. In `sdk/kernel`, a product word: tenant, role, profile, row, YAML, SQL, HTTP, job, approval, audit, model, health, gate. `boot/` and `loader/` have a closed vocabulary instead: profile, bundle, layer, row, role, scope class (`process`, `tenant`), key class, binding, required set, generation, switch name. Every check they run reads manifest fields and the distribution manifest; they know no key's meaning and import no domain definition.
3. Policy or a policy number: no retry, backoff, rate limit or threshold (the only tunables are the three deadlines); a service name other than the four built-ins; a registry of plugins populated by import.
4. Growth past the line budget, or a new package under `sdk/kernel`, `boot/` or `loader/`, without an ADR.

**Concurrency contract.** Cordis is correct because JavaScript runs to completion. The port replaces that with five rules; the implementation behind them is chosen at S0 (ADR-034).

| Rule | Statement | Status |
|---|---|---|
| G1 | No plugin code runs while kernel state is being changed, and each fiber field has one writer | Design, pending S0 validation. Compare a graph mutex with one reconciler goroutine that owns every fiber field (inbox, deduplicating work queue, `Batch`, `Settle`). The reconciler is the default candidate because it needs no lock, orders deterministically and makes self-dispose from `Apply` an inbox message; the mutex candidate must demonstrate deadlock-free self-disposal |
| G2 | At most one transition per fiber; `Apply` and disposers run on that fiber's goroutine (Cordis `inertia`) | Design, pending S0 validation |
| G3 | The call path takes no lock: bound provisions are an immutable map behind an atomic pointer, listener lists are copy-on-write. Every consumer is a dependant: there is no optional read outside a `When` sub-fiber | Design, pending S0 validation |
| G4 | Unload is quiesce, then dispose: cancel `Std()`, refuse new leases and effects, wait for open leases and tracked goroutines up to the drain deadline, then dispose in strict reverse. No call that holds a lease waits on the reload queue | Design |
| G5 | Observers see one total order of status and service events, delivered off the state owner | Design |

## 4. The context API a plugin author sees
```go
package kernel // module sdk/kernel
type Key[T any] struct{ /* name, major, provider class, consumer class, intercept config type */ }
func NewKey[T any](name string, major int, opts ...KeyOption) Key[T] // declared only in definition packages
func (k Key[T]) Of(c *Context) T // needs a declared Need or a When on k; panics *InjectError otherwise (recovered at the fiber boundary)
func (k Key[T]) Provide(c *Context, v T, o ...ProvideOption) error // an effect; ProvideOption: Available(fn(caller *Context) bool)
// ProvideFor hands each consumer a view bound to the consumer's context (the Cordis traceable proxy rebinding this.ctx):
// the view reads the caller's entry, scope values and intercept chain from the kernel, never from an argument.
func (k Key[T]) ProvideFor(c *Context, view func(caller *Context) T, o ...ProvideOption) error
func Need[T any](k Key[T]) Dep               // required: gates activation and joins the epoch
func NeedWith[T, C any](k Key[T], cfg C) Dep // Need plus per-consumer intercept config (the Cordis inject map form)
func Want[T any](k Key[T]) Dep               // declares a When on k; never gates the plugin itself
func Intercepts[C any](caller *Context, k AnyKey) []C // the merged chain, ancestors first; read inside a ProvideFor view
type Plugin struct{ /* ID, Inject, Provides, Hooks, Decode, Apply: plain data plus two functions, a value in the module table */ }
func (c *Context) Extend() *Context
func (c *Context) Isolate(k AnyKey, label ...Label) *Context         // refused for a provider-bound key, except by its bound provider
func (c *Context) Intercept(k AnyKey, cfg any) *Context              // per-subtree config of one service
func (c *Context) Plugin(p Plugin, cfg any) *Fiber                   // mount a child fiber; an effect of c; inherits c's entry
func (c *Context) When(deps []Dep, body func(*Context) error) *Fiber // Cordis ctx.inject(deps, cb): the only optional form
func (c *Context) Effect(label string, setup func() (Disposer, error)) error // ErrInactiveEffect on an unloading fiber
func (c *Context) Defer(label string, d Disposer)
func (c *Context) Go(label string, run func(context.Context) error) // tracked: cancelled and awaited at unload
func (c *Context) Std() context.Context                             // cancelled when the unload starts
func (c *Context) Enter() (leave func(), ok bool)                   // in-flight lease, taken by dispatchers
type Fiber struct{ /* State, Await, Update, Dispose, Effects */ }
type Scope[V any] struct{ /* From(c) (V, bool) for anyone; With(c, v) only from the fiber providing the owning key */ }
type Audience struct{ /* a predicate over a listener's context, built by the owner of a scope; Unscoped is the zero value */ }
type Event[A any] struct{ /* On; Bind(c) returns the dispatcher, for the fiber that provides the owning key only: Emit, Parallel, Serial, Bail, each takes (ctx, Audience, a) */ }
type Waterfall[A, R any] struct{ /* On(c, stage, fn(ctx, a, next)); Bind(c) returns the dispatcher with Run(ctx, Audience, a); no next vetoes, next twice is an error */ }

package plugin // module sdk, rooted at sdk/ (ADR-060 decision 54): what an author writes
type Spec[C any] struct {
	ID        string              // "<owner>/<name>", equal to the manifest id
	Inject    []kernel.Dep        // data: the composer reads it without running code
	Provides  []kernel.AnyKey     // Provide of an undeclared key fails
	Registers []kernel.AnyKey     // every registry Apply contributes to; the generated cycle test fails on an unlisted one
	Hooks     []kernel.HookUse    // every hook Apply may listen on, with its stage; an undeclared On fails
	Durable   []durable.Namespace // schema and version, key prefix, job kinds, secret scope, sidecar instance, external steps
	Validate  func(cfg *C) error  // pure
	Apply     func(c *kernel.Context, cfg *C) error // the only entry point; everything it registers is an effect
}
func Define[C any](s Spec[C]) kernel.Plugin // JSON Schema 2020-12 from C behind a validator interface; Volatile[T] fields
func FromManifest(m Manifest, apply func(*kernel.Context, Manifest, any) error) kernel.Plugin // declarations as data
```

A definition is a key, an interface and a version. A registration method takes the caller's context first and is implemented as an effect. The worked example is a notifier: the definition, the provider side of `Register`, a process-scope contribution and its test.

```go
package notifiers // sdk/def/notifiers/v1: a registry (plural key), provider-bound to plugins/notifications
var Key = kernel.NewKey[Registry]("notifiers", 1, kernel.ProviderBound())
type Notifier interface {
	Send(ctx context.Context, n Notification) (id string, err error) // ctx carries the tenant handle; n is already scrubbed
	Capabilities() Capabilities
}
type Registry interface {
	Register(c *kernel.Context, name string, n Notifier) error // gone when the caller's fiber unloads
	Notify(ctx context.Context, n Notification) error          // the dispatcher: scrub, pre-send gate, digest, then Send
	Inventory() []Entry                                        // registrations by owning fiber; tests and the manager read it
}
// plugins/notifications/internal: the disposer is recorded on the caller's fiber; tenants.Table is the one shared lookup.
func (r *registry) Register(c *kernel.Context, name string, n Notifier) error {
	return c.Effect("notifier "+name, func() (kernel.Disposer, error) { return r.table.Add(c, name, n) })
}

package webhook // plugins/notifier-webhook: process scope; tenant-toggleable because it only registers a contribution
type Config struct { // URL is tenant-writable: a literal, or ${secret:name} resolved in that tenant's scope
```

|---|---|---|
| `scope: process` (default) | The plugin holds nothing per tenant between calls; per-tenant config comes from `tenants.ConfigFor`, credentials from `secrets` per call | `notifier-webhook`, `notifier-email`, every `tool-*` row, `signal-ingest-*` |

Rules the author must know, stated once: a provided service is called from many goroutines; `Apply` can run again in the same process, so package-level state is a bug; a goroutine starts with `c.Go`; an optional dependency is a `When` body and nothing else; tenant identity is never a string argument (section 10); a process-scope plugin keys every in-memory table, cache and pacing window by the handle's tenant. `plugingen` writes `zz_cycle_test.go` and `zz_tenants_test.go` beside the plugin: it reads `Spec.Inject`, emits the imports of each definition's `fake` package and mounts them, so `kerneltest` imports no definition.

**Manifest.** `plugin.yaml` holds what the launcher, the index and the gate read without running code. Written by hand, in manifest schema 1.0 (amended 2026-11-11): `manifestVersion`, `id`, `version`, `title`, `description`, `license` (SPDX), `publisher` (`id` equal to the owner segment of the plugin id; `name` and `url` may be empty), `source`, `support`, `stability`, `scope` (`process`, `tenant` or both), `runtimes` (an empty list for a pack with no code), `capabilities` (`network`, `secrets`), `integrates`, `instantiable`. `engines.aiops` is removed. Generated, with CI failing on a difference: `uses`, `provides`, `registers`, `hooks`, `configSchema`, `durable`, `requires`. The schema is frozen-additive and has no edition, entitlement, price or verification field; the enterprise edition adds what it needs with a manifest major (community record §4.4). The generator is `plugingen` from the `Spec` in Go (the mdatagen pattern) and `aiops-sdk manifest` in Python, from `plugin.toml` plus the decorators `@contributes(definition)` and `@listens(hook, stage)`. The reload class is not a manifest field: it belongs to the definition (section 9).

## 5. Service-definition catalogue
A singular key is one engine or policy; a plural key is a registry of contributions. Infrastructure comes first, platform starts at `loader`, domain at `notifiers`. **Class** is provider class then consumer class: `P` provider-bound (allowed providers listed in the distribution manifest; no `Isolate`; no `Want`), `C` consumer-bound (allowed injectors listed there), `s` consumer signed (first-party, or an in-process plugin whose signer `trust.yaml` trusts for that key), `-` open; every `.Bound` key is `P`, bound to `tenant-trees`. **Tenant** says how tenant data is reached: `handle` (the process key reads the tenant from the call's handle), `bound` (a `.Bound` view exists in tenant trees and a `scope: tenant` plugin must use it), `ctx` (a tenant-scope plugin uses the process key with `tenants.Bound.Of(c).Ctx()`, the context that carries its tree's handle), blank (no tenant data). **Remote** says whether a third party can contribute from another process (`contrib`), whether a remote plugin may call it (`callback`), or neither (`no`); a contribution adapter ships with its definition, from the phase shown (section 16). Every fake is `sdk/def/<name>/v<N>/fake` unless stated, passes the suite and records its calls.

**Why each provider-bound key is bound.** A bound key is one whose replacement inside a subtree, or by a layer, would remove a fence. Everything else is open: `loader`, `reload`, `pluginManager`, `gateway`, `chatSurfaces` and `signals` were sealed in the first draft and are not (amended 2026-11-11: `harnesses`, which replaces `investigators`, is provider-bound to `agent-runs`, because a second provider would remove the transcript, the read-only tool set and the selection rule), because a second provider of any of them gains nothing it could not do as an ordinary plugin (their privilege is on the consumer side, or they reach egress only through bound keys and plugin-scoped secrets).

Where the allowed set has more than one entry (`kek`, `events`), layers 1 to 4 choose by which row they enable: the hosted bundle enables `kek-kms`, and a self-hoster's profile layer may enable `events-nats` and disable `events-outbox`. The tenant layer cannot. On self-host a distribution built by the operator may add entries to either binding map (section 11); hosted runs the release distribution only. This is what "pluggable" means for a bound key: by composition within the allowed set, by distribution manifest beyond it. A provider of a bound key is in-process code, so adding one needs a distribution build anyway and the binding line is written in the same `dist.yaml`.

- **Modules and import boundary.** `sdk/kernel` (no `require`); `sdk`, rooted at `sdk/` (requires `sdk/kernel` and pgx v5: definitions under `sdk/def/`, `sdk/plugin`, `sdk/gate`, in-memory fakes, suites; ADR-060 decision 54); `sdk/testkit` (`kerneltest`, `sqlfake`, goleak; a test-only dependency). `plugins/A` imports the SDK and its own dependencies and never `plugins/B` (everything but `plugin.go` is under `internal/`; an analyzer refuses the rest). No `fake` or `sdk/testkit` package may appear in the package graph of a server binary (amended 2026-11-23, ADR-060 decision 58): the builder and the gate check the graph, and only `_test.go` files and the `aiopsctl` check runner import them.
- **No side door, no use after release.** The method set of a provided value must be a subset of the definition's interface; every registration method takes the caller's `*kernel.Context` first (definition lint); every suite asserts that a call after the provider is disposed returns `ErrInactive` (Cordis: "cannot get required service in inactive context").
- **Go traps are provider rules.** River has `AddWorker` and no removal, so `jobs-river` registers kinds once and dispatches through a revocable handler table, and jobs of an unowned kind snooze; `http.ServeMux` cannot unregister, so `http-server` keeps a copy-on-write route table and answers 503 for a route the committed generation declares whose owner is not ACTIVE; the default Prometheus registry panics on a second activation, so `metrics` gives each fiber its own registerer. Every registry exposes `Inventory()` and stores contributions in `tenants.Table`.
- **Versioning (amended 2026-11-11; ADR-040 decided).** Every definition has its own `major.minor` in `sdk/def/<name>/v<N>/definition.yaml`; the major is in the import path, the key and the proto package. `engines.aiops` is removed: a manifest carries a generated `requires` and a signed distribution manifest a generated `serves`, and the gate compares them. On a stable major a needed minor must not exceed the served one; at major 0 the exact minor is needed unless the definition carries `compatibleFrom`. A breaking change is a new package `v<N+1>`, with `v<N>` served through an adapter row, proven by the old suite, for at least 12 months and two further minor releases and removed only in a platform major release; at most two majors are in service. A definition leaves `v0` by a release review decision, and `v1.0` is contract-identical to the last `0.y`. The statement is 00 §4.3; the detail and the stability of the manifest schema, the index format, the author API and the remote protocol are community record §4.

**The transaction contract.** One `Tx` type sits behind `sql`, `sql.Bound` and `platformSql`, and its home is the `sql` definition:

```go
package sql // sdk/def/sql/v1; imports pgx v5 for row and tag types, said plainly: the SDK takes this one dependency
type Tx interface {
	// No SQL-string methods (ADR-045, owner decision 2026-11-19). A plugin reads and writes through the typed
	// operations of its own reviewed catalog; the provider generates and binds the statements. API ratified at S3.
	AfterCommit(fn func()); OnRollback(fn func()) // participant hooks: how an in-memory fake of jobs, events or audit joins
	Tenant() tenants.Handle // what the transaction was opened with; EnqueueTx and EmitTx stamp from it, never from an argument
}
// The key sqlDriver (Pgx(tx) pgx.Tx; As(tx, fn), a role switch) is consumer-bound to the providers of jobs, events, audit and kv.
```

Rules. (1) Only infrastructure definitions (`jobs`, `events`, `audit`, `kv`) take a caller's `Tx`; each suite asserts that a rollback leaves nothing enqueued, emitted or appended. Domain plugins never pass a `Tx` to each other: they coordinate through the outbox with idempotent handlers. (2) Every plugin has its own PostgreSQL role, limited to its schema and applied by the `sql` view with `SET LOCAL ROLE`; the runtime role owns no table. `events` and `audit` write through `SECURITY DEFINER` functions their providers own; `jobs-river` switches to its own role around River's unmodified `InsertTx` (`sqlDriver.As`). A plugin therefore cannot write `approval`, `change`, `audit`, outbox or River rows through `sql`. (3) `events` is durable in the caller's transaction: every provider writes the same outbox table and differs only in the relay, which is what "replace the events provider" means. (4) A cross-tenant or tenant-less enqueue, emit or fan-out needs the platform transaction (`platformSql`). (5) A remote contribution joins no transaction: it returns a result and its dispatcher commits state, event and audit in one transaction; a remote plugin's own `kv` write and audit append are separate commits. (6) Schema migration is a durable effect run by the `durable` leader under the owner role; the `sql` view is available to a caller only when that plugin's declared schema version is applied, so a consumer whose schema is behind is PENDING. Anything applied before a generation commits is expand-only.

## 7. The fail-closed argument for policy plugins
Claim: with the approval floor, the ledger, credential leases, the audit chain and the scrub as plugins, no composition, layer, tenant overlay, failure or contribution yields a write, a model call or a message that skipped them. The claim covers missing, failed, mis-composed and mistaken plugins in process, and hostile plugins out of process. Five mechanisms, each generic:

| # | Mechanism | Guarantee |
|---|---|---|
| M1 | **Required inject.** The dispatcher of every effectful operation injects the policy services | Without an ACTIVE provider the dispatcher is PENDING, so the capability does not exist. A policy provider that fails at run time unloads its consumers first. Absence is closed |
| M2 | **Owner-side guard.** A contribution is registered with a registry and provided under no key; only its dispatcher can call it, and the dispatcher applies the invariant before or after the call | An executor, a notifier or a model provider is unreachable except through `remediation`, `notifications` or `llm-gateway` |
| M3 | **Bound providers.** In the kernel: `Provide` on a provider-bound key succeeds only for a module-table entry in the allowed set, there is one provider, no `Isolate` and no `Want`. In admission: layers 1 to 4 choose within the set and the tenant layer never; no layer disables the last provider, re-inserts its id, or isolates the key | Nobody can mount a permissive `approval` in a group, read it with a fallback, win a restart gap, or claim its id from a child spec |
| M4 | **Bound consumers and no ambient authority.** A consumer-bound key resolves only for entries the distribution manifest lists (`platformSql`, `sqlDriver`, `tokens`, `kek`, `loader`, `reload`, `pluginManager`, `tenantMint`, `credentials`, `durablePurge`, `profileContext`, `appExit`). Every plugin has its own database role; secrets are scoped (tenant, plugin, name); write credentials come only from `credentials.Write(token)`; the gateway injects the tenant header | A community or site plugin that writes `Need(platformSql)` is refused at build, at the gate and at resolve. A contribution that ignored every guard has nothing to write with. The strongest fences are outside the process |
| M5 | **Monotonic gates with a static expected set.** A policy decision is extended only through a `Gate`: every listener runs, the strictest verdict wins, none may grant; an error, a panic or a timeout is the strictest verdict. The expected listeners are the rows of the committed generation that declare the hook in that scope: if one is not ACTIVE, is unloading or is unreachable, the check denies | A plugin can add a freeze window. It cannot approve, and it cannot be made to disappear |

| Invariant | Bound provider | Injected by | If absent or failed | Suite proves |
|---|---|---|---|---|
| Approval floor, quorum | `approval` | `change-hub`, `remediation`, surfaces | No executor is reachable | Never below the floor; L3 needs two distinct verified users; the requester cannot approve; an invalid stored raise denies |
| Ledger before a write | `change-hub` | `remediation`, `credential-lease` | No token, so no lease and no `Apply` | `Apply` without a valid token or with a changed digest is refused |
| Credential leases | `credential-lease` | `remediation` | No write credential exists | `Plan` and `Verify` get none |
| Audit chain | `audit-chain` | every state-changing provider | They are all PENDING | Append in the caller's `Tx`; update and delete blocked by a database trigger |
| PII scrub | `pii-pseudonym` | `llm-gateway`, `notifications`, `chat`, `tools` | No model call, message or tool result | A seeded identifier never leaves unscrubbed, to a model, a channel or a remote listener |
| Tenant fence | `sql-postgres`, `http-server`, `tenant-directory` | all | Nothing serves | A transaction with no handle sees zero rows; a job or event runs under the tenant of the transaction that wrote it |

**At run time.** Losing a policy provider is not a reason to exit: M1 already makes writes impossible. Its consumers unload by epoch, the routes they owned answer 503, write readiness fails, `restart-policy` retries the provider in place, and the process stays up; ingest, correlation, investigation and paging never injected `approval` and keep running (00 §2.1 row 5). Losing an infrastructure provider (`sql`, `jobs`, `events`, `http`) unloads everything and is retried in place; only when `restart-policy` gives up does the process exit non-zero (section 13).

**Try to break it.** Paging and the audit append are deliberately hook-free: nothing a plugin registers can withhold a page or an audit row. `test/policy-bypass/` runs on the built binary, and each attempt must end in a refusal or in writes being impossible: (1) compose without `approval`; (2) disable it in the profile, site or `--patch` layer; (3) lower a tier in a tenant overlay; (4) add a row whose plugin declares `Provides: approval`; (5) isolate `approval` on a group; (6) declare `Want(approval)`; (7) fail `approval` at run time; (8) register a waterfall listener that returns "allow" without `next`; (9) call an executor from a plugin that is not `remediation`; (10) present a token for another digest; (11) isolate `audit.Bound` on a group with a no-op provider; (12) link a `fake` into a server build; (13) mount a child spec with the id `aiops/approval`; (14) `Need` each consumer-bound key from an unbound plugin; (15) write another plugin's table through `sql`; (16) enqueue or emit for tenant B from tenant A's transaction; (17) put `${env:...}` or `${file:...}` in a layer 5 value; (18) disable a required row or a gate row from a tenant overlay; (19) `insert` an existing id with another plugin, or add the `api` role to a worker row by patch; (20) make a gate listener absent four ways (fail the freeze row, unload the tenant tree when idle, exhaust a remote listener's reconnect budget, check during its unload); (21) dispatch a hook for tenant A and observe it from tenant B's tree; (22) call back from a disabled remote instance on every replica; (23) compose a process-scope remote row in a multi-tenant profile; (24) set `agents-paused` and try to undo it by config.

**What stays outside plugins, and why dsh agrees.** Admission, both binding maps, the required set and the reading of kill switches are in `boot` and the signed distribution manifest (`dsh-app-boot` owns admission, the required list and the telemetry switch). The class check in the kernel knows nothing of what a key means. This is an addition, not a dsh property: dsh trusts every plugin of one user. **Honest limits.** In-process Go shares the address space: the bindings, the per-plugin database role and the import boundary stop a missing, failed, mis-composed or mistaken plugin and an honest plugin with a bug. They do not stop hostile code, which can reach memory and issue `SET ROLE` itself (dsh: "not a sandbox against malicious package code"). Hosted therefore links in-process code only from the release distribution and runs every third-party plugin out of process, one instance per tenant. On self-host the operator decides (this closes ADR-039): a self-built distribution may add entries to both binding maps and may raise, never lower, the required set; its manifest is signed by a key the site lists under `distributions` in `trust.yaml`; boot prints every departure from the release bindings, the dump and `aiopsctl profile verify` report them, and each generation's digest and signer set is written to the audit chain.

## 8. Hooks
| Cordis (`events.ts`) | Go | Semantics |
|---|---|---|
| `emit`, `parallel`, `serial`, `bail` | `kernel.Event[A]` | All four modes carried. Observers cannot change an outcome |
| `waterfall` | `kernel.Waterfall[A, R]` | As is: outermost first; no `next` vetoes the chain and the built-in behaviour; `next` twice is an error |
| `ctx.tools.guard()`, an owner-side service in dsh | `gate.Gate[A, V]` in `sdk/gate`, built on `Event` | Monotonic: the definition declares an order over its verdicts (approval: allow, raise, deny; send: allow, delay, drop) and the strictest wins. The owner injects `composition` to know the expected set (M5) |

Rules that differ from Cordis, each deliberate:
- **Order** is by declared stage (the definition names its stages), then plugin id. `aiopsctl profile render --dump-hooks` prints every chain, kept as a golden file per shipped profile.
- **Ownership.** Only the fiber that provides the owning key dispatches (`OwnedBy`); a plugin declares the hooks it listens on and the kernel refuses an undeclared `On`; each hook has an access class checked by the gate (`open`, `signed`, `sealed` to the distribution).
- **Audience.** In Cordis the filter is supplied by the dispatcher, a dispatch without one reaches every listener, and `global` bypasses it. Carried as is, a process-scope owner would deliver tenant A's payload to listeners in tenant B's tree. Here a listener registered under a scope value receives only dispatches whose audience admits it; a dispatch with `kernel.Unscoped` reaches unscoped listeners only; `global` is not carried. The kernel only evaluates the predicate: `tenants.Audience(ctx)` builds it from the handle and admits that tenant's tree plus the process-scope rows enabled for that tenant. A hook the definition marks as carrying tenant data cannot be dispatched with `Unscoped` (definition lint and a kernel check). Before a tenant-relevant gate check the owner calls `tenantTrees.Ensure`; if the tree cannot be mounted the check denies. A gate on the ack path (`http/request`, `signal/admit`) admits process-scope listeners only, so it never waits for a tenant tree.
- **Remote listeners** are allowed only on hooks marked below, under a deadline, and receive the scrubbed form of the payload unless the definition marks a field raw, which forces the `signed` class. Kernel hooks are in-process chains; `events` is the durable outbox.
- **Kill switches are not listeners.** `casefile` reads `agents-paused` from the `killSwitches` launch service before it dispatches `incident/investigate`; `telemetry` reads `telemetry-disabled` and exports nothing while its row stays ACTIVE. Config cannot reach either.

## 9. Composition and reload
**Kept from 00 §6.1 unchanged:** the empty root, ordered bundles, id-addressed patches that replace the whole config, the name as an assertion, an unknown id warns, an empty file fails, only direct bundles contribute, layers 0 to 6, dumps with provenance, the schema dump, golden dumps.

**Row format.** `{id, plugin, config, enabled, required, roles, inject, intercept, isolate, group}`. `plugin` is the manifest id and replaces `type`. `inject`, `intercept`, `isolate` and `group` are the Cordis loader's entry fields. `roles` is ours: a closed vocabulary (`edge`, `api`, `worker`) that every row of a server bundle must state, enforced by lint, so no row lands in the internet-facing role by omission.

| Field or action | Layers 1 to 4 (bundle, profile, site, `--patch`) | Layer 5 (tenant overlay) |
|---|---|---|
| `insert` | A new id only; an existing id fails in every layer. `plugin` and `roles` are fixed at insert and no patch changes them | Never |
| `config` | Replaces the whole config | Only fields the schema marks tenant-writable, validated when written, volatile by rule, literal values |
| `enabled` | Yes, except the last enabled provider of a provider-bound key | Only on a `scope: tenant` row or a tenant-toggleable process-scope row (section 10); never a row in a required set (either source), a row that listens on a gate, or a provider of a bound key |
| `required` | May be raised, never lowered. A required row binds its id to its plugin | Never |
| `inject`, `isolate`, `group` | Yes, never on a required row, a provider of a bound key, or a group that holds one | Never |
| `intercept` | Yes; for a provider-bound key, bundle layers only | Never |

**No expressions, closed references.** dsh uses `!!js` for four things, each with a closed replacement: a platform gate is `roles` (or a bundle's `platforms`); a presence gate is a row-level `inject`, which leaves the row PENDING; a value read from a launch service is read by the plugin through an inject; a path or secret is a reference `${env|file|secret|flag:value}` resolved by `config-refs` on the `internal/config` waterfall. References are legal in layers 1 to 4 only. `env:` is limited to names with the prefix `AIOPS_REF_` and `file:` to one directory named by flag. A layer 5 value that contains `${` is refused at write, except `${secret:name}`, which resolves in the scope (that tenant, the row's plugin). `config-refs` resolves through the row's caller-bound `secrets` view, so it never reads outside the row's own scope. Dumps print references unresolved. A reference that fails to resolve is an error on the row, never "disabled".

**Reload.** The unit of reload is the row. The unit of change is a generation: one immutable composed tree with a digest over the tree, the module table and the lock digests of every remote plugin and of every pack with no code, so a generation also pins plugin and pack versions.

| Change | Applies |
|---|---|
| Only `Volatile` fields | Committed in place by the loader; no restart |
| Other `config`, `inject`, `intercept`, `isolate` | That fiber restarts; dependants restart only if it provides something, through their epochs |
| Enable, disable, insert or remove a row whose code is present; a tenant overlay | Live; an overlay touches that tenant's scope and tree only |
| The restart closure contains a provider the replica cannot serve without (`sql`, `jobs`, `events`, `http`, and whatever needs them) | In place, in every profile: the replica fails readiness, quiesces under the drain deadline, the fibers restart and consumers return by epoch. No exit. The composer therefore applies a process-scope generation to one replica at a time; a single replica is not ready for the settle time |
| A provider swap of a definition marked `durable` (`events`, `jobs`, `kek`, `blob`, `kv`) | In place, but admitted only when the old provider reports `Drained()` (an empty backlog, no wrapped key it alone can unwrap), checked by `profile render` and again at apply, or when the operator passes `--accept-loss <definition>`, which is audited. The class is on the definition, so every provider inherits it. `sql` has one allowed provider and no swap |
| New code | In process: a new binary and a rolling restart; the manager answers `rebuild-required` and prints the `dist.yaml` lines. Remote: live; the new instance is handshaken before the old contributions are removed |

The process is replaced, not restarted in place, in three cases only: a process-scope fiber leaked past its dispose deadline (a goroutine cannot be killed); a restore failed; `restart-policy` gave up on an infrastructure provider.

**One serialized reload.** The `reload` plugin owns one goroutine and one queue (dsh `runExclusive`; nested reloads rejected). File watches, the generation follower, the manager and `aiopsctl` all submit to it. `Submit` returns an operation id at once and never waits inside a leased call; the result is polled or streamed from `plugin-inventory`, which is outside every restart closure it reports on. Without the row every change answers `restart-required`, as dsh with its reloader disabled.

1. Compose layers 0 to 4 into a candidate. Pure.
2. Admit: gate, signature, bindings, every changed config as a candidate, the static graph, the `Drained()` precondition. Pure.
3. Plan: diff by row id; compute and print the restart closure. A failure in steps 1 to 3 rejects the generation with nothing touched.
4. Apply inside one `kernel.Batch`: remove, update, create. The loader never creates an entry for an id whose previous fiber is not DISPOSED (dsh `recomposeProfile` waits for disposal). An entry the plan creates, enables or replaces whose id, or a key it provides in the same realm, still has a previous fiber is mounted in a second batch once that fiber is DISPOSED. Per-fiber transitions do the rest; there is no planned wave.
5. Settle, then judge by the dsh rule (`dsh-app-boot` README): every row created, changed or explicitly enabled by this generation must be ACTIVE, and so must every required row; a row that was ACTIVE must still be; rows inactive before and untouched are warnings. The settle deadline is at least the largest load plus drain plus dispose deadline in the closure, and a fiber still UNLOADING at that point means wait, not judge.
6. Report the verdict. Commit or restore is the composer's decision (below); with one replica it is immediate. A failed restore ends readiness and the process is replaced.
7. Publish `composition/applied` with digest, generation and report, into the audit chain.

**Generations.** The `composer` (a leader on the worker role, a base row in every server profile) owns one state machine per scope: `proposed`, `canary`, `promoting`, `committed`, or `rolled-back`. Replicas report (replica, scope, generation, digest, verdict) and never select a generation themselves: a replica runs the committed generation, or a candidate when the composer names it in the canary or promoting set. Any failed verdict during canary or promotion rolls the scope back on every replica. Both process-scope and tenant-scope generations get one canary replica; for a tenant-scope generation the canary force-mounts that tenant's tree before it judges, because an unmounted tree has nothing to observe. The `durable` leader reconciles from committed generations, creates what a candidate adds before its canary, and deletes what a generation drops only after it commits. A replica whose image lacks a module reports `module-missing` and keeps the last generation it can serve. A breaker that opens inside the bake window pauses promotion and alerts (ADR-038).

**Where a generation is read from.** The process-scope generation must be readable before `prepare`, so it is never in a table that a row of that same generation serves. Self-host: the layer files on disk are the source; `reload-watch-files` is on in `dev` and off in server profiles. Hosted: an immutable generation object mounted into every replica and named by flag, written by the composer, holding the committed generation and at most one candidate with its target replica set; `reload-generation` follows the mount. A restarted replica boots the committed generation, never an unjudged candidate, and if it is in the promoting set it boots the candidate directly, so it never starts, reads a difference and restarts again. Tenant-scope generations, replica reports, and in hosted the profile layer, `plugins.lock` and the trust policy are rows in platform tables of the `composer` schema, written only through `plugin-manager` on the worker role.

## 10. Tenancy in the context tree
`Isolate` separates names, never memory, goroutines or data. Tenant data isolation stays where 00 §5 put it: row-level security, the gateway, per-tenant keys, per-tenant upstream processes.

| Construct | What it is | Cordis or dsh origin |
|---|---|---|
| Tenant scope | One child context per loaded tenant, kept by `tenant-directory`. `tenants.Scope.From(c)` is public; `With` works only from the fiber that provides `tenants`, so no plugin can file a registration under another tenant | `ctx.extend` |
| Process-scope row (default) | One fiber serves every tenant; tenant fields are read with `tenants.ConfigFor[C]`. It is **tenant-toggleable** only if its generated manifest shows registry contributions and hook listeners and nothing else (no route, job handler, subscription or `Provides`). One predicate, `tenants.Enabled(ctx, row)`, is consulted by the hook audience and by `tenants.Table`, the lookup every registry uses; conformance asserts that disabled for tenant T means zero calls of any kind for T. A plugin with other effects that a tenant may toggle must be `scope: tenant` | `dsh-scope`: nearest contribution wins. Adapted: for a process-scope row the revertible effects hold per process, not per tenant |
| Tenant tree | For plugins whose manifest says `scope: tenant`: `tenant-trees` mounts one group per loaded tenant under its scope. Disable is a real unload there | `dsh-agent-preset`: a nested loader tree |
| Bound views | Inside a tenant tree, `tenant-trees` isolates and provides `sql.Bound`, `kv.Bound`, `blob.Bound`, `secrets.Bound`, `audit.Bound`, `sidecars.Bound` and `tenants.Bound`, with no tenant argument. No bound key has a root provider, so a process-scope row that injects one never starts; admission refuses a `scope: tenant` plugin that injects the process form of a key that has a bound form, and any other plugin that isolates or provides a `.Bound` key | `Isolate` and `Provide`; the kernel never learns the word tenant |
| Tenant handle | For process-scope rows the tenant travels in the call's `context.Context` as `tenants.Handle`, an opaque type of `sdk/def/tenants` with no exported constructor. It is minted only through `tenantMint`, a consumer-bound key whose binding in the distribution manifest lists every entry dispatcher: the providers of `http` (after identity), `jobs` and `events` (from the tenant column their own `EnqueueTx` and `EmitTx` stamped from the writing transaction, never from job args or a payload), `signal-core` (ingest token), `fleet-agentapi` (agent JWT), `chat` (installation record), `remote` (the connection), `tenant-trees`, `tenant-lifecycle` and periodic fan-out jobs under `platformSql`. `sql`, `secrets` and `audit` read it; no handle means zero rows. A replacement provider of `jobs` or `events` mints because the manifest binds it as provider of that key. In tests `tenantsfake.As(ctx, id)` mints | Ours; 00 §5.1 "never derived from a payload" |
| Cold lookup | `tenants.Table` cannot confuse "no contribution" with "tree not mounted": a tenant lookup first calls `tenantTrees.Ensure(ctx)` (mount under the concurrency cap, await settle under a deadline) and never falls through to a process-scope contribution of the same name for a (tenant, row) pair present in that tenant's generation. On timeout a job snoozes and a synchronous path answers 503 with `Retry-After` | Ours |

Rules. Layer 5 keeps the limits of section 9. A tenant-scope `Apply` does no network I/O and starts no goroutine unless its manifest declares one (conformance; the remote proxy declares both), so a tenant tree is a cache: it mounts on first use, unloads when idle, and loads under a concurrency cap with jitter. Readiness of an upstream instance is availability, not an error: `sidecars.Bound` is available to a caller only while that instance is ready, so the consumer is PENDING, never FAILED. Per-tenant upstream processes, remote instances, their identities and virtual keys are durable effects reconciled by the `durable` and `sidecars` leaders; a fiber only binds to the endpoint. Definitions that tolerate a cold start (`notifiers`, `tools`, `harnesses`, `llmProviders`, `executors`: the job snoozes for up to the definition's cold budget) may scale an instance to zero; `oncallProviders` and anything on the ack or page path may not: their tenant rows are pinned, so the tree is never unloaded when idle and a page never waits for a cold start. A tenant has its own required set: if a tenant-required row (a stored approval raise) is not ACTIVE, write-capable dispatchers refuse that tenant.

**Durable state and tenant erasure.** `Spec.Durable` lists the namespaces a plugin owns: a schema with its version, a `kv` and `blob` prefix, job kinds, a secret scope, sidecar instances, and `external` steps (a backend tenant, a database of an external engine, a KMS key). The `durable` plugin records every namespace of every generation, per tenant, in its registry table. Disable keeps durable state; `plugin remove` detaches the row and keeps it; `plugin purge` drops it. Tenant delete is driven from the registry across all generations, not from the listeners that happen to be loaded: the saga does not finish, and the tombstone is not written, while any participant has not reported. A plugin that is disabled, failed or removed still has its `sql`, `kv`, `blob`, job and secret namespaces purged, by the owner of the namespace kind and by plugin id; an `external` namespace of a detached plugin blocks the saga until the plugin is attached again or an operator records the manual step (ADR-042). The order is the one of 00 §5.6, expressed as stages with `audit-chain` last (section 17).

Budget at 300 tenants, to be beaten or the design changes (ADR-036): about 97 shared fibers plus 2 to 4 per loaded tenant (at most about 1,200; ADR-036, accepted 2026-11-22, replaces this ceiling with 97 shared fibers plus at most 4 per loaded tenant and makes the 500-tenant benchmark the governing figure); no tenant tree at boot; a tree of in-process rows mounts in under 50 ms and holds zero goroutines while idle; a tree with remote rows mounts within the handshake deadline (2 s against a running instance, the definition's cold budget against one scaled to zero) and holds one stream per remote row; a root provider restart settles inside the drain deadline; one pod per (tenant, remote plugin).

## 11. Runtimes, installation and distribution
| Runtime | For | Isolation | Enters a profile by | Live |
|---|---|---|---|---|
| In-process Go | First-party rows, infrastructure providers, anything in a transaction or on the ack path, reviewed community plugins | None: trusted | The distribution builder, into the module table | No: a new binary |
| Remote over gRPC, any language | Third parties, Python, model-chosen actions; everything third-party in hosted | Process, network policy from `capabilities`, one tenant per instance | `aiopsctl plugin install` | Yes |
| WebAssembly | Reserved as `kind: wasm` in the manifest | | Not built: no dsh property and no journey needs it | |

**A remote plugin is a set of contributions, not a Cordis plugin.** It can register with registries marked `contrib`, listen on hooks marked remote, and call the callbacks below. It cannot provide a key, isolate, mount children, register a route, a job handler or SQL, join a transaction, or listen on any other hook. A third-party plugin is a first-class fiber only in process, through the builder. Hosted runs every third-party plugin remote, so in hosted a third party can never add a provider, a definition or a registry. That is the price of the isolation in section 7, and it is a row of section 15.

**The remote proxy fiber.** `aiops/remote` is an in-process plugin, one row per remote instance, built with `plugin.FromManifest` from the remote's `plugin.yaml` at install: its `Inject`, `Hooks` and registrations are that row's own, the hook dump and the static graph read them, and the kernel learns nothing about "remote". So a remote plugin activates and unloads by the same rules as any fiber.
- **Dial and identity.** The kernel dials the plugin; the endpoint comes from `sidecars`. The stream is mutual TLS: the instance presents a certificate issued for (tenant, plugin instance), the replica presents the cell's kernel certificate. Row and tenant come from the connection, never from a request field. In a multi-tenant profile a remote row must be `scope: tenant` (gate check 9).
- **Activation is per connection.** With three replicas there are three proxy fibers for one instance. An activation id is (replica id, epoch); `Activate{activation, generation, config}`, `Register{activation, effect_id, definition, spec}` and `Deactivate{activation}` all carry it, and `Deactivate` ends that connection's registrations only. Inside the plugin, `sdk/remotehost` runs one fiber per activation with that activation's config, so replicas on different generations are served correctly and one replica's idle unload does not touch another's contributions. A registration from a superseded activation is refused, which is `INACTIVE_EFFECT` across the process boundary.
- **Callbacks ride the proxy's own stream**, never a load-balanced listener, and are accepted only by the replica that holds that ACTIVE activation: telemetry over OTLP, own-scope read-only secrets, `kv`, `blob`, audit append, `llm` with a virtual key, `credentials` for an executor through `remediation`.
- **Lifetime.** The instance, its certificate, its virtual key and its secret scope are durable effects of the `sidecars` and `durable` leaders, never of a fiber. On disable, remove and quarantine the leader revokes the certificate and the virtual key first, then deletes the pod; from that moment every replica refuses the stream. The kernel never launches a plugin process: on one VM the leader can revoke but cannot stop a unit, so `aiopsctl plugin disable` run on the host also stops it, and inventory flags an instance that still answers after revocation.
- **Loss.** A remote plugin provides no key, so its loss never changes another fiber's epoch: a short disconnect marks contributions unavailable and fails fast behind the breaker; an exhausted reconnect budget unloads the proxy and the kernel unwinds every registration. A proxy disposer never waits on the remote beyond a bound shorter than the dispose deadline.

**One plugin, either runtime**, for plugins whose `Inject` is within the callback set and that register only `contrib` registries and remote-capable hooks: `sdk/remotehost` is the kernel itself with definitions provided by gRPC callback clients, so one Go `Plugin` value passes the same suite in both runtimes. The Python SDK (`aiops-sdk`) is generated from the protos.

**Publishing.** `aiopsctl plugin pack` builds one OCI artifact, with its signature and attestation as referrers: the image digest (remote) or the module path, version and sum (in-process); `plugin.yaml`; a bundle patch of one or more rows, disabled by default; an SBOM; and the conformance attestation (suite version, definition majors, subject digest), which `plugin sign` signs. `aiopsctl plugin sign` (key mode, in the format cosign writes; keyless is not offered at S2a, ADR-020), `aiopsctl plugin push <registry>`, and optionally a pull request to an index repository. A spec is one of `oci://<registry>/<repo>@sha256:<digest>`, `<id>@<version>` through a configured index, or a local path (dsh `inspect(spec)`).

**Installing through plugin interfaces without core source changes.**

| The plugin is | The self-hoster runs | Result |
|---|---|---|
| Remote | `aiopsctl trust add <signer> --ids <pattern> --runtimes remote`; `plugin inspect <spec>`; `plugin install <spec> --profile <p>`; start the instance; `plugin enable <row>` | Install checks signature, trust policy, the gate and the attestation, and runs no third-party code. It writes `plugins.lock` by digest, appends the artifact's bundle as a direct bundle at the end of the profile's bundle list (as dsh does) and renders a deployment unit. No rebuild |
| In-process Go | The sequence below | A new image whose module table holds the plugin |
| Nothing to build | The `aiops` image (first-party) or the `aiops-contrib` image (plus community in-process plugins whose suites run in our CI) | |

Starting a remote instance, per target: compose, install writes a fragment and a line in the `sidecars-static` table, and `aiopsctl plugin start <id>` runs it; systemd, a unit and `systemctl enable --now`; Helm, a `plugins.remote[]` values entry applied by `helm upgrade`, or `sidecars-kubernetes` enabled in self-host with its RBAC. `plugin enable` refuses, printing the exact command, while the endpoint is missing from the `sidecars` table or does not answer the handshake. `aiopsctl plugin verify <spec>` is the explicit, optional re-run of the suite against a pulled image; it is not part of install.

**In-process Go: `dist.yaml` and the builder.** `dist.yaml` has four fields: `release` (an OCI reference by digest to the release's own `dist.yaml`, a release asset that carries the module table, the pins, both binding maps and the required set, and whose OCI manifest names the release's builder image by digest in an annotation, ADR-044 decision 1); `plugins`, a list of `{module, version, sum}`; `bindings: {providers, consumers, sealedHooks, required}`, needed only to add a provider or a consumer of a bound key, a listener on a sealed hook or keys and rows to the required set (ADR-044 decision 22); and `acceptLicenses`, where each accepted SPDX id is recorded in the signed manifest and printed at boot.

1. `aiopsctl plugin install <spec>` answers `rebuild-required` and prints the `dist.yaml` lines.
2. `aiopsctl dist build` (or the builder image; no local toolchain; `--modcache <dir>` for an air-gapped site) generates the module table and `go.mod` in a scratch directory, then builds with `-mod=readonly`, cgo off and no `go generate`. It fails when minimal version selection changes any version pinned by the release, unless `--allow-bump <module>` names a module the release pipeline does not build, so never one of the three SDK modules or the root module (the OpenTelemetry Collector Builder's strict mode; ADR-044 decision 20); when a module outside the release declares an id under `aiops/`; when a `fake` package is in the graph; when a deny-list scan finds a transitive `init` that registers a `database/sql` driver, a default-mux handler, a default-registry collector or a global codec, except the codec registration of `google.golang.org/grpc/encoding/proto`, exempted by package and pinned version, in a build with the tag `grpcnotrace` (ADR-020); or when the L7 allow-list, run over the build list with detected licences, finds a licence that is outside it, unknown, or not in `acceptLicenses`. It runs the import boundary and conformance on the source and writes `THIRD_PARTY_LICENSES/`, the aggregated NOTICE texts and an SBOM into the image, and writes the site's `aiopsctl`, the `cli` profile of the same module table (ADR-020).
3. `aiopsctl dist sign` signs the distribution manifest (module table with sums, both binding maps, the required set, accepted licences) with the site's key, listed under `distributions` in `trust.yaml`. For a Go module, gate check 5 is: path, version and sum, where the toolchain records one, equal an entry of a manifest signed by a trusted distribution key.
4. Roll the image: `aiopsctl dist use <image>` rewrites the compose file, or `image.tag` and `helm upgrade`.
5. `aiopsctl plugin install <spec>` now appends the bundle with its disabled rows; then `plugin enable <row>`.

`aiops` and `aiops-contrib` take no licence acceptance; remote plugins are separate programs and stay unrestricted (08 L16). Index: a Git repository with one file per plugin, composed by CI into one document with a detached signature checked before the document is parsed (dsh lists unsigned indexes as a limitation); trusted for discovery only; no index configured by default, so the default spec is an OCI reference; a private index never falls through to a public one. `trust.yaml` lists signers, each limited to id patterns and runtimes, the distribution keys, and `allowUnsigned: [ids]`, which is empty in hosted and printed at every boot elsewhere.

## 12. Plugin manager and compatibility gate
`plugin-manager` provides `pluginManager`; `plugin-inventory` the read-only view; `plugin-index` the index reader. The CLI and the service share one operations library and one profile write lock. Every operation is a submission to the reload queue, is audited and emits `plugin-manager/changed`. Self-host: files on disk are the source. Hosted: the platform tables of section 9. The manager cannot disable itself, a required row, the last provider of a bound key or another profile. It is not exposed as an agent tool, and `pluginManager` is consumer-bound so no contributed tool can wrap it.

| Operation | Does |
|---|---|
| `list`, `inspect` | Rows with plugin, version, runtime, scope, state, epoch, what each waits for, health, effects, signer, per tenant with `--tenant`; what a spec names, fetching only the artifact's manifest and bundle, never its content, module or image, and running nothing (amended 2026-11-23, ADR-060 decision 58) |
| `install`, `remove`, `purge` | Section 11; a failure restores a snapshot of the profile definition, `plugins.lock` and the profile patch. `remove` detaches and keeps durable state; `purge [--tenant <id>]` drops the plugin's durable namespaces through `durable` |
| `enable`, `disable` `[--tenant <id>]` | Writes only a departure from the bundle layers, into the profile layer or a tenant overlay; one generation, forward |
| `update --cohort` | Check, apply to a cohort or tenant, judge, promote or restore |
| `profile rollback --scope process\|tenant/<id> --to <generation>` | Returns the whole scope, lock digests included, to an earlier committed generation |
| `rollback <id>`, `quarantine <id>@<version>`; `allow-version`, `revoke-version` | An `update` to the previous locked version; or deny one exact version everywhere and revoke its instances; exemptions |

**The hosted journey: enable a remote plugin for one tenant and roll it back.**
1. `plugin install <spec>` by a platform admin: gate, lock, bundle appended with its rows disabled at process scope. That is process generation G+1: canary replica, promotion, commit. This is what makes the row offered to tenants; an overlay can never insert.
2. `plugin enable <row> --tenant <id>`: an overlay, tenant generation N+1. The leaders create the instance, its certificate and virtual key first; the canary replica mounts the tenant's tree, the proxy must reach ACTIVE (step 5 of section 9), then promotion and commit.
3. To undo: `plugin disable <row> --tenant <id>` reverts that one row by a new generation; `profile rollback --scope tenant/<id> --to N` reverts everything in the tenant's scope since N. Either way the leader revokes the certificate and virtual key and deletes the pod after commit. The plugin's durable namespaces for that tenant are kept, so enabling again finds its state, until `plugin purge <id> --tenant <id>`.
4. Automatic restore is neither of these: it is the composer returning a scope to its committed generation when a candidate fails its judge.

| # | Gate check | Denies when |
|---|---|---|
| 1 | Manifest schema and author API (amended 2026-11-11; was `engines.aiops`) | The manifest major is unknown; `requires` is absent (stricter than dsh, where absent means no constraint); the author API version it names is not served |
| 2 | Definition versions (amended 2026-11-11) | `requires.definitions` names a major the distribution does not serve, or a minor outside the rule of section 5 |
| 3 | Remote protocol | No common version at handshake, or the manifest digest differs from the lock |
| 4 | Stability | Below the profile's `minStability` |
| 5 | Trust | Signature missing or signer outside `trust.yaml` for this id and runtime; a Go module absent from a trusted distribution manifest |

| 7 | Key and hook classes | A provider or consumer outside a binding, read from the generated `provides` and `uses`; a `signed` key or hook used by an untrusted signer; a `fake` in a server graph; a required key or row whose static need closure contains a provider outside the required set (the dump prints the closure) |

A denied row is detached as disabled in the launcher's copy; no file is rewritten; the dump names the unmet check. Exemptions follow dsh (`compatibility.yaml`, exact `id@version` to exact SDK versions, inherited by neither upgrade, `--accept-risk`) and cover checks 1, 2 and 4 only. Hosted denies exemptions. Health (`ok`, `degraded`, `failed`) is separate from state and never unloads a dependant.

## 13. Failure policy
`required` is one concept with two sources: the distribution manifest (no layer can remove it) and `required: true` on a row (a layer may add it, never remove it). The distribution set is written as dsh writes it, by what must work rather than by who provides it: **keys that must have an ACTIVE provider**, plus a few rows named by id. So replacing `events-outbox` with another allowed provider satisfies the audit. Every server profile requires the keys `sql`, `jobs`, `events`, `http`, `secrets`, `kek`, `tenants`, `identities`, `audit`, `approval`, `pii`, `durable`, and the rows `loader`, `restart-policy`, `reload`, `readiness`, `composer`; with any executor row also the keys `changes`, `credentials`, `executors`. Hosted adds the keys `tokens`, `gateway`, `signals`, `sidecars` and the rows `fleet-agentapi`, `signal-ingest-alert-webhook`, `kek-kms`. A required key or row that is absent, disabled or not ACTIVE stops boot (stricter than dsh, kept from 00 §6.1). The dump shows the set plus the static closure of its needs; observability keys are never in a closure (section 5). With `--role` the set applies to the rows that role runs.

The failure policy table is in 08 §1.6, the only failure matrix of the set; `test/failure-matrix/matrix.yaml` is that table and the input of the test that boots the built binary through every cell with fault plugins (`fail-apply`, `panic-apply`, `slow-apply`, `bad-config`, `rogue-provider`, `leaky-goroutine`, `slow-dispose`) and stub remote images (one hangs a call, one ignores `Deactivate`). Amended 2026-11-21: this section held a copy of the table, which ADR-059 decisions 13 and 14 of 2026-11-20 outdated for a tracked goroutine, a leak and a `restart-policy` that gives up (a required row that fails at boot stops boot, and a leak marks the fiber leaked and replaces the process in every column). The copy is removed so that it cannot drift again.

A Go limit, stated in the matrix: a goroutine cannot be killed. An `Apply` past its deadline is FAILED, its goroutine runs until it returns, and anything it registers later gets `ErrInactiveEffect`. Optional failures print once as one grouped diagnostic with state, error and what each row waits for.
