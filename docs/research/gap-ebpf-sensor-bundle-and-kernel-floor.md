## 1. Decisions in one screen

| Question | Decision | Why (details in the section cited) |
|---|---|---|
| Which eBPF sensors ship in the customer bundle | `beyla.ebpf` (RED metrics, traces, network flows) and `pyroscope.ebpf` (whole-host profiles) inside the Alloy DaemonSet; Tetragon as a second DaemonSet for runtime security | §2, §3 |
| Child process vs standalone container for Beyla/OBI | Use Alloy's `beyla.ebpf`, which is already a supervised child process (since Alloy 1.19.0). Standalone Beyla/OBI container only as an escape hatch (sidecar/`--pid=container` mode, or when a feature lands in OBI before Alloy picks it up) | §2.1, §2.3 |
| Profiler isolation | `pyroscope.ebpf` is in-process (Go library). Accept it; a crash takes Alloy down, so keep it behind a feature flag and ship the watchdog/restart at the systemd/Kubernetes level, not inside Alloy | §2.2 |
| Falco vs Tetragon | Tetragon is the default sensor in the bundle; Falco is an optional, mutually exclusive plugin for tenants that want the curated Falco rule library. This overrides `oncall-and-aiops-oss.md` §B.3 (which chose Falco); the architect must ratify | §3 |
| Kernel/BTF floor | Tier A (supported): Linux >= 5.10 with `CONFIG_DEBUG_INFO_BTF=y` (`/sys/kernel/btf/vmlinux` present), amd64/arm64. Tier B (best effort): RHEL-family 8.5+ (4.18.0-348+). Tier C: everything else gets Alloy without eBPF components, chosen automatically by the config generator | §4 |
| BTF mirror (btfhub-style) | Do not ship one in v1. | Agent-side C2 | Two DaemonSets on Kubernetes (Alloy privileged + Tetragon), one singleton Deployment (OBI k8s-cache for > ~50 nodes), tetragon-operator; on hosts, Alloy + Tetragon as two systemd units. Not the Datadog "one pod, system-probe sidecar" shape | §6 |
| Non-goals | Windows network/USM/CWS, Fargate (ECS/EKS) eBPF-less mode, GKE Autopilot eBPF, BTF-less kernels, kernel-module drivers, SNMP traps + MIB DB, NetFlow enrichment, traceroute/Network Path, in-kernel enforcement by default, Go write-memory context propagation by default | §7 |

## 2. Sensor inventory and isolation model

### 2.1 `beyla.ebpf`: Alloy child process (not a library, not a separate container)

- Alloy docs: "Alloy spawns Beyla as a child process and transfers the required capabilities" via "the kernel's inheritable and ambient capability sets"; "`beyla.ebpf` runs Beyla as a separate child process. This isolates failures in Beyla from Alloy". Process metrics carry `subprocess="beyla"`. The embedded version is "Grafana Beyla version v3.38.0". Capabilities: `BPF`, `NET_ADMIN`, `NET_RAW`, `PERFMON`, `DAC_READ_SEARCH`, `SYS_PTRACE`, `CHECKPOINT_RESTORE`, `SYS_RESOURCE` (kernels < 5.11), `SYS_ADMIN` "for library-level instrumentation only"; Kubernetes needs `hostPID: true` and an Unconfined AppArmor profile; `privileged: true` is "not recommended for production". Source: https://grafana.com/docs/alloy/latest/reference/components/beyla/beyla.ebpf/ (Alloy 1.21.2).
- Implementation (grafana/alloy `main`, `internal/component/beyla/ebpf/`): `exec_linux.go` "Spawns Beyla: raises eBPF capabilities, extracts the embedded binary to a memfd, `exec`s it, and pipes its logs"; config is also passed as a memfd; `otlp_linux.go` "ingests the subprocess's OTLP over a unix socket and forwards to the component's `output`"; Prometheus `/metrics` and pprof are proxied to the child; `watchdog_linux.go` "Periodic liveness probe; a dead/unhealthy subprocess triggers a restart". The binary is `//go:embed`-ded per arch from `binaries/{amd64,arm64}/beyla` with a `.beyla-binary-version` stamp; "Supported on `linux/amd64` and `linux/arm64`; elsewhere it is a no-op". Alloy's `go.mod` has no `github.com/grafana/beyla` or `go.opentelemetry.io/obi` dependency, confirming Beyla is shipped as a binary, not linked. Sources: https://github.com/grafana/alloy/tree/main/internal/component/beyla/ebpf (README), https://raw.githubusercontent.com/grafana/alloy/main/go.mod.
- History: CHANGELOG 1.19.0 (2026-08-21) "beyla.ebpf: Run Beyla as a subprocess (#6695)"; 1.21.0 (2026-10-16) "Add CAP_DAC_OVERRIDE in the allowed Linux capabilities list (#7303)". Source: https://raw.githubusercontent.com/grafana/alloy/main/CHANGELOG.md.
- Consequences for the bundle: the child shares the container cgroup (one memory limit covers both), has its own PID and restart loop, and its logs flow through Alloy. A Beyla verifier failure on an odd kernel no longer crashes the metrics/logs pipeline. Backoff interval and max-restart count are not documented (UNVERIFIED; read `supervisor_linux.go` before relying on them).

### 2.2 `pyroscope.ebpf`: in-process Go library

- `internal/component/pyroscope/ebpf/ebpf_linux.go` has build tag `//go:build linux && (arm64 || amd64)`, imports `go.opentelemetry.io/ebpf-profiler/...` and drives `controller.New(c.cfg)` / `ctlr.Start(ctx)` directly (retried up to `sessionMaxErrors = 3`); there is no `os/exec`. `go.mod` replaces `go.opentelemetry.io/ebpf-profiler` with `github.com/grafana/opentelemetry-ebpf-profiler v0.0.202602-0.20261014150131-01c499662e68` (the maintained variant's default branch is `pyroscope_alloy`; it adds on-target symbolization and target selection and states "The goal is to upstream these capabilities"). Sources: https://raw.githubusercontent.com/grafana/alloy/main/internal/component/pyroscope/ebpf/ebpf_linux.go, https://github.com/grafana/opentelemetry-ebpf-profiler.
- Privileges (Alloy docs): "you must run Alloy as root and inside the host PID namespace", or capabilities `BPF`, `PERFMON`, `SYS_PTRACE`, `CHECKPOINT_RESTORE` (kernel 5.9+, else `SYS_ADMIN`), `SYS_RESOURCE`, `DAC_READ_SEARCH`, `SYSLOG`; mount `/sys/kernel/tracing` (or `/sys/kernel/debug`) read-only; a writable symbol-cache directory. `no_kernel_version_check` (added in Alloy 1.18.0, 2026-07-17) skips the kernel check for distros with backports. Defaults `sample_rate` 19/s, `collect_interval` 15s. Source: https://grafana.com/docs/alloy/latest/reference/components/pyroscope/pyroscope.ebpf/.
- Kernel floor comes from upstream: "Commit 8047150e was the last to support kernel version 5.4. Subsequent changes may require a minimal Linux kernel version of 5.10 or greater"; policy is to track "the lowest kernel shipped by actively maintained major distros". Upper-bound cost claim: "1% CPU and 250MB memory are our upper limits in testing and the agent typically manages to stay way below that". Licensing: project Apache-2.0, "eBPF source code: GPL 2.0 (`support/ebpf/LICENSE`)". Source: https://raw.githubusercontent.com/open-telemetry/opentelemetry-ebpf-profiler/main/README.md.
- Consequence: a profiler fault is an Alloy fault. Mitigation is organisational, not code: the feature is off unless the tier check passes, Alloy restarts under systemd/kubelet, and the docs page itself warns that multiple `pyroscope.ebpf` instances add CPU/memory. Do not wrap it in a second supervisor.

### 2.3 Standalone Beyla/OBI container: when it is still the right tool

- The k8s-monitoring Helm chart's `autoInstrumentation` feature does not use `beyla.ebpf`; it installs the upstream `beyla` chart `1.16.16` as its own DaemonSet ("Beyla runs with hostNetwork enabled and binds its port on every node"), Alloy scrapes those pods (`beyla.labelMatchers`), and an optional `beyla.k8sCache` Deployment is sized "1 replica per 50 nodes as a starting point". Source: https://raw.githubusercontent.com/grafana/k8s-monitoring-helm/main/charts/k8s-monitoring/charts/feature-auto-instrumentation/README.md.
- Version skew is real but small: Alloy 1.21 embeds Beyla 3.38.0 (2026-10-05); Beyla 3.39.1 is "Latest" (2026-10-22, maintenance-only: "Bump go versions to latest"); 3.40.0 is a pre-release (2026-10-26) bundling OBI commits up to "Prepare OBI for version v1.0.0-rc.2". Beyla's README: "Beyla vendors part of the code from the opentelemetry-ebpf-instrumentation (OBI) project" as the `obi-src` submodule; "All Beyla current maintainers work full time on the upstream repository". OBI: v0.15.2 is "Latest"; v1.0.0-rc.1 (2026-10-07) and v1.0.0-rc.2 (2026-10-16) are pre-releases, each with "a minimum 14-day maintainer validation window"; "there is no `collector/v1.0.0-rc.2` tag". Sources: https://github.com/grafana/beyla/releases, https://raw.githubusercontent.com/grafana/beyla/main/README.md, https://github.com/open-telemetry/opentelemetry-ebpf-instrumentation/releases.
- Deployment modes OBI supports that Alloy's child process does not: sidecar sharing the pod PID namespace and `--pid=container:<app>` (OBI SUPPORT_MATRIX). These matter for namespaces where a privileged DaemonSet is not allowed but a per-pod sidecar is.
- Decision: the bundle uses `beyla.ebpf` (single config surface, single restart loop, one privileged pod, metrics/traces already wired to `otelcol.*` consumers). The standalone container is documented as the "advanced" path, and we track OBI 1.0 GA before considering swapping the embedded binary for the `otel/ebpf-instrument` image.

### 3.2 Decision and the condition that flips it

Default sensor: Tetragon.

1. The bundle's job is cheap, always-on telemetry with Kubernetes identity; findings are produced server-side by the SecOps plugin (Loki ruler rules over Tetragon events, plus Trivy/Kubescape/Prowler which already produce findings). That matches the plugin architecture: the agent emits events, server plugins decide.
2. In-kernel filtering and namespace-scoped CRDs give per-tenant/per-namespace policy delivery without rewriting rule conditions, and the same policy files work on hosts via `--tracing-policy-dir`.
3. Go user space on cilium/ebpf, same toolchain as Alloy/OBI; non-root operator (UID 65532 since v1.6.0); explicit capability list without `privileged: true`.
4. Floor (4.19 + BTF) sits inside our Tier A/B, including arm64 at 5.10.
5. The only published overhead numbers are Tetragon's, and the JSON export already fits `loki.source.file`.

Flip condition: if the SecOps pillar must ship curated detections at v1 without us authoring a starter policy pack and Loki ruler rules, choose Falco (modern eBPF only, `leastPrivileged: true`, `file_output` JSON tailed by Alloy, `falcoctl artifact follow` per tenant). Never run both on a node. Never ship Falco's kernel module path.

## 4. Kernel/BTF floor and fleet coverage

### 4.1 Floor definition

- Tier A (supported): Linux >= 5.10, `CONFIG_DEBUG_INFO_BTF=y` with `/sys/kernel/btf/vmlinux` present, amd64 or arm64, cgroup v2. Rationale: OBI documents "Linux `5.8+`" with "Kernel must expose BTF", and its CI's lowest verified kernel is 5.10; the OTel eBPF profiler's recent commits need 5.10; Tetragon's arm64 recommendation is 5.10; Falco modern eBPF needs ringbuf (5.8). 5.10 is the lowest kernel every sensor is actually tested on. Tetragon note: cgroup v1 on kernels >= 6.11 additionally needs `CONFIG_MEMCG_V1=y` and `CONFIG_CPUSETS_V1=y`.
- Tier B (best effort): RHEL 8 family with 4.18.0-348+ (RHEL/Rocky/Alma/OL 8.5 and later, i.e. in practice 8.8-8.10 today). Beyla README: "Linux distributions running RedHat Enterprise Linux 4.18 kernels build 348 and above"; OBI CI covers RHEL 8.9/8.10; Falco modern eBPF reported working on 4.18.0-553; Tetragon and the profiler need `no_kernel_version_check`-style bypasses that are not officially covered (UNVERIFIED). BTF is native from 8.2 (4.18.0-193) per btfhub.
- Tier C: no eBPF components. The config generator decides per host from `uname -r`, `/etc/os-release` and the existence of `/sys/kernel/btf/vmlinux`; Alloy's `enforce_sys_caps`/OBI `OTEL_EBPF_ENFORCE_SYS_CAPS` default to warn-and-continue, so the generator must gate, not the sensor.

Sources: https://raw.githubusercontent.com/open-telemetry/opentelemetry-ebpf-instrumentation/main/SUPPORT_MATRIX.md, https://raw.githubusercontent.com/grafana/beyla/main/README.md, https://raw.githubusercontent.com/open-telemetry/opentelemetry-ebpf-profiler/main/README.md, https://tetragon.io/docs/installation/faq/, https://raw.githubusercontent.com/aquasecurity/btfhub/main/docs/supported-distros.md.

### 4.3 What "share of a typical fleet" means here

No public fleet-composition data was used, so the share is structural, not a percentage: of the 12 rows above, 8 are Tier A on their current default kernels (RHEL 9, Ubuntu 22.04/24.04, AL2023, Bottlerocket, GKE COS, Debian 11/12, Ubuntu 20.04 on HWE), 1 is Tier B (RHEL 8 family), and 3 are structurally excluded (Autopilot, Fargate, Windows) plus the two end-of-support kernels (AL2 4.14, Ubuntu 20.04 GA). A fleet that still runs AL2 4.14 or Ubuntu 20.04 GA in October 2026 is running unpatched kernels; our docs should say so instead of promising eBPF there. Datadog's extra reach (4.4 for NPM, 4.14 for USM/CWS) comes from runtime compilation and prebuilt-offset fallbacks that none of our upstreams implement (datadog-agent.md §1.4).

## 5. BTF mirror (btfhub-style): not in v1

- What exists: aquasecurity/btfhub-archive (Apache-2.0) holds BTF for "published kernels that lack native support for embedded BTF" under `amzn`, `centos`, `debian`, `fedora`, `ol`, `rhel`, `sles`, `ubuntu`. Covered families: AL2 4.14, CentOS/RHEL 7.x (3.10) and 8.0-8.1 (4.18.0-80/-147; later 8.x also mirrored though native), Debian 9/10, Fedora 29-31, OL 7.8-8.4 incl. UEK 4.14/5.4, SLES 12.3-15.3, Ubuntu 16.04-20.04 (5.4.0, 5.8.0 HWE). Datadog maintains `DataDog/btfhub`, a variant of aquasecurity/btfhub and its agent downloads `minimized-btfs.tar.xz` from `install.datadoghq.com` after trying user file -> kernel -> embedded collection (lookup order from `pkg/ebpf/btf.go`: "configured BTF file", "kernel", "embedded collection", "remote config"). Sources: https://github.com/aquasecurity/btfhub-archive, https://github.com/aquasecurity/btfhub, https://github.com/DataDog/btfhub, https://raw.githubusercontent.com/DataDog/datadog-agent/main/pkg/ebpf/btf.go.
- Who could consume it in our bundle:
  - Tetragon: yes. "If your kernel does not support BTF you can: Retrieve the BTF file for your kernel version from an external source", via `--btf` or `/var/lib/tetragon/btf/vmlinux` (FAQ; Helm `tetragon.btf`).
  - Falco modern eBPF: no. The probe design states "we cannot use solutions like BTFHub since when we try to access kernel memory directly, the verifier must check kernel BTF information", and those kernels lack the ring buffer anyway (libs proposal 20220329-modern-bpf-probe.md, via search excerpt).
  - Beyla/OBI: "Linux without BTF" is explicitly out of scope in SUPPORT_MATRIX; no external-BTF knob is documented (UNVERIFIED whether cilium/ebpf's `KernelTypes` override is reachable).
  - OTel eBPF profiler / `pyroscope.ebpf`: no documented external-BTF option (UNVERIFIED).
- Therefore a mirror would unlock only Tetragon on AL2 4.14 (EOL 2026-06-30), Ubuntu 20.04 GA (standard support ended May 2025), RHEL 8.0/8.1 and Debian 10, at the cost of hosting a multi-GB archive and a per-kernel lookup service. Decision: no mirror; Tier C is honest. Keep two cheap hooks: (1) the agent config generator accepts `btf_path` and passes it to Tetragon's `--btf`; (2) docs link btfhub-archive for customers who insist. Revisit if a paying tenant has a Tier C fleet it cannot upgrade.

## 6. Agent-side C2: privileged layout

### 6.1 Kubernetes

| Workload | Kind | Contents | Privilege | Host access |
|---|---|---|---|---|
| `aiops-agent` | DaemonSet (k8s-monitoring `privileged` + `daemonset` presets) | Alloy: node metrics/logs/OTLP receiver + `beyla.ebpf` (child process) + `pyroscope.ebpf` (in-process) | root, `hostPID: true`, AppArmor Unconfined, `privileged: false`; caps add `BPF`, `PERFMON`, `NET_ADMIN`, `NET_RAW`, `SYS_PTRACE`, `DAC_READ_SEARCH`, `CHECKPOINT_RESTORE`, `SYSLOG`, `SYS_RESOURCE` (kernels < 5.11), `DAC_OVERRIDE`; `SYS_ADMIN` only when Go library-level propagation is enabled (default off) | `/proc`, `/sys/fs/cgroup`, `/sys/kernel/tracing` (ro; `/sys/kernel/debug` on old kernels), `/var/log` (ro, includes `/var/log/tetragon`), symbol-cache volume (emptyDir), `/etc/os-release` |
| `aiops-sensor` | DaemonSet (Tetragon chart) | Tetragon agent + `export-stdout` sidecar | `privileged: false`, AppArmor Unconfined; caps drop ALL, add `SYS_ADMIN`, `SYS_PTRACE`, `SYS_RESOURCE`, `DAC_OVERRIDE`, `SYSLOG` | bpffs/tracefs/cgroup2 mounts (via SYS_ADMIN), `/var/log/tetragon` (rw), `/var/run/tetragon` socket; `rthooks` off by default (installs OCI hooks on the node, UNVERIFIED default) |
| `tetragon-operator` | Deployment | CRD install, policy reconciliation | non-root UID 65532 (v1.6.0+) | none |
| `obi-k8s-cache` | Deployment (optional) | OBI/Beyla Kubernetes metadata cache | none | API server only; "1 replica per 50 nodes" |
| Existing collectors | StatefulSet/singleton | metrics-collector, events-collector per grafana-stack.md §3.8 | none | none |

Why two DaemonSets rather than Datadog's one-pod `system-probe` sidecar: Tetragon brings its own chart, operator, CRDs and OCI hook installer with an independent release cadence (v1.7.1 vs Alloy's three-week minors), and its JSON export is a file, so co-location buys nothing except a shared cgroup. Beyla and the profiler, by contrast, are already inside Alloy, and the Alloy pod already needs the eBPF capability set for them, so a separate "probe" container for Beyla would duplicate privilege rather than reduce it. Tier C clusters (Autopilot, Fargate) run only the non-privileged collectors plus an Alloy sidecar for OTLP/logs.

### 6.2 Hosts (VMs, bare metal, Docker)

Two systemd units: `alloy` (root; the generated `config.alloy` enables `beyla.ebpf`/`pyroscope.ebpf` only on Tier A/B hosts) and `tetragon` (deb/rpm/tarball from tetragon.io, `--tracing-policy-dir` populated by the fleet plugin, JSON export to `/var/log/tetragon` tailed by `loki.source.file`). Docker-only hosts: the same two containers with `--pid=host` and the capability lists above; never `--privileged`.

## 7. Explicit non-goal list (v1)

1. Windows network flows, USM-style protocol parsing and runtime security. Datadog does these with the `ddnpm`/`ddprocmon` kernel drivers and ETW (datadog-agent.md §1.5); no OSS sensor exists, and none of ours builds for Windows. Windows gets `prometheus.exporter.windows` + `loki.source.windowsevent` only.
2. Fargate eBPF-less mode. Datadog's `cws-instrumentation` (ptrace) and `DD_NETWORK_CONFIG_ENABLE_EBPFLESS` have no equivalent. Fargate tasks get an Alloy sidecar for OTLP/logs/metrics; no process, network or security telemetry.
3. GKE Autopilot eBPF. Requires a Google partner allowlist we do not have. Autopilot gets the non-privileged collectors.
4. BTF-less kernels (AL2 4.14, Ubuntu 20.04 GA 5.4, RHEL 7, RHEL 8.0/8.1, Debian 10, Oracle UEK 4.14/5.4): no BTF mirror, no runtime compilation, no prebuilt struct offsets. Tier C.
5. Kernel-module drivers (Falco `kmod`, DKMS, header downloads). Modern eBPF only.
6. SNMP traps receiver and MIB/OID database; NetFlow/IPFIX/sFlow collection with SNMP/cloud/ASN enrichment. Not eBPF; deferred to a separate network-devices plugin (polling via `prometheus.exporter.snmp` stays in scope).
7. Traceroute / Network Path (scheduled or flow-driven). No Alloy component; deferred.
8. In-kernel enforcement on by default. Tetragon `Sigkill`/`Override` and Falco response engines ship disabled; `Override` is impossible on COS kernels.
9. Go write-memory context propagation (`bpf_probe_write_user`, needs `CAP_SYS_ADMIN` and lockdown `none`). Off by default; impossible on Bottlerocket and other lockdown-integrity hosts. Header-based (`context_propagation = "headers"`) and TC-based propagation remain.
10. Architectures other than amd64/arm64 (OBI, profiler and Alloy's embedded Beyla binaries are amd64/arm64 only).
11. Running Falco and Tetragon on the same node.

## 8. Open questions for the architect

1. Ratify Tetragon-default vs Falco-default (§3.2); `oncall-and-aiops-oss.md` §B.3 currently assumes Falco for the SecOps pillar.
2. Who authors the starter TracingPolicy pack and the Loki ruler detection rules if Tetragon is chosen; this is new work with no upstream equivalent to Falco's `falco-rules`.
3. Tetragon `rthooks` (OCI runtime hooks) default: on gives correct pre-start policy application but writes node-level runtime config; off is best-effort. Recommend off in v1 and document the race.
4. Bottlerocket SELinux labels for the two DaemonSets (`spc_t`/`super_t`) and whether Lockdown integrity breaks anything beyond Go write-memory propagation: needs a lab run.
5. Whether to let the config generator auto-enable `no_kernel_version_check` on RHEL 8 (Tier B) for `pyroscope.ebpf`, or require an explicit opt-in.
6. Alloy image size impact of the embedded Beyla binary and whether a slim image without `beyla.ebpf` is worth maintaining for Tier C hosts (not researched).
