Research note, 2026-10-27. Scope: the facts needed to draw the chat-ops C2 container and C3 components for the aiops-platform, for (i) the hosted multi-tenant tier with N customer Slack workspaces and (ii) self-hosted single-workspace installs. Every public upstream fact carries the source URL and the date/version it was checked against. Anything not confirmed from a primary source is marked **UNVERIFIED**. This note builds on `plugin-architecture.md` (kernel, extension points, profiles) and `oncall-and-aiops-oss.md` §B.9 (SDK versions, Socket Mode summary), and corrects two of their statements (§1).

Historical design sketch: the [canonical decisions](../architecture/00-decisions.md), especially §2.1 row 4 and §2.2, govern current Slack optionality, identity and approval contracts. ## 0. Summary

| Question | Answer (details in the section cited) |
|---|---|
| Distribution model, hosted multi-tenant | One publicly distributed Slack app owned by us, installed per customer workspace or org through OAuth v2, receiving events, interactivity and slash commands over the Events API at a public HTTPS request URL with request signing. Socket Mode is technically possible for a distributed app but is excluded from the Marketplace, and an unlisted commercially distributed app is throttled to 1 request/minute and 15 objects on `conversations.history`/`conversations.replies`, which an agent that reads thread context cannot live with. (§3) |
| Distribution model, self-hosted | The customer creates their own Slack app from a manifest we generate (`aiopsctl slack manifest`), so it is an internal app: exempt from the non-Marketplace throttle, no Marketplace review, Socket Mode by default (outbound-only, no public URL), Events API as an opt-in for sites that already have ingress. (§3) |
| Slack → tenant | An *installation* is `(enterprise_id, team_id, is_enterprise_install)`. Default mapping is one installation → one tenant; an org-wide Grid install maps the enterprise to one tenant with workspaces as sub-scopes; a channel binding table can override the tenant and the default pillar per channel. Route on `authorizations[0]` from the envelope, never on the inner event's `team`. (§4) |
| Slack user → platform user and approval role | `(installation, slack_user_id)` → platform user via a link table. Link by verified email scoped to the installation for read/ask roles; require an explicit Sign in with Slack (OpenID Connect) link, or a one-time confirmation in the portal, before a Slack identity may exercise `approvals.decide`. L3 quorum = two distinct *platform* users holding `approvals.decide`, neither of whom is the requester, both evaluated in the kernel, never in Slack. External (Slack Connect) users are never approvers. (§5) |
| Per-pillar addressing | One Slack app, one bot user, one agent. The pillar is a routing dimension: channel binding default, `/aiops <pillar> …` slash command, `@aiops <pillar> …` mention, and thread stickiness (a session opened by a pillar stays with it). Per-pillar persona via `username`/`icon_emoji` overrides (`chat:write.customize`). Slack has no sub-agent or multi-persona concept per app; "multi-agent stacking" means several *apps* in one thread. Separate apps per pillar remain an optional self-host configuration, not the default. (§6) |
| Block Kit approvals and streaming | Identical payloads and Web API calls in both modes; only the receiver differs (HTTPS POST + signature + 3 s 200, versus WebSocket envelope + `envelope_id` ack). Streaming (`chat.startStream/appendStream/stopStream`) is outbound Web API, so it is transport-independent; limits are 10 minutes total per stream, 12,000 characters, 50 tasks, `thread_ts` required outside session channels, `recipient_user_id`+`recipient_team_id` required in channels. (§7) |
| Runtime | `chat-surface.slack` is a Go plugin inside the kernel on `slack-go/slack` v0.31.0. slack-go merged `agents.sessions.*`, the three agent events and `authorizations` parsing in v0.30.0 (2026-10-04); streaming chunks since v0.23.0; `visible_to_user_ids` since v0.31.0. Bolt Python 1.30.0 and Bolt JS 5.1.0 `Assistant` helpers still call the legacy `assistant.threads.setStatus`, so a Bolt sidecar would buy nothing the kernel needs and would move tenant routing and approval authorization out of the kernel. (§8) |
| `assistant_view` deprecation | Announced 2026-08-20: deprecated February 2027; `agents.sessions.setStatus`/`rename` replace `assistant.threads.setStatus`/`setTitle`; compatibility bridge "for now". New apps can only use `agent_view` since 2026-06-30. We start on `agent_view` and the Agent Sessions API; nothing to migrate. (§2.5) |

## 1. What the earlier reports settled, and two corrections

Design inputs: the Go runtime and remote-process boundary (`plugin-architecture.md` §4), the `chat-surface` and `notifier` interfaces (§4.5), and the tenant ID constraint for Mimir `X-Scope-OrgID`. Current approval requirements come from the canonical record §2.2, not a chat SDK: writes fail closed without an approval; L3 requires two distinct verified platform users holding `approvals.decide`, neither the requester, re-checked at dispatch. Slack is an optional surface under §2.1 row 4.

Two corrections to `oncall-and-aiops-oss.md`:

1. §B.9 marked slack-go `agents.sessions.*` support as **UNVERIFIED whether merged**. It is merged: issue [slack-go/slack#1606](https://github.com/slack-go/slack/issues/1606) was closed 2026-09-23 by PR #1607, and the v0.30.0 CHANGELOG (2026-10-04) lists `SetAgentSessionStatus`, `RenameAgentSession`, `AppContextChangedEvent`, `AgentSessionStoppedEvent`, `AgentSessionTitleChangedEvent`, `Features.AgentView`/`AssistantView`, and `EventsAPICallbackEvent` now unmarshalling `authorizations` ([CHANGELOG](https://github.com/slack-go/slack/blob/master/CHANGELOG.md), checked 2026-10-27).
2. §B.10 recommended "Bolt (Python or JS) with `Assistant` class, Socket Mode default" as the chat-ops runtime. That recommendation predates the facts in §8: the Bolt `Assistant` helpers wrap the method being deprecated, and Socket Mode is the wrong default for the hosted tier. The runtime is slack-go in the kernel; Socket Mode is the self-host default only.

The 2026-08-20 changelog date and the February 2027 deprecation, both **UNVERIFIED** in that report, are now verified from the changelog entry itself (§2.5).

## 2. Slack platform facts (checked 2026-10-27 against docs.slack.dev unless noted)

### 2.1 Transports

### 2.2 Distribution and OAuth v2

- "OAuth allows a user in any Slack workspace to install your app." A non-distributed app "can only be installed on the workspace that owns it" (`invalid_team_for_non_distributed_app`). The `redirect_uri` must be HTTPS; the temporary `code` expires after ten minutes; a `state` mismatch must be treated as forgery. ([Installing with OAuth](https://docs.slack.dev/authentication/installing-with-oauth/))
- `oauth.v2.access` returns `access_token` (`xoxb-`), `bot_user_id`, `team.id`, `team.name`, `enterprise.id` (when the workspace is in an org), `authed_user.id`, `is_enterprise_install`; "The `team` property will be `null` for org-level installations where `is_enterprise_install: true`"; "Treat `team` as a hint rather than a guarantee"; "The `oauth.v2.access` response is the source of truth". Tokens "do not expire" unless token rotation is enabled (`settings.token_rotation_enabled`). Re-installs only add scopes; scopes cannot be downgraded. (same page; manifest reference)
- Socket Mode and OAuth combine: the Bolt JS repository ships `examples/socket-mode-oauth/app.js` with `socketMode: true`, `appToken`, `clientId`, `stateSecret` ([bolt-js examples](https://github.com/slackapi/bolt-js/tree/main/examples/socket-mode-oauth), checked 2026-10-27). The Bolt Python OAuth page states "Slack apps installed on multiple workspaces will need to implement OAuth" and that org-wide installs are supported since Bolt Python 1.1.0 ([Bolt Python OAuth](https://docs.slack.dev/tools/bolt-python/concepts/authenticating-oauth/)).

### 2.3 Enterprise Grid, shared channels and identity fields

- Org-ready apps: "The app has a single token that represents the permissions for the app on multiple workspaces, and is authorized once for an entire organization"; org admins then add it to workspaces without further authorization; `auth.teams.list` returns the approved workspaces; `team_access_granted`/`team_access_revoked` events track changes. ([Organization-ready apps](https://docs.slack.dev/enterprise/organization-ready-apps/), [Developing for Enterprise orgs](https://docs.slack.dev/enterprise/developing-for-enterprise-orgs/))
- Events: "The `authorizations` object is truncated at a single installation"; "We'll only send one event, regardless of how many workspaces within the organization your app is installed on"; the full list comes from `apps.event.authorizations.list` (app-level token in the header, scope `authorizations:read`, 600 requests/min per app per team, input `event_context`; returns `enterprise_id`, `team_id`, `user_id`, `is_bot`, and in the envelope also `is_enterprise_install`). The envelope carries `team_id`, `context_team_id`, `context_enterprise_id` ("the enterprise org through which your app is receiving the event (i.e., where the app is installed)"), `event_context`, and `is_ext_shared_channel`. ([Events API](https://docs.slack.dev/apis/events-api/), [apps.event.authorizations.list](https://docs.slack.dev/reference/methods/apps.event.authorizations.list/))
- Org tokens: "some API methods will require a `team_id` parameter to indicate which workspace to act on" (`conversations.list`, `users.list`, `conversations.create`, `files.list`, `users.conversations`, `usergroups.*`, search and team methods); "A safe option is to always pass a `team_id` parameter"; for channel-argument methods such as `chat.postMessage` the optional `client_context_team_id` field exists; a single-workspace channel queried through an org token returns `team_access_not_granted`. (Developing for Enterprise orgs)
- User IDs: "Within an Enterprise org, all users have a single, global ID beginning with either the letter `U` or `W`"; "The specific prefix does not indicate anything in particular"; `migration.exchange` maps pre-migration local IDs to global ones. Outside a Grid, user IDs are per workspace. (same page)
- Slack Connect: "there is no single property to substantiate if the user is external or not"; deduce it from `is_stranger` on `users.info` and from the user's `team` differing from the installing team; use `is_ext_shared` (not `is_shared`) on the conversation; "Slash commands and message actions are not shared — they are limited only to the team that has installed the app"; for interactive messages from other teams, "let them know if an action is not permissible due to their external nature"; "your app should default to exposing less information in shared channels". ([Slack Connect](https://docs.slack.dev/apis/slack-connect/))
- `block_actions` payload: `user` (`id`, `username`, `team_id`), `team` ("The workspace the app is installed on. Null if the app is org-installed."), `enterprise`, `api_app_id`, `container` (`message_ts`, `channel_id`, `is_ephemeral`), `channel`, `message`, `actions[]` (`block_id`, `action_id`, `value`, `action_ts`), `trigger_id`, `response_url`. ([block_actions payload](https://docs.slack.dev/reference/interaction-payloads/block_actions-payload/)). A bolt-js issue reports that `user.team_id` in a Grid may not reflect the originating workspace — **UNVERIFIED**, [bolt-js#1875](https://github.com/slackapi/bolt-js/issues/1875); the envelope `team_id`/`authorizations` is the field to route on regardless.
- Slash command payload: `team_id`, `team_domain`, `enterprise_id`, `enterprise_name` (only in an org), `channel_id`, `user_id`, `command`, `text`, `response_url`, `trigger_id`, `api_app_id`; `token` is deprecated; 200 within 3,000 ms or the user sees `operation_timeout`; "Slash commands are not namespaced" — a name collision means "Slack will always invoke the one that was installed most recently"; once created, "any channel or workspace where your app is installed will immediately be able to start using it". ([Slash commands](https://docs.slack.dev/interactivity/implementing-slash-commands/))

### 2.4 Interactivity rules

- "All apps must, as a minimum, acknowledge the receipt of a valid interaction payload" with HTTP 200 "within 3 seconds"; `response_url` "can be sent up to 5 times within 30 minutes"; `replace_original: true` edits the original message; `chat.update` for non-ephemeral messages; `trigger_id` expires in three seconds and is single use. ([Handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction/))
- Button element: `style` `primary`/`danger`, `confirm` dialog, `value` ≤ 2000 chars, `action_id` ≤ 255, and `visible_to_user_ids` — "An array of user IDs for which the button appears. If not provided, the button is visible to all users." ([Button element](https://docs.slack.dev/reference/block-kit/block-elements/button-element/)). The page documents visibility, not server-side click enforcement, so the app must still authorize every click.

### 2.5 Agents, sessions, streaming, deprecation

- 2026-06-30 "Introducing the Agent messaging experience": `agent_view` ("agent conversations now look & feel the same as a regular direct message"); `assistant_view` ("separate Chat and History tabs"); "New apps can only use the Agent messaging experience"; requires "Slack CLI v4.4.0, Python SDK v3.43.0 with Bolt Python v1.29.0, and @slack/web-api@7.18.0"; `app_home_opened` (tab `messages`) replaces `assistant_thread_started` as the DM-open signal; `thread_ts` no longer required for suggested prompts. ([changelog 2026-06-30](https://docs.slack.dev/changelog/2026/06/30/agent-messages-tab/))
- 2026-08-20 "The next wave of Agent messaging experience": "The Assistant messaging experience (`assistant_view`) will be deprecated in February 2027"; `agents.sessions.setStatus` and `agents.sessions.rename` "replace the `assistant.threads.setStatus` and `assistant.threads.setTitle` API methods, respectively"; "For now, your existing calls keep working through a compatibility bridge"; new thread features "including multi-agent stacking, thread naming, a revamped thinking UI, and a native stop button for agent streams"; `agent_session_stopped` event. ([changelog 2026-08-20](https://docs.slack.dev/changelog/2026/08/20/agent-updates/)). Manifest reference adds: "Switching an app from `assistant_view` to `agent_view` cannot be reversed."
- Agent sessions: "thread-based and scoped to a single thread"; statuses `processing`, `active`, `suspended` ("the agent needs clarification, a decision, or a tool approval"), `closed`; "Sessions in the `processing` status time out after one hour and automatically transition to `active`"; the stop button appears only when the app subscribes to `agent_session_stopped`, otherwise `setStatus` warns `missing_agent_session_stopped_event_subscription`; "The session status will not update automatically when the user clicks stop"; `agent_session_stopped` carries `streaming_message_ts` (empty array when no stream); users may rename a session at any time (`agent_session_title_changed`); "Only apps declared as agents in the app settings can create sessions"; declaring adds `assistant:write`; `chat:write` manages thread sessions; `chat:write.customize` for `username`/`icon_emoji`/`icon_url`. `agents.sessions.setStatus`: Tier 3, `channel_id` required for public channels, `thread_ts` required for thread sessions, `title` ≤ 200 chars and `initiator_user_id` on creation; errors include `feature_disabled` ("The agent tasks feature is not enabled for this workspace") and `enterprise_is_restricted`. ([Agent sessions](https://docs.slack.dev/ai/agent-sessions/), [agents.sessions.setStatus](https://docs.slack.dev/reference/methods/agents.sessions.setStatus/), [Developing agents](https://docs.slack.dev/ai/developing-agents/))
- Streaming: `chat.startStream` needs `chat:write`, Tier 2 (20+/min); "A stream can stay open for up to 10 minutes … a limit on the stream's total duration, not an idle timeout"; on timeout content is saved, pending tasks become `error`, the session goes `active`, later calls return `message_not_in_streaming_state`; `thread_ts` omitted "is only supported in channels where the whole channel is one session, such as Slack Code", else `invalid_thread_ts`; `recipient_user_id` and `recipient_team_id` "Required when streaming to channels"; lifetime limits 12,000 chars of `markdown_text` across all calls, 50 tasks, 50 sources per task, 50 blocks; `markdown_text` and `chunks` cannot be mixed (`streaming_mode_mismatch`); chunk types `markdown_text`, `task_update` (`pending|in_progress|complete|error`), `plan_update`, `blocks`; `task_display_mode` `timeline`|`plan`; "Only the app that started a stream can append to or stop it"; `chat.stopStream` takes `session_status` (default `active`); starting a stream creates the session and sets `processing`; errors `message_limit_exceeded` (free-plan usage limit), `messages_tab_disabled`, `channel_type_not_supported`. ([chat.startStream](https://docs.slack.dev/reference/methods/chat.startStream/), Agent sessions page)
- "Developing and using some AI features require a paid plan, despite being visible in the app settings on any plan." ([Developing agents](https://docs.slack.dev/ai/developing-agents/))
- No official construct for several agents or personas inside one app was found; "multi-agent stacking" refers to several apps in one thread; the documented way to get distinct agent identities is one app per agent (search of docs.slack.dev 2026-10-27; absence of a feature is **UNVERIFIED** by nature).

### 2.6 Rate limits that shape the design

- Web API: tiers "per API method per workspace/team per app"; Tier 1 "1+ per minute", Tier 2 "20+", Tier 3 "50+", Tier 4 "100+"; posting "generally allows posting one message per second per channel, while also maintaining a workspace-wide limit"; HTTP 429 with `Retry-After` seconds; design for 1 request/second per method. ([Rate limits](https://docs.slack.dev/apis/web-api/rate-limits/))
- Non-Marketplace throttle (2025-05-29): `conversations.history` and `conversations.replies` move "from `Tier 3` to `Tier 1`" for "applications that are commercially distributed outside of the Marketplace (also called 'unlisted' apps)": "1 request per minute and will return a maximum of 15 objects per request"; "Internal customer-built applications are not impacted by these changes" (they keep 50+/min and 1,000 objects); "This change will not impact Marketplace apps"; new apps and net-new installs affected "immediately, as of May 29, 2025"; the current page says existing installations are not impacted. ([changelog 2025-05-29](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/)). Third-party posts claim an enforcement date of 2026-03-03 for existing installs — **UNVERIFIED**, not on the official page as fetched 2026-10-27.
- Marketplace review: the app must already be installed on "10 or more active workspaces" (used in the past 28 days), review of each requested scope, no scope requested for unbuilt features, functional review "up to 10 weeks", and once published "the live version of your app is locked" (scope or redirect-URI changes need resubmission). ([Marketplace review guide](https://docs.slack.dev/slack-marketplace/slack-marketplace-review-guide/)). Whether token rotation is mandatory for listing: **UNVERIFIED** (not on the review-guide page).
- `users:read.email` is "now required to access the `email` field in user objects returned by the `users.list` and `users.info` web API methods" and "must be requested at the same time as `users:read`" ([users:read.email](https://docs.slack.dev/reference/scopes/users.read.email/)). Sign in with Slack is OpenID Connect at `https://slack.com/openid/connect/authorize`, scopes `openid`, `profile`, `email`, token exchange at `openid.connect.token`, ID-token claims `sub` (= user id), `https://slack.com/team_id`, `https://slack.com/user_id`, `email`, `email_verified`; OpenID scopes cannot be mixed with other scopes in one flow ([Sign in with Slack](https://docs.slack.dev/authentication/sign-in-with-slack/)). An `enterprise_id` claim is not shown on that page — **UNVERIFIED**.

## 3. Distribution model per deployment mode

| | Hosted multi-tenant (we operate, N customer workspaces) | Self-hosted (customer operates, usually one workspace or one Grid org) |
|---|---|---|
| Who owns the Slack app | We do: one app, "Distribute app" enabled, listed in the Marketplace once it has 10 active installs | The customer: created from our generated manifest in their own workspace or org; it is an "internal customer-built" app |
| Install flow | `GET /slack/install` (Add to Slack, `state` bound to the platform tenant and user) → `slack.com/oauth/v2/authorize` → `GET /slack/oauth/redirect` → `oauth.v2.access` → installation record written for the tenant that started the flow | Same code path with the customer's `client_id`/`client_secret`, or, for Socket Mode only, paste the `xoxb-` and `xapp-` tokens into the profile; the install is bound to the single tenant |
| Inbound transport | Events API: `POST /slack/events`, `/slack/interactive`, `/slack/commands` behind the public ingress; signature verification; 200 within 3 s; event queued to the `events` host service before processing | Socket Mode by default (`socket_mode_enabled: true`), one connection per kernel replica up to the 10-connection cap; Events API when the site has ingress and wants it |
| Why not the other transport | Socket Mode: Marketplace exclusion; unlisted commercially distributed app ⇒ 1 req/min, 15 objects on `conversations.replies`, which the agent needs for thread context; the 10 connections are shared across all N workspaces, so replicas and throughput are capped at 10 regardless of tenant count; single app-level token is a single blast radius | Events API: needs a public HTTPS URL, TLS, and the Slack IP space reachable — most on-prem sites do not want that for a chat bot; Socket Mode avoids request signing and ingress entirely |
| Token storage | Per installation: bot token, optional refresh token (`token_rotation_enabled` is a product decision, see §10), in the tenant-scoped `secrets` host service; signing secret and client secret are global to our app | Bot token, app-level token, signing secret (Events only) in the single tenant's secrets |
| Scopes (bot) | `app_mentions:read`, `chat:write`, `chat:write.customize`, `commands`, `im:history`, `im:write`, `channels:history` and `groups:history` (only if the tenant enables alert-thread reading), `users:read`, `users:read.email`, `assistant:write` (added by declaring the agent); `authorizations:read` on the app-level token for `apps.event.authorizations.list` | Same manifest; the customer can trim read scopes |
| Grid | Support org-wide installs from day one (`settings.org_deploy_enabled` is not required for this; the "Org Level Apps" switch is); installation keyed by `enterprise_id` when `is_enterprise_install`; `team_id` passed on every workspace-scoped call | Same; Socket Mode is allowed for org-wide enterprise deployment |

The chat-surface plugin therefore ships two receivers behind one handler core, exactly the two rows already named in `plugin-architecture.md` §4.5: `chat-surface.slack-events` and `chat-surface.slack-socket-mode`. The `hosted-multi-tenant` profile composes the first, `lgtm-self-host` and `single-node` the second, and a site patch can swap them. Both receivers emit the same normalized `InboundEnvelope{installation, actor, surface, payload}`; everything after the receiver (routing, identity, approvals, sessions, streaming) is transport-agnostic and is what the conformance suite tests with recorded Slack fixtures (`fixtures/chat-surface/slack/*.yaml`, replay-strict as in `plugin-architecture.md` §4.7).

## 4. Mapping Slack installations to platform tenants

Entity: `slack_installation` — `installation_id` (ours), `enterprise_id` (nullable), `team_id` (nullable for org installs), `is_enterprise_install`, `bot_user_id`, `app_id`, `installed_by_slack_user_id`, `tenant_id`, `created_at`, `revoked_at`. Unique on `(app_id, coalesce(enterprise_id,''), coalesce(team_id,''))`. The `team: null` org-install case from `oauth.v2.access` is keyed by `enterprise.id` alone; workspaces inside that org are discovered with `auth.teams.list` and recorded in `slack_installation_workspace(installation_id, team_id)` so routing can resolve a workspace event to the org installation.

Mapping rules:

1. **Default: one installation → one tenant.** The tenant is the one whose user clicked Add to Slack (carried in `state`), never derived from the Slack payload. The platform tenant ID stays ours (DNS-label subset per `plugin-architecture.md` §5) and is *not* the Slack `T…`/`E…` ID.
2. **Several workspaces → one tenant** is allowed (a customer with two workspaces, or one org install covering many workspaces). The reverse, **one workspace → several tenants** (prod/staging tenants, one Slack), is resolved by `slack_channel_binding(installation_id, channel_id) → tenant_id, default_pillar, policy_overrides`. A message in an unbound channel uses the installation's default tenant. DMs with the bot use the default tenant unless the user picks one with `/aiops tenant <id>`, stored per `(installation_id, user_id)`.
3. **Routing key is `authorizations[0]`**, not the inner `event.team` and not the envelope `team_id`: the envelope `team_id` is the workspace where the event occurred, which in a Slack Connect channel can be the *other* company's workspace; `authorizations[0].{enterprise_id,team_id}` is an installation of ours that can see the event. When the envelope has `is_ext_shared_channel: true` and more than one of our installations could be involved (two customers sharing a channel), call `apps.event.authorizations.list` with `event_context` and process the event once per installation whose tenant has opted in; default policy is to ignore messages in externally shared channels unless the channel is explicitly bound.
4. **Org tokens always pass `team_id`** (or `client_context_team_id` on message methods) taken from the envelope, as the Enterprise doc advises; the Web API client pool is keyed by `installation_id` and the call wrapper injects it.
5. **Uninstall**: `app_uninstalled` and `tokens_revoked` events mark the installation revoked and revoke the tenant-scoped secret; channel bindings and user links are kept for audit, disabled for routing.

Tenant isolation consequence for the hosted tier: Slack rate limits are "per API method per workspace per app", so one noisy tenant cannot consume another tenant's Slack budget, but the Events API 30,000/hour cap is per workspace too, so an alert storm in one customer only throttles that customer. The platform still needs tenant-scoped notification pacing before calls reach `chat.postMessage` at 1/s per channel. Paging is a separate class that no digest or pacing hook may withhold (canonical record §2.1 row 3 and §4.3).

## 5. Mapping Slack users to platform users and approval roles

Entity: `slack_user_link` — `installation_id`, `slack_user_id`, `platform_user_id`, `link_method` (`email` | `oidc` | `portal-confirm`), `linked_at`, `verified_for_approvals` (bool). Unique on `(installation_id, slack_user_id)` and on `(installation_id, platform_user_id)` so two Slack accounts cannot map to one platform user inside one installation, and one Slack account cannot map to two platform users. In a Grid org the Slack user ID is global, so links are keyed by the org installation and reused across its workspaces; outside a Grid the same human in two workspaces is two Slack IDs and two links to the same platform user, which is why uniqueness is per installation.

Linking, by assurance level:

| Role exercised from Slack | Link required | How |
|---|---|---|
| `chat.ask`, `incidents.view`, `report.view` (read, ask the agent) | `email` link, scoped to the installation | On first interaction call `users.info` (needs `users:read` + `users:read.email`), match the profile email against tenant members; the workspace admin controls both sides, so the match is intra-tenant by construction |
| `incidents.act`, `feedback.submit` | same | same |
| `approvals.decide` (release a gated action), `members.manage`, any L2/L3 decision | `oidc` or `portal-confirm`, `verified_for_approvals = true` | Button "Link my Slack account" opens Sign in with Slack (OpenID Connect; separate flow from the bot OAuth); the kernel verifies the ID token, checks `https://slack.com/team_id` matches the installation and `sub` matches the clicking user, and binds to the currently logged-in platform user. Alternative without OIDC: the platform user confirms the pending Slack link once in the portal. Tenant policy `slack.approvals.require_verified_link: true` by default |
| External user (Slack Connect: `users.info` `is_stranger: true`, or `user.team` ≠ installation team and not in the org's `auth.teams.list`) | never linked | May read what the channel policy allows; every interactive click is answered with an ephemeral "not permitted for external members" and logged |

Approval evaluation belongs to the platform's `approval` provider, not the Slack surface. The surface submits `Decision{approval_id, platform_user_id, verdict, source: slack, installation_id, slack_user_id, action_ts}` for server-side authorization. Under the canonical record §2.2, **L3 requires two distinct verified platform users holding `approvals.decide`, neither the requester, re-checked at dispatch**. Quorum counts platform users, so two Slack identities linked to one platform user cannot supply two votes. The canonical record §2.1 row 4 requires Sign in with Slack linking for approval.

Slack-side hardening that costs nothing: set `visible_to_user_ids` on Approve/Deny buttons to the linked Slack IDs of the tenant's `approvals.decide` holders (slack-go v0.31.0 `ButtonBlockElement.VisibleToUserIDs`), add a `confirm` dialog on Approve, encode only `approval_id` plus a random nonce in `value` (never the action itself; the server resolves the request and checks the approved plan digest under the canonical record §2.2), treat `action_ts` + `approval_id` as an idempotency key, and after the decision `chat.update` the message to show who decided and when. `response_url` (5 uses, 30 minutes) is used only for the immediate ephemeral acknowledgement; the authoritative edit is `chat.update` with the stored `channel`/`message_ts`.

## 6. Addressing per-pillar agents

Options evaluated against the Slack facts:

| Option | What Slack gives | Cost | Verdict |
|---|---|---|---|
| A. One app per pillar (7 apps) | Distinct bot identity, distinct agent entry in "Agents & Tools", native per-agent sessions; "multi-agent stacking" lets several of them answer in one thread | 7 OAuth installs per tenant, 7 Marketplace listings each needing 10 active workspaces, 7 token sets, 7× the per-workspace event quota (a plus), slash command names must not collide; hosted onboarding becomes a 7-click ritual | Optional self-host configuration only |
| B. One app, one bot, pillar as routing | One install, one agent, one `/aiops` command; sessions are per thread, and a thread stays with the pillar that opened it | Pillar must be inferred or stated; one identity in the sidebar | **Default** |
| C. One app with sub-agents exposed as personas | Not a Slack construct (no manifest field, nothing on docs.slack.dev as of 2026-10-27) | — | Not available |

Routing order inside the `router` component for option B, first match wins: (1) explicit pillar in a slash command `/aiops <pillar> <question>` or in a mention `@aiops <pillar> …`; (2) thread stickiness: the thread already holds a session created by a pillar (stored in `slack_thread_session(installation_id, channel_id, thread_ts) → tenant_id, pillar, session_state`); (3) channel binding `default_pillar` (an `#alerts-prod` channel bound to `incident`, a `#finops` channel bound to `finops`); (4) DM default pillar from the user's last choice; (5) otherwise a cheap LLM intent classifier over the seven pillar descriptions, with the chosen pillar echoed in the reply header so the user can correct it. Pillar persona is shown with `username` and `icon_emoji` overrides on `chat.postMessage` and `chat.startStream` (`chat:write.customize`), and the session title is set to `[<pillar>] <summary>` with `agents.sessions.rename`.

Slash command surface: one command `/aiops` with sub-verbs `ask`, `incident`, `change`, `compliance`, `secops`, `finops`, `improve`, `report`, `oncall who|ack|page`, `tenant`, `link`, `status`. A single command avoids the non-namespaced collision rule and keeps the manifest small; the `oncall` verbs call the `on-call-provider` extension point from `plugin-architecture.md` §4.5. Slash commands never fire from external Slack Connect members (Slack limits them to the installing team), so they are the safest entry point for write verbs.

Pillar agents are Python `investigator` plugins over gRPC; the chat plugin never calls an LLM itself. It translates one Slack turn into one `Investigate` (or `Ask`) call with `ToolSet` scoped to the tenant's permissions for that user, and renders the server-streamed `Finding` stream into the Slack session (§7).

## 7. Block Kit approvals and streaming under each mode

Both transports deliver the same `block_actions`, `view_submission`, `slash_commands` and `event_callback` payloads; the difference is only the acknowledgement discipline:

| Concern | Events API receiver | Socket Mode receiver |
|---|---|---|
| Ack | HTTP 200 within 3 s before any work; retry dedup on `event_id`/`event_context` and `x-slack-retry-num`; return `x-slack-no-retry: 1` for events we deliberately drop | Send `{"envelope_id"}` immediately; for slash commands and interactive envelopes the ack may carry the response payload (`accepts_response_payload: true`) |
| Approval button click | Verify signature, ack, enqueue `Decision`, reply ephemeral via `response_url`, then `chat.update` | Ack with the ephemeral text in the payload, enqueue `Decision`, then `chat.update` |
| Modal (optional command-review UI) | `trigger_id` must be used within 3 s of the click, so `views.open` is called inside the handler before the ack completes | same; the `trigger_id` is in the envelope |
| Failure mode | Slack retries 3× and disables the subscription above 95 % failure; the receiver must stay a thin, always-200 shim in front of the `events` bus | Connection refreshes every few hours; the client reconnects (slack-go `socketmode` reconnects with backoff, 5-minute cap since v0.30.0); at most 10 replicas |

Streaming is a sequence of outbound Web API calls and is identical in both modes. Design rules derived from the limits in §2.5:

1. On an inbound question: `agents.sessions.setStatus(processing)` (creates the session if the thread has none), subscribe to `agent_session_stopped` so the user gets a stop button; on `agent_session_stopped` cancel the gRPC `Investigate` context and `chat.stopStream` with `session_status: active`.
2. Stream only the final answer, not the whole investigation: `chat.startStream` → `appendStream` chunks → `stopStream`. The 10-minute total cap and the 12,000-character cap are below what a long investigation produces, so intermediate findings are posted as separate `chat.postMessage` replies in the thread (one per finding, `task_update`-style blocks), and the stream carries the summary. If a stream must run longer, close it and open a new one; never rely on the stream to stay open.
3. `thread_ts` is always set (sessions are thread-based; top-level streams are for Slack Code channels only); in channels pass `recipient_user_id` (the asking user) and `recipient_team_id` (the envelope `team_id`).
4. Fallback ladder when streaming is unavailable: `feature_disabled` / `messages_tab_disabled` / `message_limit_exceeded` / `enterprise_is_restricted` → `chat.postMessage` once, then `chat.update` every ~2 s with the accumulated text (respecting 1 message/s per channel), final `chat.update`; the `Capabilities()` of the plugin reports `streaming: false` for that installation so the pillar can shorten its answer.
5. Suspended, not active, while waiting on an approval: when a pillar emits an `ApprovalRequired` finding, post the Block Kit approval message (§5) and set the session `suspended`; on decision set `processing` again and resume. This is a presentation state; the platform's approval provider remains the authority.
6. Re-arm the one-hour `processing` timer for long runs by calling `setStatus(processing)` again from the pillar's keep-alive ticks.

Decision: implement `chat-surface.slack` in Go with slack-go, in-process in the kernel, as `plugin-architecture.md` §4.5 already lists (`inproc`). Reasons, in order of weight:

1. Everything that makes the Slack surface safe is kernel policy: installation → tenant routing, user → platform-user linking, `approvals.decide` checks, L3 quorum, external-user rejection, per-tenant digesting, audit. A Bolt sidecar would have to call back into the kernel over gRPC for every one of these on every message, or re-implement them in Python; both are worse than reading them from the host services the plugin already gets (`tenant`, `secrets`, `events`, `store.sql`, `http.router`).
2. The framework value of Bolt is thin for us and partly stale: the `Assistant` helpers wrap the method being deprecated in February 2027, so a Bolt app targeting the Agent Sessions API drops to the raw Web API client anyway. The OAuth routes and installation store are ~300 lines in Go against `oauth.v2.access` and our Postgres.
3. The hosted tier needs an HTTP receiver behind the same ingress, TLS and signature verification as the rest of the control plane, and the self-host tier needs a WebSocket client that shares the kernel's reconnect, metrics and leader election. slack-go provides both transports; a sidecar would duplicate ingress and health plumbing.
4. Failure containment, the one argument for a sidecar in the §3 decision matrix, is weak here: the Slack plugin does no LLM work and no untrusted code; a panic is recovered at the kernel boundary and marks the row `Failed` without touching other tenants' rows.
5. Contributor path stays open: a Teams or Mattermost `chat-surface` can still be a gRPC plugin in any language; the Go interface and proto are the same, and the conformance suite (`conformance/chat-surface/`: envelope normalization, 3-second ack, retry dedup, identity rejection for external users, approval idempotency) runs over both runtimes.

Risks to record: slack-go has shipped breaking changes in consecutive minor releases (Go 1.26 floor and signature changes in v0.30.0, struct comparability in v0.31.0) — pin and vendor, run its examples in CI; it is a volunteer project (BSD-2), so the kernel should keep its own thin `slackapi` interface so a library replacement is local to one package. Bolt Python remains the right choice for a self-hoster who wants to script their own bot against our REST/MCP API; that is outside the platform.

## 10. Open questions

1. Token rotation for the hosted app: Slack's review guide does not mention it as a listing requirement (**UNVERIFIED** either way); enabling it later is possible per manifest, but it changes the installation store schema (refresh token, expiry). Decide before the first customer install.
2. Should hosted tenants be allowed to bring their own Slack app (customer-owned app, our hosted kernel) to escape the Marketplace dependency during the first months before we reach 10 active installs? It is the self-host code path pointed at the hosted kernel, so it is cheap; the question is support policy.
3. Slack Connect channels shared between two of our customers: process once per opted-in installation (fan-out) or refuse entirely? Default proposed: refuse unless bound.
4. Whether Grafana-side identity (Grafana org user) or the platform OIDC user is the `platform_user_id` for self-hosted sites that run the "aiops-only" profile without our portal; affects where the Sign in with Slack link lands.
5. Per-pillar separate apps as a supported self-host option (§6 option A): worth the installation-store `pillar_filter` field now, or defer until requested?
6. Streaming budget: whether to always stream the final answer (Tier 2, 20+/min per workspace for `chat.startStream`) or only when the answer exceeds N characters; alert storms with many simultaneous questions could hit the tier.
