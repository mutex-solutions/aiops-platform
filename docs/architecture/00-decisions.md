## 1. Product definition and principles

**Product.** aiops-platform is an Apache-2.0 AIOps platform on the Grafana observability stack, on-prem and open-source first. The end goal is a plugin marketplace where users contribute and sell plugins to each other, which is why the design follows dsh. Phase 1 is the community edition, the subject of this file; the marketplace with billing is a later enterprise edition and is not built, and the boundary between the two is an open owner decision (ADR-049). The Grafana stack is first-party and the default, not a contract: other observability systems are reached through connector packs that a contributor can write and contribute back (§6.2). The parts:

- **Agent.** One agent per customer host or cluster: unmodified Grafana Alloy plus our installer, enrolment and served config, writing metrics, logs, traces, profiles and eBPF signals through our tenant gateway into Mimir, Loki, Tempo and Pyroscope.
- **Kernel.** One Go control-plane binary (`aiops`) that ingests alerts, opens incidents, investigates them with an agent harness, pages the on-call person, runs approved changes, and serves chat-ops and dashboards (provisioned dashboards from P1, a dashboard app plugin as an optional bundle in P2). It is built on a Go port of the Cordis model, the kernel of DeepSeek Harness (dsh): every feature is a plugin behind a service definition, composed from a profile, and a provider restarts in place in every profile (§2.1 row 1). Its features are organised as seven pillars: Incident, Change, Compliance, SecOps, FinOps, Continuous Improvement and Executive Reporting.
- **Profiles.** One binary, composed four ways: `hosted` (multi-tenant, run by us), `self-host-full` (customer runs the whole stack), `aiops-only` (kernel against the customer's own observability systems) and `dev` (laptop and demo).
- **Target estate.** P1 and P2 cover Kubernetes clusters and Linux hosts on virtual machines or bare metal, and from P2 network devices polled over SNMP. Hypervisors, hardware health and self-hosted databases enter on named triggers (§7.3). Cloud inputs are optional later rows. No row in `self-host-full` needs a public cloud provider API. A chat service, an external on-call engine, a paging carrier and a hosted model are optional bindings: with none bound the loop runs through the API and `aiopsctl`, email or webhook paging and a local model endpoint.
- **Estate model.** An open vocabulary, rule table and export of the customer estate, published as files (§2.1 row 15).

Out of scope: our own telemetry store or lakehouse (product scope, §1), a configuration database of our own (the estate of row 15 is a projection rebuilt from its sources), a rule evaluator of our own, a triple store or ontology server at runtime, SSH or a shell from the kernel or any harness, our own IdP, a portal SPA, status pages, a second SQL engine (§2.4 W2), and any modified Grafana or backend build.

**Principles.** Every later document is checked against these nine rules.

1. **Profiles, not products.** Every surface is a profile of ordered bundles over one binary. Hosted, self-host, aiops-only and dev differ only in which rows are composed, and anything that works in only one profile is a bug unless a profile row says so (dsh-architecture §7, §8.1).
2. **A plugin that cannot be tested alone is not a plugin.** The kernel ships in the SDK, so a Go plugin is tested on the real runtime with fakes of the services around it, and a non-Go plugin is driven by the same kernel inside `aiopsctl`. No fake host exists. Every provider and contribution also passes the conformance suite of its definition in every runtime it ships in, and a real-composition boot of the built binary (§4.5; plugin record §14).
3. **A seam exists when a consumer does.** Every service that another plugin calls, the launch services included, has a definition with three roles that must all exist (definition, provider, consumer), a fake and a conformance suite that the fake passes. The fake is the second implementation from the first day, with one stated exception: the `sql` fake is the same engine in a throwaway schema, because the contract is a PostgreSQL dialect (§2.4 W2). A plugin that nobody calls has no definition (§4.1; plugin record §1, §5).
4. **The ingest path never depends on the kernel.** Agents write through a stateless gateway with short-lived JWTs, and token issuance is the only control-plane call on the ingest SLO (gap-tenant-gateway §1.1).
5. **Policy is an invariant of the plugin that owns the seam.** The approval floor, change ledger, credential leases, quorum, audit chain and PII scrub are first-party plugins. The kernel makes each of them impossible to shadow and its privileged keys impossible to inject without a binding, and a consumer cannot exist without its provider, so absence is closed. The kernel holds no policy (§4.2; plugin record §7).
6. **Shared fate is a budget.** Code or commands a model wrote, and any third-party harness, run out of process. The first-party loop executes only typed read tools through the `tools` dispatcher, under caps, a deadline and a breaker, and runs in process, as the kernel-data tools do (§2.4 W12). Third-party code runs out of process in hosted, one instance per tenant, as remote contributions only (§2.4 W4); on self-host it may also enter the process, through a distribution the operator builds and signs (§2.4 W3). In-process Go is trusted code, not a sandbox. An upstream process with unauthenticated admin endpoints or a single-tenant design runs one instance per tenant in a multi-tenant profile; its plugin manifest says so, and no default bundle carries such a process. First-party executors run only typed plans under a lease that `credential-lease` mints, so they run in process in every profile until the first third-party executor or ADR-016 needs otherwise (§2.1 row 1).
7. **Unmodified upstream behind a service boundary.** We render configuration for every upstream process a composed bundle deploys (by default the agent, the four stores, the dashboard server, the tenant gateway proxy and the object store), each listed once in the upstream register (§3.2). They remain unmodified separate processes, and we link none of their AGPL code (licence record §7.3). The default stack is a choice of bundles, not of contracts: no row outside a connector pack or a stack bundle holds a query string or calls a telemetry store's query API, and payload parsers are `signals` contributions (§4.1; CI checks it on the static graph).
8. **Operator-visible means logged, and "later" means a named trigger.** Every state change is an outbox event written in the same transaction. Every deferral carries a trigger in §7.3 and a `ponytail:` comment at the code seam.
9. **An upstream is a plugin, never the product.** Every upstream (a process, a library, a service, content or a contract) enters through one provider or contribution behind a definition whose fake and suite name no upstream, and lives in its own bundle, a connector pack or a stack bundle. Nothing in the core names or needs one, and removing any one upstream plugin leaves a binary that builds and boots every shipped profile (§4.3; harness record §7).

### 2.3 Where this record departs from the research

- **gap-tenant-gateway §1.4.** Argon2id for agent secrets is replaced by a plain SHA-256 hash: the secret is 256-bit random, not a password, so it needs neither key stretching nor a server key. §1.4 must be amended (ADR-001).
- **gap-ebpf §1.** The "second Tetragon DaemonSet in the bundle" is deferred until SecOps has a consumer.
- **oncall-and-aiops-oss §B.3.** Falco is replaced by Tetragon (gap-ebpf §3.2).
- **oncall-and-aiops-oss §B.9 and §B.10.** Bolt is replaced by slack-go, as gap-slack §1 already corrected.
- **gap-kernel-hot-path §4.2.** Superseded by the second amendment of 2026-11-11: the default provider is first-party and GoAlert is an optional provider plugin (§2.1 row 3). Opsgenie's service ends 2027-04-05 (licence record §2.4), so its row is dropped.
- **plugin-architecture §0, §3, §4 (superseded by the plugin record).** The compile-time `init()` registry, the lifecycle `Validate`, `Provision`, `Start`, `Health`, `Shutdown`, point guards in a plugin host, the fake host, the fixed boot order and restart-only layers are withdrawn: the registry is a generated module table, the lifecycle is one `Apply` whose registrations are effects, a guard is the dispatcher of a registry, and a plugin is tested on the real kernel. `store`, `scheduler` and `events` are not single-implementation packages: `sql`, `kv`, `blob`, `jobs` and `events` are definitions, each with a fake and a suite. `sql` has one allowed provider because the contract is a PostgreSQL dialect; `events-nats` is the planned second relay (ADR-007). Protos and remote adapters are written with each contribution definition, not with a point's first out-of-process row, and the Python SDK ships at S2b. `notifier-sms-twilio` and `notifier-push-ntfy` are dropped as first-party rows and stay open to contribution. `on-call-provider-builtin` is no longer trigger-based (§2.1 row 3).
- **plugin-architecture §4.6.** Profile renames: `single-node` becomes `dev`, which is dev and demo only and not a production tier (single replicas, demo credentials). It runs PostgreSQL, not SQLite, because River on SQLite is experimental (gap-kernel-hot-path §2.4). Tiny estates run `self-host-full` on one VM.
- **gap-kernel-hot-path §2.4.** River Pro is not an upgrade path for fairness: it is a paid add-on, and no row may need one (08 §5.1 L9). The kernel token bucket stays, with `events-nats` (Apache-2.0) as the only other option.
- **gap-kernel-hot-path §3.2 item 3.** A tenant admin maps to the Grafana Editor role, not Org Admin, and tenant data sources are provisioned read-only, because an Org Admin can create a data source with any URL and an `X-Scope-OrgID` header of its choice (§5.7).
- **gap-kernel-hot-path §2.5.** MVP correlation is fingerprint and a join on the typed correlation key (row 16) in the `correlate` plugin, with storm mode as the `storm-mode` row. `topology-fold`, `change-window-fold` and `shared-alertname-fold` wait for a measured trigger (§7.3).
- **hosted-sre §2.8 (not adopted).** Its reason for org-API provisioning is wrong. `org_mapping` is unavailable only on Grafana Cloud and works on our OSS pools (gap-kernel-hot-path §3.2 item 6). We provision through the org API because the kernel owns tenant membership.
- **dsh-architecture (the Cordis pin, the epoch, and the properties adapted or not carried).** The reference is the installed package: dsh 0.2.2-rc.1, Cordis 4.1.0 and cordis-plugin-loader 1.1.0, all MIT. Those two versions exist only as the `@deepseek-ai` packages published from the harness repository (upstream Cordis 4.0.0-rc.11 and plugin-loader 1.0.0-rc.8 plus the dsh modifications), so the port carries two MIT notices (licence record §2.1). The research note describes Cordis 4.0.5 and is wrong on the epoch, which derives from the provision uid, so a provider swap restarts its consumers; the note is corrected under ADR-035, and the port carries the MIT attribution (08 §5.1 L12). Of 63 dsh properties, 21 are carried as is, 23 adapted and 11 not carried, and 8 are added (plugin record §15). No adaptation is argued from schedule; each is forced by a multi-tenant, multi-replica Go server. Notably: every hook dispatch names its audience instead of `Context.filter`, and `global` is not carried, because one tenant's payload must not reach another tenant's listener. `ctx.get` is not carried, since an optional read is a check-then-use race in Go; a `When` sub-fiber is the only optional form. Listener order is by declared stage and then plugin id, not by registration. `!!js` expressions are replaced by `roles`, a row-level `inject` and closed references. Code is not imported or replaced at run time: in-process code enters by the module table and a new binary. A remote plugin is a set of contributions, not a first-class fiber. Provider-bound and consumer-bound keys limit "any provider can be swapped" and "any plugin may inject any service". The plugin manager is not an agent tool. A live recomposition repeats the required audit and can roll back.

## 4. Service definitions, rows and tests

### 4.1 Service-definition catalogue

- **Definition.** A key, an interface and a version, in `sdk/def/<name>/v<N>` with `fake/` and `conformance/`. A singular key is one engine or policy. A plural key is a registry of contributions: a contribution is registered through the registry and provided under no key, so only the registry's dispatcher can call it. A definition lands with its first consumer, carries its own `major.minor` version in `definition.yaml`, and is `v0` until a release review promotes it (§4.3). A plugin imports definitions and never a provider. Definitions replace the extension points, seams, packages, host services and kernel rows of round 1 (detail: plugin record §4 to §8, §14).
- **Plugin.** One value from `plugin.Define(Spec[C])`: `ID`, `Inject`, `Provides`, `Hooks`, `Durable`, `Validate` and `Apply`. `Apply` is the only entry point, and everything it registers (a provision, a route, a job handler, a listener, a goroutine) is an effect of the caller's fiber, reverted in strict reverse order after a quiesce step. There is no lifecycle interface. `plugin.yaml` holds what the launcher and the gate read without running code: hand-written, in manifest schema 1.0, `manifestVersion`, `id`, `version`, `title`, `description`, `license` (SPDX), `publisher` (its `id` equals the owner segment of the plugin id; `name` and `url` may stay empty until the enterprise edition uses them), `source`, `support`, `stability`, `scope` (`process`, `tenant` or both), `runtimes` (an empty list for a pack with no code), `capabilities`, `integrates` and `instantiable` (§6.2); generated from the `Spec`, with CI failing on a difference, `uses`, `provides`, `registers`, `hooks`, `configSchema`, `durable` and `requires` (§4.3). The schema is frozen-additive from the release that first ships it. It has no edition, entitlement, price or verification field: the enterprise edition adds what it needs with a manifest major, which a community kernel refuses by gate check 1.
- **Columns.** *Class* is provider class, then consumer class: `P` provider-bound, `C` consumer-bound, `s` consumer signed, `-` open (§4.2). *Tenant* says how tenant data is reached: `handle` (from the call's tenant handle), `bound` (a `.Bound` view exists in tenant trees), `ctx` (a tenant-scope plugin uses the process key with its tree's context), blank (none); §5.1. *Remote*: `contrib` (a third party can contribute from another process; the step or phase is when the adapter ships), `callback` (a remote plugin may call it), `no`. Consumers, fakes and the two toy registries of S2a (`examples/echoers`, `examples/stampers`) are listed in plugin record §5.

### 4.2 Key classes and the fail-closed argument

A provider-bound key is one whose replacement inside a subtree, or by a layer, would remove a fence. `Provide` on it succeeds only for a module-table entry in the allowed set of the signed distribution manifest; there is one provider, no `Isolate` and no `Want`. An entry is the registered `Plugin` value, never an id a plugin declares about itself. A consumer-bound key resolves only for the entries the manifest lists: `platformSql`, `sqlDriver`, `tokens`, `kek`, `loader`, `reload`, `pluginManager`, `tenantMint`, `credentials`, `durablePurge`, `appExit`. A `signed` key (`identities`, `approval`, `gateway`) is injected only by first-party plugins or by an in-process plugin whose signer `trust.yaml` trusts for it. Every other key is open and can be swapped or isolated by composition. The kernel checks the class and knows nothing of what a key means.

- **Pluggable for a bound key.** Where the allowed set has more than one entry (`kek`, `events`), layers 1 to 4 choose by the row they enable; the tenant layer never does. Beyond the set, a provider or consumer enters by distribution manifest: on self-host the operator may build and sign a distribution that adds entries to either binding map and may raise, never lower, the required set (§2.4 W3). Boot prints every departure from the release bindings, and each generation's digest and signer set is written to the audit chain. Hosted runs the release distribution only. In-process Go shares the address space, so the bindings, the per-plugin role and the import boundary stop a missing, failed, mis-composed or mistaken plugin, not hostile code; hosted therefore runs every third-party plugin out of process, one instance per tenant (§2.4 W4).
- **Five mechanisms, each generic (plugin record §7).** M1 required inject: a dispatcher injects the policy services, so without an ACTIVE provider the capability does not exist. M2 owner-side guard: a contribution is reachable only through its dispatcher. M3 bound providers. M4 bound consumers and no ambient authority: a per-plugin database role, secrets scoped (tenant, plugin, name), write credentials only from `credentials.Write(token)`. M5 monotonic gates with a static expected set: every listener runs, the strictest verdict wins, none may grant, and a listener that should be there and is not ACTIVE denies.

### 4.3 Rules under the catalogue

- **Kernel, launcher and import boundary.** `sdk/kernel` has no `require` line, no product word (tenant, role, profile, row, SQL, HTTP, job, approval, audit, model, health, gate), no policy number beyond three deadlines (load, drain, dispose) and no service name beyond its four built-ins (`reflect`, `registry`, `hooks`, `logger`). `boot/` and `loader/` have a closed vocabulary and import no domain definition. Growth past the line budget fixed at the S0 exit needs an ADR. Three Go modules: `sdk/kernel`; `sdk/def` (definitions, `sdk/plugin`, `sdk/gate`, in-memory fakes, suites; it requires `sdk/kernel` and pgx v5); `sdk/testkit` (`kerneltest`, `sqlfake`; test-only). `plugins/A` never imports `plugins/B`. No `fake` or `sdk/testkit` package may appear in the module graph of a server binary; the builder and the gate check it. All of this is checked in CI, not by review (plugin record §3).
- **No side door, no use after release, and provider rules.** The method set of a provided value is a subset of the definition's interface. Every registration method takes the caller's context first, and every suite asserts that a call after the provider is disposed returns `ErrInactive`. Go traps are provider rules: River has no worker removal, so `jobs-river` dispatches through a revocable handler table and a job of an unowned kind snoozes. `http.ServeMux` cannot unregister, so `http-server` keeps a copy-on-write route table and answers 503 for a declared route whose owner is not ACTIVE. `metrics` gives each fiber its own registerer.
- **Transaction contract.** One `Tx` type sits behind `sql`, `sql.Bound` and `platformSql`. It carries no SQL-string method: a plugin reads and writes through the typed operations of its own reviewed catalog, the provider generates and binds the statements, and only the infrastructure participants keep a raw-driver path on the same transaction (ADR-045, owner decision 2026-11-19; the operation API is ratified with the `sql` definition at S3). Only the infrastructure definitions `jobs`, `events`, `audit` and `kv` take a caller's `Tx`, and each suite asserts that a rollback leaves nothing enqueued, emitted or appended. A cross-tenant or tenant-less enqueue, emit or fan-out needs `platformSql`. A remote contribution joins no transaction: it returns a result and its dispatcher commits state, event and audit together. The `sql` view is available to a caller only when that plugin's declared schema version is applied (§5.2).
- **Hooks.** Definitions declare typed hooks: `Event` (four Cordis modes) and `Waterfall` in the kernel, and `Gate` in `sdk/gate`, where the strictest verdict wins. Order is by declared stage, then plugin id. Only the owner dispatches, a plugin declares the hooks it listens on, and every dispatch names its audience, so one tenant's payload never reaches another tenant's listener. A remote listener is allowed only on hooks marked remote and receives the scrubbed payload. Paging and the audit append have no hook. Two hooks have first-party listeners that the hook list does not name as rows. `incident/correlate`: `storm-mode` is the first stage, and fold rules follow on their trigger (§2.1 row 5, §7.3). `incident/investigate`: `storm-mode` is the one listener and is in the expected set, so the gate denies while it is not ACTIVE. The other two uses the hook list gives this gate are not listeners. The daily budget and the run slots are leases that `agent-runs` takes before a run (§2.1 row 13; 03 §8.2). The P2 per-incident run cap (§5.5) is the owner's own check: `casefile` reads it from `TenantLimits` before the dispatch, as it reads the kill switch. `run/first-message` and `run/answer` are owned by `agent-runs` and dispatched with the pillar and the kind, so a pillar group names its builder and checker, and `agent-runs` starts no run while a named one is not ACTIVE (§6.1); `loop/pre-step` and `loop/tool-result` are owned by `harness-native`, signed and not remote, and a listener there may only tighten tools and directives. The `agents-paused` switch is read by `casefile`, `agent-runs` and `llm-gateway`. The hook list is plugin record §8; `aiopsctl profile render --dump-hooks` prints every chain, kept as a golden file per shipped profile.
- **Versioning (ADR-040, decided 2026-11-11).** Every definition has its own `major.minor`; the major is in the import path, the key and the proto package. There is no single SDK range. A manifest carries a generated `requires`: the author API version for in-process code, the remote protocol majors for remote code, and each definition as `major.minor` (for a pack with no code, the definitions its rows feed). A signed distribution manifest carries a generated `serves`, and the gate compares the two. A major is any change that could fail a plugin that passed the suite; a minor is additive, which for a provider or a contribution means a new optional capability, never a new required method. On a stable major a plugin attested on `1.3` runs where `1.y` with `y >= 3` is served. At major 0 every minor may break, so the exact minor is needed unless `definition.yaml` carries `compatibleFrom`. **Support window.** When `v<N+1>` of a stable definition ships, `v<N>` stays served through an adapter row, proven in CI by the old suite, for at least 12 months and two further minor releases, and leaves only in a platform major release; at most two majors of a definition are in service. The window covers consumers and contributions; a third-party provider of an open singular key moves with the major. **Promotion to `v1`** is a release review decision once a release has shipped with the definition, a `contrib` definition has passed its suite through the remote adapter and, for the four vendor-neutral read seams (`signals`, `tools`, `evidenceSources`, `estateSources`), a second contribution or pack for a different backend family has passed, a condition the review may waive with a recorded reason. `v1.0` is contract-identical to the last `0.y`, which stays served beside it through an identity adapter for the window. **Other contracts.** The manifest schema, the index format and the handshake message are frozen-additive from their first release; the first message of a protocol major reserves one optional field that nothing reads in the community edition; the author API is `0.y` and the remote protocol is major 0 until platform 1.0, after which the kernel serves the current and the previous protocol major. Detail: community record §4.
- **Upstreams (principle 9; ADR-054).** An upstream's name never appears in a definition, hook, proto, fake or suite, in `sdk/`, `boot/` or `loader/`, in a dispatcher, a policy row or a row of `aiops-core`, or in a container id, compose service, chart key, database or metric. The row that wraps an upstream, and a bundle whose rows all wrap it, carry its lowercase technical name once, as the suffix, when its register entry allows it (§8.1); rows of a stack bundle keep role names. The stated exceptions are contracts, not defaults: the PostgreSQL dialect behind `sql` (§2.4 W2), the two query dialect keys, protocols with several implementations (the S3 API, the OpenAI-compatible API, OIDC, SMTP, OCI, OTLP, the Kubernetes API, MCP), the Cordis semantics of the kernel and the default stack bundle. A row of `aiops-base` may wrap an upstream only if it is on the base provider allow-list of the register (the protocol providers and `jobs-river`), and an upstream library is imported only inside the plugin that wraps it. The register and its verdicts are checked at release (U7); the name lint (U1), the import boundary (U2), suite neutrality (U3) and the leave-one-out render of every shipped profile (U4) run in CI before the first community release (harness record §7; licence record §7.2).

## 5. Tenancy and data ownership

### 5.1 Tenant id rules

- **Format.** A tenant id matches `[a-z0-9]([a-z0-9-]{0,59}[a-z0-9])?`, at most 61 characters so that `t-<id>` is a valid DNS label, enforced at tenant create from day one (plugin-architecture §2.5).
- **Reserved ids.** Tenant create refuses `default` (reserved for the self-host tenant), `anonymous` (Pyroscope's multi-tenant segment directory), `fake` (Loki's single-tenant id), `admin`, `platform`, and anything matching `aiops*`, `kube-*` or `system*`.
- **Never reused.** A purged id keeps a tombstone row in `tenant_directory.tenant_tombstone` and is never created again, because the backends create tenants implicitly and a reused id would inherit leftover data (Pyroscope segments, late Mimir uploads, Loki chunks waiting on retention).
- **One string everywhere.** The same string is the `X-Scope-OrgID` on all four backends, the kernel `tenant_id` column, the secrets scope, the blob prefix `aiops/<tenant>/` and the key for the Grafana org mapping. The tenant's Kubernetes namespace is derived as `t-<id>`. Self-host uses the single tenant `default`.
- **Never derived from a payload.** Agents: the JWT `orgid` claim. Webhooks: the per-tenant ingest token, plus HMAC for dashboard alerting. Chat: the surface's installation record (for Slack, `authorizations[0]`) and its grants. Grafana (P2): app instance settings verified against the app token. API: the kernel binding of the OIDC subject. A missing or ambiguous tenant is a hard reject. A job or event runs under the tenant of the transaction that wrote it: the `jobs` or `events` provider stamps the tenant in its own column and never reads it from job args or an event payload.
- **Tokens.** Write-scoped tokens never carry a pipe. Cross-tenant read tokens are admin-only.
- **Tenant record.** `tenant_directory.tenant` carries `plan`, `status`, `cohort` (§6.4), `pool` and `cell`. `cell` has a single value until P3, so adding cells later needs no migration.
- **Tenant handle.** Inside a process the tenant travels in the call's `context.Context` as `tenants.Handle`, an opaque in-memory value with no exported constructor. It is minted only through the consumer-bound key `tenantMint`. Its provider is `tenant-handle`, a stateless row that injects nothing, so the providers of `jobs` and `events` mint with no need on `tenant-directory`, which itself injects `audit` and `events` (§2.3). The binding lists every entry dispatcher: the providers of `http` (after identity), `jobs` and `events`, `signal-core` (ingest token), `fleet-agentapi` (agent JWT), `chat` (installation record), `remote` (the connection), `tenant-trees`, `tenant-lifecycle` and platform fan-out jobs. `sql`, `secrets` and `audit` read it, and no handle means zero rows. Tenant identity is never a string argument of a plugin API.
- **Tenants in the composition.** A tenant is a child context with a typed scope value kept by `tenant-directory`; the kernel never learns the word tenant. A row is process scope by default: one fiber serves every tenant, reads tenant fields with `tenants.ConfigFor` and keys every in-memory table by the handle's tenant. It is tenant-toggleable only if it registers contributions and hook listeners and nothing else. A plugin is `scope: tenant` when it keeps a tenant's client, credential, process or remote instance, or when a tenant may toggle it and it owns routes, jobs or subscriptions. `tenant-trees` then mounts one group per loaded tenant, where data is reached only through bound views that take no tenant argument (`sql.Bound`, `kv.Bound`, `blob.Bound`, `secrets.Bound`, `audit.Bound`, `sidecars.Bound`, `tenants.Bound`). A `scope: tenant` row may be declared as a child of a process-scope `core:group`. An external harness is not such a child: it is a top-level `scope: tenant` row of its own optional bundle, mounted in each loaded tenant tree, and a pillar group selects it through its `harness` field (§2.1 rows 2 and 12), so one harness row can serve the incident, compliance and FinOps agents. Where a group does declare such a child, the group mounts its process-scope children only. `tenant-trees` mounts the `scope: tenant` child in each loaded tenant's group under the same composed id (`<group>:<id>`) and adds the declaring group's row-level `inject` to the child's own, so the child is PENDING for the same reason as its group and is absent where the group is disabled. A group's `isolate` and `intercept` do not reach such a child, and `profile render` rejects a group that sets either and holds one. From S4b a tenant tree is a cache (until then `tenant-trees` mounts one pinned tree per tenant of the directory): it mounts on first use and unloads when idle; a cold lookup waits for it (a job snoozes, a synchronous path answers 503 with `Retry-After`); rows on the ack or page path are pinned. `Isolate` separates names, never memory or data: data isolation stays with RLS, the gateway, per-tenant keys and per-tenant upstream processes (plugin record §10; budget under ADR-036).

### 5.2 What the kernel database stores

Every tenant table carries `tenant_id` (platform tables excepted). RLS is on in every profile, self-host and dev included, with `FORCE ROW LEVEL SECURITY` on every tenant table, and the `sql` conformance suite proves that a transaction with no tenant handle sees zero rows. There is one schema per plugin id, with one owner, and one PostgreSQL role per plugin: no login, limited to that schema, applied by the `sql` view with `SET LOCAL ROLE`. The runtime role owns no table. Another plugin reaches a schema only through its owner's definition. `events` and `audit` rows are written through `SECURITY DEFINER` functions their providers own, and `jobs-river` switches to its own role around River's `InsertTx`, so a plugin cannot write approval, change, audit, outbox or River rows through `sql`. Cross-tenant operations run on the worker role under the platform role (`platformSql`), never on kernel-api. Migration is a durable effect run by the `durable` leader under the owner role: a consumer whose schema is behind stays PENDING, and anything applied before a generation commits is expand-only. **Durable namespaces.** `Spec.Durable` declares what a plugin owns, each derived from its plugin id: the schema and its version, the `kv` and `blob` key prefix, the job-kind prefix, the secret scope, sidecar instances (pod label) and `external` steps (a backend tenant, a database of an external engine, a KMS key). The `durable` plugin records every namespace of every generation, per tenant. Disable keeps durable state, `plugin remove` detaches the row and keeps it, and `plugin purge` drops it (ADR-042).

### 5.4 Secrets and credentials

**Envelope encryption.** Each tenant has one DEK, wrapped by the KEK from the bound `kek` provider: `kek-local-file` in self-host, and from P2 `kek-kms` in hosted, with one KMS key per tenant. Secrets are scoped `(tenant, plugin, name)`, and a plugin cannot read another plugin's secrets. Write-scoped secrets leave the store only through `credential-lease`. Only secrets are encrypted; run transcripts and tool results (`agent_runs`), raw groups, interaction logs and usage are plaintext rows.

**Erasure bound.** Deleting a hosted tenant schedules deletion of its KMS key, which makes its wrapped DEK, and so its secrets, unreadable in live stores and in backups. Plaintext rows leave live stores when the delete saga's schema step passes (§5.6) and leave database backups when the backup retention expires. ADR-009 sets the backup retention and publishes the whole bound; we do not call this crypto-shredding.

### 5.5 Per-tenant limits

- **Backend limits.** `TenantLimits` (gap-tenant-gateway §5.2) is the single source. Until P2 the single tenant's backend limits are static chart values. From P2 four renderer rows, contributions to `limitsRenderers` under `limits`, emit complete tenant blocks, written by one single-flight job per backend (`unique: (backend)`) that renders every current `TenantLimits` and writes with a resourceVersion precondition. `traces-store` reads one file and keeps no last value, so its block is validated with the pinned Tempo binary and written atomically. Metrics, logs and profiles mount theirs with `optional-keep-last-value-on-failure`, so an unparseable render never takes down ingestion.
- **Blast-radius guard (P2).** The job diffs each render against the last applied file. It refuses, and raises a tenant event, when a reconcile triggered by one tenant changes another tenant's block, or when any limit drops by more than 50 % without an operator flag.
- **Drift and sharding (P2).** The reconciler reads back `/runtime_config?mode=diff` and `/api/overrides?scope=merged` and records drift as a tenant event. `ingestion_tenant_shard_size` is on by default in hosted.
- **Shared-part knobs.** `TenantLimits` also carries ruler and Alertmanager limits, read-path shuffle sharding (`max_queriers_per_tenant`), the dashboard pool `[quota]` per org (including `org_alert_rule`), per-tenant kernel-db storage, the cap on pending ingest jobs and on raw-group bytes per day, and the Envoy `local_ratelimit` keyed on `orgid`, set well above the plan limit and answering 429, which agents retry. Mimir's per-integration notification rate limit and receiver firewall limits are set per tenant too; their key names are not in the research and are confirmed in P1.
- **Kernel-side defaults.** Alerts 50/s sustained, 1,000 burst, 10,000 open; storm mode above 500 alerts/min; run concurrency the smaller of 2 and the model endpoint's parallelism (an operator value until the P2 probe); run jobs take incident runs before chat turns and a higher incident priority first, on the job priority the `jobs` provider already has; at most 50 open `unmapped:` incidents, above which further unmapped alerts join one digest incident. The admission bucket counts requests and bytes; storm mode counts alert items, including the truncated count a sender reports. From P2: a body limit and a bucket per `signal-ingest-*` row, a per-incident cap on investigation runs, and caps on `estate` entities and relations (initial 100,000 and 1,000,000). The same document carries the LLM budget, the per-run caps keyed by pillar and kind (steps, tool calls, tokens, deadline), the on-call limits (schedules, policies, steps, pages per hour), the agent count and the chat digest interval. Where each limiter keeps its state is fixed in 03 §8.2: hot-path fences per replica at limit/N, money and concurrency as PostgreSQL lease rows.
- **Ingest SLO.** Per tenant, at least 99.9 % of write requests over 28 days get a 2xx or 429 from the gateway. It is measured from Envoy access logs by route group and response class, aggregated outside Envoy so tenant labels stay out of Envoy's stats. Any rise of gateway-generated 401 or 403 on write routes pages within 5 minutes, independent of agent self-monitoring. The token endpoint targets 99.9 % success and p99 below 100 ms at 300 req/s; the S7 load test measures both and records the figure, and the pass threshold is a gate of S9b (§7.2). These are initial targets, reviewed at the P1 exit.
- **Suspend.** `status: suspended` makes `auth` refuse tokens. Backend limits stay as the second fence.

### 5.6 Tenant lifecycle

- **Create** is an idempotent saga in kernel-worker, run by `tenant-lifecycle`; each participating plugin performs its own step on the `tenant/create` hook, in serial order with compensation: limits blocks (P2); dashboard org and data sources in a pool (P2); DEK and its KMS key (hosted); bootstrap token; the step of each composed on-call provider plugin (the default provider has none); the alert router's contact point with the `Watchdog` rule, the `platform-page-path` rule group and their routes (§2.1 row 5); and, in hosted from P2, the shipped rule files into the tenant's ruler. Self-host loads the rule files from the chart or compose.
- **Suspend** stops token issuance, scales sidecars to zero and keeps all data.
- **Delete** is an ordered saga in kernel-worker. Its participants come from the `durable` registry across all generations, not from the listeners that happen to be loaded: the saga does not finish, and the tombstone is not written, while any participant has not reported. A disabled, failed or detached plugin still has its `sql`, `kv`, `blob`, job and secret namespaces purged, by the owner of the namespace kind and by plugin id. An `external` namespace of a detached plugin blocks the saga until the plugin is attached again or an operator records the manual step (ADR-042). Each stage's status is visible on the tenant. The order is unchanged and is expressed as stages:
  1. `quiesce`. Set `status: deleting`. `auth` refuses tokens. Backend deletes wait out the last token TTL and the Mimir ingester flush, so no late upload lands after them.
  2. `backends`. Run the backend steps in gap-tenant-gateway §5.3. A `status: deleting` block with 1 h retention stays in all four limits files until verify passes; the limits job renders deleting tenants from `tenant_directory.tenant_limits`, not from whether the tenant row is present.
  3. `domain`. Purge the plugin schemas in this order: `signal_core`, `casefile`, `agent_runs`, `change_hub`, `approval`, `compliance`, `chat_surface_slack` where that bundle is enabled (the tenant's grants and bindings, and `dm_tenant_id` references to it; `apps.uninstall` only when the tenant is the installation's sole grantee), `paging`, `on_call_provider_builtin`, `llm_gateway`, `estate`, `fleet`, `auth`, then any other plugin namespace by plugin id.
  4. `secrets`, then `dashboards` (`dashboard_sync`), then `audit` (`audit_chain`, last). Every schema purge of stages 3 and 4 goes through `tenant_purge(tenant)`, the only path past the audit trigger, and each call is recorded in the platform audit chain.
  5. `external`. Clear the `external` namespaces that composed or detached plugins declared (a database of an external engine, an instance that retains run data) and remove the tenant's remote plugin instances.
  6. `key`, then `tombstone`. Schedule deletion of the tenant's KMS key (§5.4), then write the tombstone (§5.1).
- **Verify.** Mimir, Loki and Tempo pass when the tenant has no blocks or chunks left. Pyroscope passes when no level-0 segment older than the delete time plus one TTL is still uncompacted and the tenant's compacted blocks are gone; compaction lag alerts. The per-cell Kafka (ADR-011) and database backups keep data until their retention expires, and both are part of the erasure bound in ADR-009.

### 5.7 Cell network rules

Tenant isolation rests on the gateway injecting `X-Scope-OrgID`, because none of the backends authenticates (grafana-stack §12.1). So nothing else in the cell may reach a backend, and nothing that dials a tenant-supplied URL may reach the cell.

- **Data-plane ingress.** The data-plane namespace is default-deny. Backend pods accept ingress only from `gateway` and from the backends' own pods. Rulers and Alertmanager reach the ingest endpoint by its public hostname.
- **Dead-man path.** The `metrics-store` Alertmanager sends the `platform-page-path` alerts straight to the platform-health receiver, a static email or webhook receiver from operator config, so that path does not cross the kernel (§2.1 row 5, ADR-021). Where the bound on-call provider returns a heartbeat target of its own, `Watchdog` is also sent straight to it.
- **Tenant-supplied URLs.** Pods whose only in-cell peers are fixed (dashboard pools; the `metrics-store` Alertmanager, whose fixed peers are the platform-health receiver and a provider's heartbeat target) get an egress NetworkPolicy that allows those peers and denies node, pod, service and link-local CIDRs. Kernel processes, which must reach their database, dial every tenant-supplied URL (notifier webhooks, runbook fetch, a bring-your-own LLM base URL, a customer cluster URL, an MCP server URL) through the `dialer` key, provider-bound to `dialer-guarded`, which refuses those ranges after DNS resolution. The refused ranges are row config of `dialer-guarded`: the cell ranges in hosted, and link-local only by default in the self-host profiles, where the operator's own stores sit on private addresses (ADR-047).
- **Tenant data sources.** Provisioned read-only, and tenant admins map to the Grafana Editor role (§2.1 row 8).
- **Proof.** `test/cell-network/` shows that a pod in the cell cannot reach a distributor, query frontend, compactor, ruler or Alertmanager API with a header it picks, and that a tenant-supplied URL cannot reach a cluster CIDR.

## 6. Profiles

### 6.1 Composition, generations and reload (layers lowest to highest precedence, mapped from dsh-architecture §3.2)

| # | Layer | dsh equivalent |
|---|---|---|
| 0 | Empty root | `cordis.yml` `[]` |
| 1 | Bundle patches, in the profile's bundle order | `dsh.profile.bundles` |
| 2 | Profile layer `$AIOPS_HOME/profiles/<name>/aiops.patch.yml` | profile user layer |
| 3 | Site layer `$AIOPS_HOME/aiops.patch.yml` | home user layer |
| 4 | `--patch <file>` overlays in argv order, never persisted | same |
| 5 | Tenant overlay `tenants/<id>/aiops.patch.yml`, from S4b: `enabled` and the fields a row's schema marks tenant-writable, within the limits of the table below | ours |
| 6 | Environment kill switches `AIOPS_AGENTS_PAUSED` and `AIOPS_TELEMETRY_DISABLED`, read by `boot` into the `killSwitches` launch service; config cannot undo them. They are not listeners: `casefile` reads `agents-paused` before it dispatches `incident/investigate`, `agent-runs` before every run and `llm-gateway` on every model call, and `telemetry` reads `telemetry-disabled` and exports nothing while its row stays ACTIVE | `DSH_TELEMETRY_DISABLED` |

| Field or action | Layers 1 to 4 (bundle, profile, site, `--patch`) | Layer 5 (tenant overlay) |
|---|---|---|
| `insert` | A new id only; an existing id fails in every layer. `plugin` and `roles` are fixed at insert and no patch changes them | Never |
| `config` | Replaces the whole config; there is no deep merge | Only fields the schema marks tenant-writable, validated when written, volatile by rule, literal values |
| `enabled` | Yes, except the last enabled provider of a provider-bound key | Only on a `scope: tenant` row or a tenant-toggleable process-scope row; never a row in a required set, a row that listens on a gate, or a provider of a bound key |
| `required` | May be raised, never lowered | Never |
| `inject`, `isolate`, `group` | Yes, never on a required row, a provider of a bound key, or a group that holds one | Never |
| `intercept` | Yes; for a provider-bound key, bundle layers only | Never |

- **Row format.** A row is `{id, plugin, config, enabled, required, roles, inject, intercept, isolate, group}`. `plugin` is the manifest id and replaces `type`. `inject`, `intercept`, `isolate` and `group` are the Cordis loader's entry fields. `roles` is ours: every row of a server bundle states it (lint), so no row lands in the internet-facing role by omission. Row order carries no load semantics. `core:group` nests rows (a pillar, a tenant tree) and `core:include` mounts a file-backed tree.
- **Patches.** A patch targets a row by `id`. An unknown id prints a warning; an empty patch file fails boot; only direct bundles contribute. Swapping an implementation means disabling one row and enabling another, within the allowed set for a provider-bound key (§4.2). Budget and limit keys live in `TenantLimits`, which only operators edit. Whether a row's upstream process is shared or per tenant follows from the `sidecars` provider the bundle composes and is never tenant-writable; the manifest's `scope` replaces `tenantScope` and `instancing`.
- **No expressions, closed references.** Rows carry no expressions. A platform gate is `roles`, a presence gate is a row-level `inject` (the row stays PENDING and says what it waits for), and a path or secret is a reference `${env|file|secret|flag:value}` resolved by `config-refs`. References are legal in layers 1 to 4 only, `env:` only for names with the prefix `AIOPS_REF_` and `file:` only under one directory named by flag. A layer 5 value that contains `${` is refused at write, except `${secret:name}`, which resolves in the scope (that tenant, the row's plugin). Dumps print references unresolved, and a reference that fails to resolve is an error on the row.
- **Install, distribution and admission.** `aiopsctl plugin install <spec>` takes a signed OCI artifact; install is not enable and runs no third-party code. A remote plugin, or a pack with no code, is locked by digest in `plugins.lock`, its bundle is appended at the end of the profile's bundle list, after the profile's own bundles, with its rows disabled, and for a remote plugin a deployment unit is rendered; no rebuild. The bundle of an installed artifact may only insert rows, each disabled, of its own plugin or of a first-party plugin marked `instantiable`; they mount under one group named by the artifact, and their secret scope and purge key are the artifact's (§6.2). An in-process Go plugin answers `rebuild-required`: `dist.yaml` (`release`, `plugins`, `bindings`, `acceptLicenses`) feeds `aiopsctl dist build`, `dist sign` and `dist use` (§2.4 W3). `trust.yaml` lists signers limited to id patterns and runtimes, the distribution keys, indexes limited to the id patterns they may list, and `allowUnsigned`, which is empty in hosted (plugin record §11). The compatibility gate is `boot` library code that reads manifests only and runs at build, check, install, boot, every recomposition and every remote handshake. Its ten checks: manifest schema and author API version, definition versions (`requires` against `serves`, §4.3), remote protocol, stability, trust, licence, key and hook classes, layer rules (with the insert-only rule for an artifact's bundle), remote scope, conformance attestation. A denied row is detached as disabled and the dump names the unmet check; hosted denies exemptions. `plugin-manager` is a plugin whose every operation is audited and submitted to the reload queue; it cannot disable itself, a required row or the last provider of a bound key, and it is not an agent tool. It ships at S6a working on the profile files; cohort update, quarantine and exemptions by version are methods added at S6b, so the binding maps do not change (plugin record §12).

**Reload.** The unit of reload is the row. The unit of change is a generation: one immutable composed tree with a digest over the tree, the module table and the lock digests of every remote plugin and of every pack with no code, so a generation also pins plugin and pack versions. A failed fiber is sticky in the kernel and retry is the `restart-policy` plugin. The process is replaced, not restarted in place, in three cases only: a process-scope fiber leaked past its dispose deadline, a restore failed, or `restart-policy` gave up on an infrastructure provider.

| Change | Applies |
|---|---|
| Only `Volatile` fields, which include every tenant-writable field | Committed in place by the loader; no restart, unless the old or new value holds a reference, which restarts the row (ADR-059 decision 17) |
| Other `config`, `inject`, `intercept`, `isolate` | That fiber restarts; its dependants restart only if it provides something, through their epochs |
| Enable, disable, insert or remove a row whose code is present; a tenant overlay | Live; an overlay touches that tenant's scope and tree only |
| A provider the replica cannot serve without (`sql`, `jobs`, `events`, `http`) | In place, in every profile: the replica fails readiness, quiesces under the drain deadline, the fibers restart and consumers return by epoch. No exit. A process-scope generation therefore goes to one replica at a time. A provider swap of a `durable` definition (`events`, `jobs`, `kek`, `blob`, `kv`) is admitted only when the old provider reports `Drained()`, or with an audited `--accept-loss <definition>` |
| New code | In process: a new binary and a rolling restart. Remote: live; the new instance is handshaken before the old contributions are removed |

- **One queue.** The `reload` plugin owns one queue; file watches, the generation follower, the manager and `aiopsctl` all submit to it. A submission is composed, admitted and planned with nothing touched, applied in one batch, then settled and judged: every row this generation created, changed or enabled and every required row must be ACTIVE, and a row that was ACTIVE must still be. The verdict is published as `composition/applied` into the audit chain. Without the `reload` row every change answers `restart-required`. `ConfigReader.For` is deleted: tenant fields are read with `tenants.ConfigFor`.
- **Generations.** On one process, which is every profile of the first community release, the `reload` row is the committer: it holds one PostgreSQL advisory lock, applies a generation, judges it and commits or restores it, and a second process that cannot take the lock fails readiness and names `composer`. From S4b `composer`, a leader on the worker role and a base row of every profile that runs more than one process, owns one state machine per scope: `proposed`, `canary`, `promoting`, `committed` or `rolled-back`. Replicas report and never select a generation. A generation of either scope gets one canary replica per role that mounts a row it creates, changes or enables: up to three in hosted, one where the process runs `--role all`. Each canary judges the rows of its own role, and any failed verdict during canary or promotion rolls the scope back on every replica. The order of the canaries of several roles, and how a generation reaches several self-host replicas one at a time, are ADR-038. The `durable` leader creates what a candidate adds before its canary and deletes what a generation drops only after it commits. The process-scope generation is read by the launcher before any row mounts, so it is never in a table that a row of the same generation serves. Self-host: the layer files on disk (`reload-watch-files` is on in `dev`, off in server profiles). Hosted: the generation object (§3.1), followed by `reload-generation`; a restarted replica boots the committed generation, never an unjudged candidate. Tenant-scope generations and replica reports, and in hosted the profile layer, `plugins.lock` and the trust policy, are platform tables of the `composer` schema, written only through `plugin-manager` on the worker role.
- **Required set.** One concept with two sources: the distribution manifest, which no layer can remove, and `required: true` on a row, which a layer may add and never remove. It is written by what must work: keys that must have an ACTIVE provider, plus a few rows named by id. Every server profile requires the keys `sql`, `jobs`, `events`, `http`, `secrets`, `kek`, `tenants`, `identities`, `audit`, `approval`, `pii` and `durable`, and the rows `loader`, `restart-policy`, `reload` and `readiness`, and `composer` in every profile that composes it; with any executor row also the keys `changes`, `credentials` and `executors`. Hosted adds the keys `tokens`, `gateway`, `signals` and `sidecars` and the rows `fleet-agentapi`, `signal-ingest-alert-webhook` and `kek-kms`. A required key or row that is absent, disabled or not ACTIVE stops boot; with `--role` the set applies to the rows that role runs. Every other row degrades to one grouped warning that names its state and what it waits for. At run time, losing a policy provider (`approval`, `changes`, `credentials`, `audit`, `pii`) does not exit the process: its consumers unload, their routes answer 503, write readiness fails and the provider is retried in place. What keeps running depends on the provider. Without `approval`, `changes` or `credentials` no approval is decided and no executor is reachable, while ingest, correlation and paging, which never inject them, keep running. Runs keep running without `approval` or `credentials`. Without `changes` a run of the incident pillar waits: `context-pack`, `rca-contract` and `tool-change-lookup` inject `changes` and are PENDING, `agent-runs` starts no run while the first-message builder or the answer checker that the pillar group names for it is not ACTIVE, so the `investigate` job snoozes and the timeline says what it waits for. A run never starts without its context pack and answer spec. Runs of a pillar whose builder and checker do not inject `changes` keep running. Without `pii` the four dispatchers that inject it unload (`llm-gateway`, `notifications`, `chat`, `tools`), so no model call, tool result, chat message or notice leaves and runs wait; ingest and correlation keep running. Pages of the built-in on-call provider leave through `notifications`, so they wait too and the `platform-page-path` route fires; an external provider keeps paging. Without `audit` every state-changing provider unloads (plugin record §7), so nothing that writes runs on that replica until the provider returns: ingest answers 503 and senders retry (§2.1 row 5), and the `platform-page-path` route, which does not cross the kernel, still reaches the platform-health receiver. Losing an infrastructure provider unloads everything and is retried in place. The matrix is `test/failure-matrix/matrix.yaml`, which is both the table and the test input (plugin record §13; 08 §1.6).
- **Tooling.** `aiopsctl profile render --tenant <id> --dump` prints the composed tree with its provenance, the required set and the static closure of its needs; `--dump-config-schema` prints the merged schema; `--dump-hooks` prints every hook chain; `aiopsctl profile verify` reports every departure from the release bindings.

### 6.2 Bundles

A bundle is a data-only list of row patches. The server bundles, with their rows, content and settings, and `agent-base` are the table of §4.4. The lab (§2.1 row 18) is neither a bundle nor a profile. The agent-side bundles carry no server row, with one exception from P2, the template row of `agent-security`:

| Bundle | Contributes |
|---|---|
| `agent-host` / `agent-k8s` | systemd unit + 0600 secret + `remotecfg`-only local config / umbrella chart values for the k8s-monitoring layout + enrol Job |
| `agent-security` (P2) | The row `fleet-template-runtime-security` (template `runtime-security`) with its `runtimeSecurity` key, the first `fleetTemplates` contribution from a bundle other than `agent-base` (§2.1 row 10) and the one server row an agent-side bundle carries; the DaemonSet or systemd unit of `sensor` |
| `agent-windows` (P2) | Windows metrics and event logs only |

**Connector packs.** A connector pack makes one external observability system usable for one or more capabilities: alert intake, the agent's reads, kernel reads, change evidence, estate sources, rule content. It is a bundle published as one signed artifact (`plugin.yaml`, rows, content and at most one plugin), not a manifest kind or a runtime, and it sits in a profile's bundle list like any bundle, after the bundles whose registries it feeds. `aiops-datasources` is the default connector pack. Three sizes: a data pack (rows of the instantiable first-party plugins `tool-mcp`, `signal-ingest-generic-json` and `notifier-webhook`, plus content; no code; installed with no rebuild), a read connector (the same plus one plugin that contributes to `signals`, to `tools`, and at P2 to `evidenceSources` and `estateSources`), and a stack bundle (agents, gateway, limits and provisioning for a second stack; not planned in this edition). Packs cover capabilities, not stacks, so several compose in one profile. A pack never adds a second provider of a singular key: it ships a profile-layer snippet that repoints the existing row. A pack proves itself with the suites of the registries it feeds and with the connector scenario, one vendor-neutral script replayed from the pack's fixtures on `aiops-only`: a firing alert becomes one incident on the expected entity, the first message lists the bound signals, the default harness, on replayed model turns, makes one successful call on each tool the pack offers, and the resolve yields `cleared`. The scenario runs in `aiopsctl` and needs no container runtime. A `tool-mcp` row carries a digest of the recorded tool list of its server, and the recorded text only where the server's licence is open (licence record §7.4); its effects class is asserted by the pack, not proven, and boot says so. What stays specific to the default stack in this edition is stated in the release notes: the agent and fleet, the tenant gateway, limits rendering, backend provisioning, the dead-man rule and route, provisioned dashboards with the annotator, the shipped rule files and the lab (community record §6).

### 6.4 Cohorts

A tenant's `cohort` is `canary` or `stable`. It selects four things:

1. the image versions of a tenant's upstream sidecar processes, where an optional plugin runs one;
2. the fleet composer version its agents are served (04 §2.4);
3. the River queues its jobs land on (`canary.<kind>` or `stable.<kind>`), so a canary kernel-worker Deployment running the new binary serves only canary tenants;
4. the version of a remote plugin during `aiopsctl plugin update --cohort`, which applies to a cohort, judges, then promotes or restores.

kernel-api and kernel-edge keep the N/N-1 rolling deploy. Contract migrations wait until the stable cohort has run N for one bake period. The fleet canary for one tenant's revisions matches agents on a separate remote attribute, `ring` (04 §3.4). A cohort is not the canary replica of a generation (§6.1): the first chooses tenants, the second chooses a replica.

## 7. MVP scope and phases

### 7.1 The first community release (the P1 exit test)

The first community release is version `0.1.0`: `self-host-full` with the tenant `default` and one `aiops --role all` process, `dev`, and `aiops-only` for leg B. It is accepted when six legs pass. The scripts under `test/acceptance/` name roles and take a provider map, so no script names an upstream. "MVP" elsewhere in this file means the scope of this release. **Leg A, the operator,** is this six-step demo, with its host leg, on `self-host-full`, replayed from fixtures in CI and run live in the lab (`lab/`, §2.1 row 18), with latencies measured against D4 (gap-kernel-hot-path §2.5):

1. A VM `curl | sh` and a cluster `helm install aiops-agent` both appear in the fleet inventory within two minutes, and all four signals show on the tenant's dashboards.
2. A rule from the shipped rule files fires on one entity. The burst becomes one incident keyed on that entity, visible through the API and `aiopsctl`. The on-call person of the bound escalation policy is paged once on their first contact method (a webhook sink in CI, email or a chat direct message live) and acks by the link, the API or `aiopsctl`. A second run lets the first step time out and asserts that the page reaches the second step. If providers only ships (§2.4 W11), the default provider map binds no provider: the step asserts instead that the incident says so and that the incident notice reaches the notifier rows, and the page, ack and escalation assertions run in the `oncallProviders` suite on the definition fake.
3. The harness of the incident pillar writes an RCA to the incident, citing the last deployment, taken from the change candidates the kernel put in the first message, and log evidence read through the bound logs tool. The RCA is also written through `annotations`.
4. The incident offers rollout restart (L1), and the proposal writes the `ChangeRecord` in state `planned`. A second user approves, the `ChangeToken` is signed at dispatch, the action applies, the two zero-cost checks verify it, and the incident closes when the alert clears.
5. The compliance score answers from the findings of the two scanner payload families in the fixtures, which carry scanner-native control ids and synthetic text. A scanner-native id is not proof of clean wording, so the display allow-list works per control id and provenance: a scanner control or check that references a restricted framework shows its rule id and our catalogue wording only. The score is named after our own catalogue, never after a third-party framework (licence record §7.4). A failed control shows as a `control:<id>` incident.
6. The whole loop is visible in the provisioned dashboards and exportable from the audit chain. MVP approvals go through `aiopsctl`, the API or an enabled chat surface. With `aiops-chatops-slack` enabled, steps 2 to 4 also pass in a thread, replayed from synthetic cassettes (leg F3).

**Host leg.** Steps 2 and 3 also pass on the enrolled VM. A `host-basics` rule fires, and one `host:` incident opens with one page. The first message says that the kernel did not read host change evidence. The RCA cites a line from that stream, read with the bound logs tool and the host runbook, or states that none was found. No action button is offered, because P1 has no host executor.

**Local model.** The live run is recorded once more on an open-weight model served locally with public egress denied. That run has no pass threshold; the release notes name both models and what passed on each. Its weights are under Apache-2.0 or MIT at a pinned revision (licence record §5).

**`dev`.** The fixture replay also passes on `dev`, which composes `aiops-oncall` (§2.4 W11; not when providers only ships) and pages a local webhook sink.

**Leg B, own stores.** The connector scenario (§6.2) passes on `aiops-only` with the default pack, from fixtures recorded against a Prometheus-compatible store, an Alertmanager and a Loki-compatible store that we do not deploy. It asserts that the timeline says no policy is bound, and asserts no annotation.

**Leg C, the contributor.** C1: with `aiopsctl` and no SDK, toolchain or container runtime, the reference data pack for a logs store outside the default stack, rows of `tool-mcp` for that store's MCP server, is created from the template, passes `plugin check`, is packed, signed, installed with no rebuild and enabled, and the script of leg B passes with its fixtures. C2: with the SDK, `aiopsctl` and a Go toolchain and no kernel checkout, a `signals` contribution for a sample sender family that retries only 5xx is created from the template, passes `plugin check`, enters a distribution through `dist build`, `dist sign` and `dist use`, and delivers one alert of the scenario; the same code under the `contrib` id is green as a pull request under `contrib/` and ships disabled in the next `aiops-contrib` image.

**Leg D, index and gate.** The index lists the reference pack, and `plugin search` verifies its signature before parsing. The gate refuses a plugin that needs a definition version the release does not serve, one with a missing or foreign attestation, a manifest with an unknown major, and a pack whose bundle changes an existing row or inserts a row of a plugin that is not instantiable.

**Leg E, evaluation (§2.4 W10).** On the hand-written case set (at least 24 cases, 3 runs per arm) every case-run ends without a harness error and inside its caps, the leg A case passes 3 of 3 on the default model binding, and a smoke baseline is recorded for both models (harness record §9).

**Leg F, upstream independence.** F1: the leave-one-out render (U4) is green for every shipped profile. F2: legs A and B pass with the default provider map, which names no optional upstream plugin. F3: for each optional upstream plugin in the release (`harness-holmesgpt`, `on-call-provider-goalert`, the Slack bundle), the steps it serves are replayed from that plugin's cassettes with its provider map.

The release also requires `aiops-only` to boot in CI without `aiops-stack`, and `dev` to boot every row.

## 8. Naming conventions and glossary

### 8.1 Rules

**Trademarks.** No Grafana, Loki, Tempo, Mimir or Pyroscope in any product, repository, plugin, bundle, profile, container, tool, metric or config name. Derived marks such as LogQL and TraceQL are also excluded from names. Alloy and Beyla are treated the same, because the mark list is non-exhaustive, and no abbreviation or combined form of a mark is used. Prose may say "writes to Mimir". Service-facing terms use generic nouns: "hosted dashboard tenancy", "dashboard pools", "instance-per-tenant dashboard tier". The marks are for open-source technical prose only (08 §5.2 T4). Every document, UI page, chart README or NOTES, store listing and marketing page that uses a mark carries the policy's two-sentence attribution statement verbatim (grafana-stack §13.2; 08 §5.2 T3). The deny-list applies to every id, title and content path in the project index and in `aiops-contrib`, whoever the publisher is. Names for other vendors' systems follow community record §6.7, checked by a lint of `plugin check` and of the index, and the index renames an entry on a credible objection from a mark owner (`renamedTo`).

**Upstream names.** Outside the stated exceptions of §4.3, no id in the SDK, a definition, a hook, a schema, a metric, a container, a compose service, a chart key or a row of a bundle that a shipped profile lists contains the name of an upstream project. The exceptions are the contract names (the PostgreSQL dialect, S3, OpenAI-compatible, OIDC, the Kubernetes API, MCP) and the rows on the base provider allow-list of the register (the protocol providers and `jobs-river`); a schema is named by its plugin id (§5.2), so it carries a suffix only where its plugin does. The name of an upstream outside the default stack appears at most once, as the lowercase suffix of the plugin that wraps it and of that plugin's own bundle, and only when its entry in the upstream register is marked `suffix-ok`; an owner whose policy asks for approval keeps a generic id until cleared, and an entry with no policy read is `needs-approval` (licence record §7.5). The register is written at S2a (ADR-054), so until an entry is `suffix-ok` every such suffix in this set is a working name. `harness-holmesgpt` and `aiops-harness-holmesgpt` are `needs-approval` today, because the owner of the HolmesGPT mark is UNVERIFIED (licence record §9; LAWYER Q4): if the mark check or Q4 fails, they become `harness-external` and `aiops-harness-external`. `on-call-provider-goalert` and `aiops-oncall-goalert` wait on Q4 as well and would become `on-call-provider-external` and `aiops-oncall-external`. A row of a bundle that a shipped profile lists is named by role, as `fleet-template-runtime-security` is. CI greps the golden dumps of the shipped profiles and the SDK tree and reads the allow-list from `tools/upstream-components.yaml` (U1, §4.3).
